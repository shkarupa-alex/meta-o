## Framing: what the evidence now settles

Both proposals were revised, and the right way to judge them is against primary sources rather than internal coherence, because the original task makes verification a hard constraint and forbids accepting capability claims about Herdr/Omnigent/Paseo on assertion. On this machine: `herdr 0.8.0`, `omnigent 0.6.0`, `codex-cli 0.146.0`, `agent-browser 0.33.2`, `apm 0.27.0` installed; `paseo` and the vercel `skills` CLI absent; `claude`/`codex` resolving to `/Users/alex/bin/*` wrappers whose contents I read. I re-probed the things each proposal's design load-bears on, and this round the two documents diverge sharply on evidentiary quality — one of them has clearly gone to the primary sources and one has not.

I spot-checked roughly a dozen of Proposal 2's `[V]` claims and every one held exactly: `herdr api schema --json` is 251,527 bytes with **zero** `compact` matches; `AgentInfo.tokens` is indeed a free-form display map (`additionalProperties: {type: string}`, `propertyNames.pattern: ^[A-Za-z0-9_-]{1,32}$`), not LLM token counts; `agent_session` appears in the schema; `~/.claude/hooks/herdr-agent-state.sh` exists (3.2k, dated today); `omnigent session export --id --output` exists verbatim in `--help`; `apm install` advertises "Claude skills (SKILL.md)" with `--runtime` values including `agent-skills, claude, codex, opencode`; `agent-browser` is 0.33.2. Most importantly, the Herdr skill states verbatim at line 128: "`agent prompt` atomically submits text and encoded Enter while honoring the pane's live bracketed-paste mode," and at line 130: "This wait tracks lifecycle state, not an individual turn; if the agent is already working, completion of the active turn may satisfy it." Proposal 2 quotes both correctly and derives the correct operational rule from the second (wait for `idle` *before* prompting). This is genuine primary-source engineering, and it settles a direct disagreement between the two proposals in Proposal 2's favor: Proposal 1 prefers `send-keys` with a separate Enter for `/goal`, which bypasses the documented atomic, bracketed-paste-aware path and is therefore *more* likely to split the slash command, not less.

## Facts & Constraints (White Hat)

The one place I can materially extend both proposals is Codex goal mode, and it cuts against both. `~/.codex/goals_1.sqlite` exists and contains sqlx-migrated tables: `thread_goals(thread_id, goal_id, objective, status CHECK(status IN ('active','paused','blocked','usage_limited','budget_limited','complete')), token_budget, tokens_used, time_used_seconds, created_at_ms, updated_at_ms)` and `thread_goal_continuation_deferrals(thread_id)`. Row count is currently 0 — goal mode has never been used here — but a binary does not ship a migrated goal store with six lifecycle statuses for a feature that does not exist. This has four consequences neither proposal captures.

First, Proposal 2's risk table rates "`/goal` does not exist or is unreachable" as **high** probability on the grounds that `codex --help` lacks the word (which I confirmed: no matches, exit 1). Its epistemics are correct — slash commands don't appear in `--help`, so neither asserting nor denying is licensed — but the probability estimate is now demonstrably too pessimistic, and the whole §6.3 procedure is built around that pessimism.

Second, both proposals verify activation by *reading the terminal*: Proposal 2's criterion is "a goal-mode-specific CLI response (banner/confirmation) appears in the output, and not an echo of `/goal …` as an ordinary message"; Proposal 1's is "check visible goal UI/status." Both are screen-scraping the Codex TUI on the alternate screen — the exact channel both documents prove is lossy and unrecoverable. A `sqlite3` query against `thread_goals` for the executor's thread answers the task's literal Q24 ("как проверить, что goal действительно активна, без нового `goal.json`, FSM или proxy CLI") using state Codex already maintains, with no new artifact and no pattern-matching a banner string that will change between releases.

Third, this partially falsifies the "unavailable" telemetry verdicts at the *route* layer. Proposal 2's §19 Codex row says context/compaction telemetry is absent from `--help`, which is true, but `tokens_used`, `token_budget`, `time_used_seconds` and `updated_at_ms` are right there in the goal store. Proposal 2's Herdr verdicts are airtight (I confirmed zero `compact` hits and the free-form `tokens` field), and its route-split structure is the correct shape — it just under-researched the Codex route's on-disk state, and its own `inferred` proxy (transcript byte size) is strictly weaker than a real `tokens_used` counter.

Fourth, `status='paused'` plus a dedicated `thread_goal_continuation_deferrals` table bear directly on §6.4. Proposal 2 rejects variant A (feature-level goal through all cycles) because goal mode would auto-continue while the executor must wait for independent review — a genuinely good argument, and its selection of C is well-reasoned. But if a goal can be natively *paused* across the gate wait, A's stated defect may be preventable, so C's superiority is argued rather than established. Also `usage_limited`/`budget_limited` are first-class native statuses that map exactly onto §10's stated real-world reason for switching routes (subscription limits exhausted), which Proposal 2 handles only as a manual user decision.

One more verified constraint that matters: the Herdr skill's fallback paragraph reads, in full, "After that failed read, ask the agent to write its complete response as Markdown in a temporary directory and reply only with the file path, then read the file directly. **Use this only as a fallback; do not request file output in the initial prompt.**" That last clause is dispositive for Proposal 2's central mechanism.

## Risks & Failure Modes (Black Hat)

**Proposal 2's file-handoff-as-primary contradicts the authority it declares canonical.** Its §5.1 S1 instructs the agent to run `herdr --skill` and treat the installed binary as the source of truth. Its §5.1 S5 then puts a file-write instruction into *every* worker prompt and describes this as "exactly what the Herdr skill prescribes as a fallback, elevated to the primary path." The elevation is disclosed; the *prohibition* is not. The skill explicitly says not to request file output in the initial prompt. I think Proposal 2's engineering judgment is right — a reviewer verdict is precisely the case where the panel tail is useless in principle, and a prospective write is categorically better than a retrospective "reproduce it verbatim" — but an implementer who reads the skill (as S1 commands) will see a direct conflict and may "correct" it back, silently reinstating the lossy path that the task names a hard criterion. The deviation must be named as a deliberate override with its reason, or the two instructions will fight.

**The premature-idle detector is self-reported and shares a root cause with the failure it detects.** Proposal 2 calls the STATUS block "the only thing compensating for the absence of goal mode." But an executor that has prematurely convinced itself the scope is done will print `SCOPE-COMPLETE: yes`. The detector catches honest-but-incomplete stops (real and common) and misses confidently-wrong ones (the exact failure `/goal` exists to prevent). Its `QC: pass|fail|not-run` line is verifiable by the orchestrator re-running `make mo-qc`, and `CLEAN COMMIT` by `git status --porcelain` — but `SCOPE-COMPLETE` is not verifiable from the block itself. The spec should pair it with an orchestrator-side spot-check against the spec's requirement list, or drop the "only thing compensating" framing.

**`refs/mo/candidate` is a single global ref with no collision or staleness semantics.** It is the one fact the methodology persists outside sessions, which makes its naming load-bearing. Two features in flight in one repo — entirely plausible here, since the task explicitly contemplates self-hosting the methodology while also running product work — collide silently on the same ref. And a ref left over from a feature finished three weeks ago will be picked up by the §4.1 no-argument flow and reported to the user as an unfinished candidate. Proposal 2's risk table covers only "forgotten during manual manipulation — low — it's a hint, not a source of truth." Cheap fix: `refs/mo/candidate/<branch-slug>`, deleted on completion.

**`interrogate fail-under=100` with every ignore disabled will manufacture ritual docstrings.** Proposal 2 handles the GRACE-versus-task contradiction more honestly than I expected — it quotes GRACE's risk-proportional density lines, states that the task demands the opposite, and resolves by splitting mechanical coverage from reviewer-judged depth. That is the right decomposition. But `ignore-nested-functions=false, ignore-magic=false, ignore-private=false` at 100% means every closure and every `__repr__` needs text, and the only escape hatch offered is a file-level exclusion list for generated/vendored code. The task warns specifically against "бессмысленные повторяющиеся docstrings." A symbol-class exclusion mechanism (trivial accessors, closures under N lines) is needed alongside the file list, or the depth rule ("one line suffices") becomes a license that reviewers must enforce thousands of times.

**A dangling cross-reference under the entire QC evidence base.** §14 opens: "Все данные ниже — `[V]` с первоисточниками (см. §21 «источники исследования»)." §21 is titled "Рефлексия после существенных сбоев." No sources section exists anywhere in the document. So the Oxlint claims I cannot verify offline (type-aware stable 22.07.2026, 59-of-61 rule parity, 12–18× benchmarks, TypeScript 7.0+ requirement, absence of JSDoc/`max-lines`/`max-depth` rules) have no reachable citation. Those claims are load-bearing for N-028 (compatibility profile as default). For an implementation-ready document this is a real gap, even though the conclusion it supports is conservative and likely correct.

**Proposal 1's defects are carried forward unrepaired.** The revision genuinely improved completeness — the three-level table now covers all seven mandated dimensions, §18 audits every `.mjs` individually (including the nine `quality/` scripts I flagged), §10 adds an attention policy, and the helper became conditional with an admission test, which is a strong addition. But not one of the three verified capability defects from the previous round was fixed. §7 still resolves lost alternate-screen output by asking the reviewer to "записать предыдущее сообщение verbatim в Markdown-файл" — retrospective regeneration, not retrieval, from a context that may have been compacted, which is the same class of silent lossy substitution the task forbids; the transcript JSONL that Herdr's own `agent_session` pointer and the installed hook expose is never mentioned. Goal activation is still verified via "visible goal UI/status." The §7 capability table still has no route axis, so it reports "Context fill: Unavailable на Herdr layer" and "Last-turn time: Inferred" as the whole answer to a question the task explicitly scopes per-route. Every Paseo cell is still marked "Available" — session status, full transcript, last-turn time — with no version and no `inferred` label, for a CLI that is not installed; §23 notes the schema must be checked but the table still asserts availability. The successor rule still requires "подтверждённый `lineId`" while `ModelRef.lineId` is optional and no derivation rule is given, so on the real catalog (`gpt-5.6-sol`, `-sol-wm`, `-terra`, `-luna`, `gpt-5.5`, `gpt-5.4`) it either needs a hand-maintained lineage map or degrades permanently to `AMBIGUOUS_LINEAGE`. And `skills/adopt-project` still receives no verdict in either audit table, despite §18 being exhaustive down to individual test fixtures. Proposal 2 answers every one of these: prospective file handoff plus `mo-lastmsg` reading the JSONL; per-route tables with Paseo marked entirely unvalidated; a concrete vendor+family successor rule with worked examples and a stated reason the catalog snapshot is required (without a prior snapshot you can say "exists," not "is new"); and `adopt-project` → `mo-setup`.

## Strengths & Benefits (Yellow Hat)

Proposal 2's opening §0 is the single most valuable thing in either document: it establishes that the current implementation's central advertised guarantee — `session read --complete` — is not merely heavy but *wrong*, doubling a line window to 32000 and then returning `text: ""` with `truncated: true` without ever extracting the envelope, over a channel whose own documentation says the rows are gone. That reframes the whole exercise from "simplify" to "replace a broken control plane," which is a stronger and more honest mandate, and it justifies deletion on correctness rather than taste. The §3.4 table of explicitly cancelled guarantees, each with what replaces it and what is genuinely lost, is exactly what the task's "удаление state/CLI не маскирует неразрешённый hard requirement" criterion asks for.

The §5.4 argument against a shared adapter is the best I have seen on this question and I could not break it: the three backends differ precisely where an adapter would have to unify them (full-message retrieval — absent in Herdr, native `session export` in Omnigent, `logs` in Paseo; status — five-valued in Herdr with `done` meaning literally `needs_attention`, inferred in Omnigent; isolation — native worktree in Herdr, plain `git worktree` elsewhere), so any adapter must discard `session export` and `done` semantics, the only two places the backends are actually strong. And it shows this already happened, with `COMPLETION_CRITICAL` collapsing to `["statusRead","stop"]` and seven methods leaking outside the interface. That is an empirical argument, not an aesthetic one.

Several smaller pieces are excellent and novel. The bloat health indicator — total methodology code ≤500 lines, currently 330, "exceeding it is a signal to audit, not a reason to raise the threshold" — is falsifiable in a way pre-mortems usually are not. The self-deletion metric for its own script ("if `mo-models list` is called fewer than three times in a month, delete it") applies the pre-mortem to the proposal's own additions. The "three violations, recorded in `docs/todo.md`, before any script is written — two is coincidence" rule is a concrete tripwire. Discovering that `agent wait --until idle --timeout 900000` blocks, and therefore replaces the one thing a deterministic watchdog process was needed for (an accurate timer) with the backend's own timer, is a genuinely clever elimination of the last argument for watchdog code. Running the anchor system (`§B/§A/§M`) through `sdd-issues.md`'s own artifact test and concluding its only reader is a checker that cannot verify meaningfulness is disciplined self-application. And §16.1's six enumerated revision-mismatch scenarios with the honest "case 4 is not caught, cost is one extra QC run" is exactly the proportionality argument the task demanded instead of a restated axiom.

Proposal 1 retains real strengths: its §18 per-file audit is more granular than Proposal 2's family-level table, and the "Replace, do not retain" verdict for `model-set`/`project-key`/`safe-fs` — no public API or workflow coupling survives, the few needed operations are rewritten inside the bounded helper — is a precision that prevents coupling from sneaking back through a "reused" module. Its §2 level-3 reopening conditions (six simultaneous criteria) and §24's twelve-question admission test are well-constructed. And making the helper itself conditional, with an explicit statement that vNext stays at level 1 if discovery turns out to be reliable via direct CLI, is intellectually honest about its own architecture claim.

## Alternatives & Creative Ideas (Green Hat)

The highest-value amendment for Proposal 2 is to add the goal store as a route-level channel and let it do three jobs at once: prove goal-mode existence (settling N-008 without a banner regex), verify activation and current status (`active`/`paused`/`blocked`/`usage_limited`), and supply the `tokens_used`/`token_budget` signal its §19 currently marks unavailable — while explicitly noting the layout is a version-specific implementation detail to re-probe, not a stable API. That also lets `mo-lastmsg` grow a sibling read rather than a new mechanism, keeping the ≤500-line indicator intact.

For the STATUS-block weakness, a cheap asymmetric check: have the orchestrator, not the executor, enumerate the spec's requirement headings once at kickoff and diff that list against the executor's final claim. It costs one orchestrator turn, requires no code, and breaks the shared-root-cause problem because the checker never saw the implementation.

For the file-handoff/skill conflict, the clean resolution is to state the override explicitly in `mo-herdr` — "the installed skill says not to request file output in the initial prompt; we deliberately override this for reviewer and executor verdicts, because for a multi-page verdict the panel tail is lossy by construction and a retrospective re-export is regeneration, not retrieval" — so the next reader reconciles rather than reverts.

For the candidate ref, namespacing per branch costs one string interpolation and removes both collision and staleness. For `interrogate`, adding a symbol-class allowance (documented in `pyproject.toml` with a reason, e.g. nested closures under 5 lines and trivial dunders) keeps 100% presence meaningful without manufacturing filler.

One synthesis worth noting: Proposal 1's per-file audit granularity and its "Replace, do not retain" discipline would strengthen Proposal 2's family-level §23, and Proposal 1's twelve-question admission test is slightly sharper than Proposal 2's six pre-mortem rules on the question of whether a helper hides the native interface. Those two pieces are worth grafting.

## Completeness & Process (Blue Hat)

Against the 26 required output sections, Proposal 2 covers all of them and adds an interface/contract section (§24) reducing the entire methodology's persistent footprint to three items — `~/.meta-o/models.json`, `refs/mo/candidate`, git-ignored `.mo/out/*.md` — which is the crispest possible answer to Q2 and Q3. Against the 36 mandatory questions it answers each directly, and where it cannot it says so and assigns the answer to Phase 0 with a named command. Its §30 separates assumptions-to-close from open questions-requiring-data, and the Phase 0 gate ("ни одна строка не удаляется, пока Phase 0 не закрыта") is the correct ordering: it keeps the control case alive until the replacement is proven. The `[V]`/`[A]` marking discipline is the single best process feature in either document and is exactly what the task's verification constraint asks for.

Gaps: the dangling §21 sources reference; Phase 0 estimated at 2–3 hours for installing Paseo, closing a seven-item checklist, live-testing `/goal`, dry-running `apm`, and measuring two lint suites, which is optimistic but harmless; and no convergence rule for the review loop ("число циклов не ограничено и само по себе не эскалируется" is a stated policy, which is better than silence, but a livelock where each revision surfaces new findings still has no exit besides the out-of-scope routing to `docs/todo.md`).

Proposal 1's completeness improved markedly and now satisfies the three-level comparison and near-complete component audit, but it remains a document whose capability claims were reasoned about rather than probed, and the specific consequence is that its answers to Q5 (full reviewer output), Q24 (goal activation), and Q33 (per-backend/per-route signals) are weaker than the evidence available at review time permits — with Q5 actively lossy against a hard criterion.
