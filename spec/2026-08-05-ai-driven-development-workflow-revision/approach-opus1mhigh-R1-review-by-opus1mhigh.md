## Facts & Constraints (White Hat)

Proposal 1's Herdr grounding is real, not asserted. `herdr agent read --source recent-unwrapped` exists exactly as named, and the proposal's claim that raising `--lines` cannot recover alternate-screen content is a faithful restatement of `herdr --skill` line 183 ("Rows that leave the alternate screen do not enter Herdr's host scrollback, so a larger line count cannot recover them"). `herdr agent send-keys` exists, so key-level `/goal` entry is a real mechanism rather than an invention. `herdr agent prompt --wait --until idle|working|blocked|done|unknown` exists, and its help even documents the turn-tracking hazard the proposal's premature-idle detection depends on ("It does not track turns: if the agent is already working, that active turn's completion may match") — a caveat Proposal 1 does not mention but should, since its fallback continuation logic hinges on distinguishing "finished my turn" from "was already working".

The tool selections are sound and correctly prefer mature tooling: Import Linter genuinely covers `layers`/`forbidden`/`independence`/acyclic contracts, so deleting the custom `quality/import-graph.mjs` is well-founded; Interrogate covers docstring presence including private symbols; ESLint's built-in `complexity`/`max-lines`/`max-lines-per-function`/`max-statements` make a custom TS AST checker unnecessary. Separating `tsc --noEmit` from Oxlint `--type-check` on maturity grounds, and refusing to treat Vitest's transpilation as typechecking, both match the task's research snapshot rather than over-claiming beyond it.

The PATH contract is correct and, if anything, under-argued: because the local `claude` wrapper injects a system prompt in addition to permission flags, bypassing it changes *model behavior*, not merely approval posture. That is a stronger argument for the rule than the one given.

One structural constraint the proposal respects well: Git commit OID genuinely does everything `snapshot_digest` did except survive history rewriting, and the task pre-committed to deleting the digest absent a better failure mode. I tried to construct one — two reviewers reading a branch ref while the executor force-pushes — and it fails as a counterexample, because passing an explicit full OID rather than a branch name closes it, which is exactly what `CandidateRef.commitOid` does.

## Risks & Failure Modes (Black Hat)

**The reviewer-retrieval fallback is lossy regeneration disguised as retrieval.** This is my most serious finding. Proposal 1's Herdr path is: read `recent-unwrapped`; if the alternate screen already dropped the content, "попросить reviewer экспортировать предыдущее сообщение verbatim в Markdown-файл и вернуть только path." An LLM asked to reproduce its own prior message verbatim does not retrieve it — it regenerates from context, and if that context was compacted (the very scenario in which long reviews get lost) it will silently paraphrase, drop caveats, and compress evidence. That is the *same class of defect* as the truncated tail the task forbids: "Нельзя молча считать truncated tail полным результатом." The proposal closes the loudly-obvious lossy path and leaves an equally lossy one that merely looks authoritative because it arrives as a file. The verified fix costs no new protocol: read the harness's own on-disk rollout/transcript JSONL, which is authoritative, non-generative, and — importantly — a property of the *route*, so it works identically under Herdr, Omnigent, and Paseo and collapses three backend-specific retrieval designs into one. A second, cheaper hardening the proposal misses: instruct the reviewer to write its verdict to a file as its *first* action and report only the path, making retrieval correct by construction rather than by reconstruction.

**The capability tables collapse a dimension the task explicitly required, and thereby record available data as unavailable.** §4.2 demands analysis per backend *and* per Claude/Codex/OpenCode route. Proposal 1's table has only a backend axis. The consequence is not cosmetic: it reports "Context fill: Unavailable на Herdr layer", "Last-turn timestamp: Inferred/terminal-dependent", "Cache TTL/cold-resume: Unavailable" and concludes "ни один backend не даёт достаточных данных для общего cache tracker." But `thread_goals` exposes `tokens_used`, `token_budget`, `time_used_seconds`, and `updated_at_ms` per thread — a real last-turn timestamp and real consumption data at the route layer. The final recommendation (no custom cache tracker) may well survive, but it is currently reached from a false premise, and the task grades honesty of these tables directly. The correct cell is `available (route-level, Codex) / unavailable (multiplexer-level)`.

**Goal-activation verification depends on the exact channel the proposal declares unreliable.** Proposal 1 verifies `/goal` by having the orchestrator check "visible goal UI/status", and for Paseo by "native timeline/UI". Codex runs in a TUI on the alternate screen — the place the proposal itself proves content is unrecoverable. So the guarantee that the strong-executor model even engaged rests on screen-scraping a TUI. Meanwhile `thread_goals` answers Q24's literal wording — "как проверить, что goal действительно активна, без нового `goal.json`, FSM или proxy CLI" — with a query against state Codex already maintains: `objective` text plus `status`. Because it never found this, §21 downgrades Herdr goal support to "требует disposable capability test. До подтверждения используется weaker fallback", i.e. it defers to the weaker path where a verified answer existed at review time. This is the single largest missed opportunity in the proposal.

**The goal-granularity decision rejects option 1 without evaluating the native mechanism for it.** Q26 asks how to hold a goal without pointless auto-continuation during independent gates. Proposal 1 picks option 3 (goal ends at candidate, then plain follow-up turns). But `status='paused'` and a dedicated `thread_goal_continuation_deferrals` table exist natively — meaning a feature-level goal *can* be suspended across the review wait rather than terminated. Option 1 may be the better answer; either way its rejection is currently unsupported. Relatedly, `usage_limited`/`budget_limited` are first-class goal statuses that map directly onto §4.1's stated real reason for switching models ("закончились лимиты одной подписки"), which the proposal handles only as a manual user decision.

**The one helper that justifies architectural Level 2 is weaker than argued, and its successor rule breaks on the real catalog.** The proposal's central architectural claim is "skills + exactly one narrow helper", justified because dedup/lineage/cache across several SDKs is a genuinely algorithmic task. For the Codex route, though, discovery is *reading one existing JSON file*, and `~/.meta-o/model-catalog.json` duplicates a native cache that already carries `etag` and `fetched_at`. Worse, the actual catalog defeats the successor rule: it contains `gpt-5.6-sol`, `gpt-5.6-sol-wm`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`, `gpt-5.3-codex-spark`. The rule requires matching vendor plus "явно установленный `lineId`" with a strictly newer release — but nothing in the catalog supplies `lineId`. Is `gpt-5.6-terra` a successor to `gpt-5.6-sol`, or a sibling at the same release? Is `-wm` a line or a variant? Either the helper carries a hand-maintained lineage map (an unpriced maintenance cost, and precisely the kind of hidden knowledge layer the task's pre-mortem targets) or it degrades permanently to `AMBIGUOUS_LINEAGE` and the upgrade feature never fires. Since this helper is the *only* surviving code, Level 2 may collapse into Level 1 — which the proposal's own table calls an acceptable baseline, so this is fixable by honest restatement rather than redesign, but it must be stated.

**Paseo capabilities are presented with the same confidence as verified ones.** `paseo` is not installed here. Herdr and Omnigent rows carry versions (0.8, 0.6); the Paseo column carries none — a tell. Yet its cells read "Available" for session status, full transcript, last-turn timestamp, and native compaction signals, and §5 says "Требуется версия с native Codex `/goal` support" without establishing that any released version has it. Under the task's mandated `available | inferred | unavailable` labeling, every Paseo cell should currently read `inferred (docs only; CLI not installed)`. The Omnigent row has a milder version of the same issue: I can confirm `session`, `resume`, and `import` from `--help`, but not the "session export JSONL" primitive on which its reviewer-retrieval and last-turn-timestamp claims depend.

**Two-PASS-on-one-revision has no convergence rule.** "Completion требует двух PASS на одной revision" plus "fixes создают C2, все затронутые проверки повторяются" admits a livelock where each new revision surfaces a fresh finding from the other reviewer. The dispute protocol handles a *contested* finding well (second reviewer as targeted arbiter) but not the unbounded-new-findings case. Given the task's "время человека дороже токенов" framing this should not escalate to the user by default, so it needs an explicit convergence rule (e.g. after round N, remaining non-blocking findings go to `docs/todo.md` and the candidate ships).

**`mo-e2e` exit-code 2 is a re-introduced machine protocol without a named consumer.** The proposal deletes `e2e.json`, the QC manifest, and machine-readable results specifically for lacking a consumer, then invents `AGENT_REQUIRED` + `exit 2`. If the orchestrator is an agent reading full output, the sentinel is redundant; if `mo-qc` aggregates `mo-e2e`, then standard `make` semantics mean every QC run fails in any project whose E2E requires an agent. The proposal never states whether `mo-qc` depends on `mo-e2e`, leaving the one contract the task calls mandatory (Q7) ambiguous.

**Watchdog liveness gap is acknowledged but its cost is not.** "Watchdog сам уснул → не обещать liveness" is honest, but a silently-dead watchdog is worse than none, because the user believes they are covered and stops checking. `herdr notification` exists as a verified native primitive and is never used. At minimum the design needs a cheap user-visible liveness tell, or an explicit instruction that watchdog presence must never be relied upon.

**Audit completeness gaps.** `skills/adopt-project` gets no `keep/replace/delete/defer` verdict (the table covers `adoption-manifest.json` but not the skill). "Project QC helpers: **Mostly delete**" is not a per-component decision for nine concrete scripts — which of `bootstrap`, `format-check`, `run-qc`, `run-tests` survive? And the mandated three-level comparison (user flow, skills/scripts, recovery, review/E2E, non-standard projects, maintenance cost, lost guarantees — for *each* level) is delivered as a 3×4 table with the seven dimensions elaborated only for the chosen level.

## Strengths & Benefits (Yellow Hat)

The core architectural judgment is right, and I could not break it. Deleting the `meta-o` CLI, FSM, run state, `SessionAdapter`, receipts, digests, and registries is correctly argued from the task's own constraints rather than from taste, and the deletion table is unusually disciplined about naming the replacement for each removal. The explicit "потерянные гарантии, принятые осознанно" list is exactly what the task's "удаление state/CLI не маскирует неразрешённый hard requirement" criterion asks for, and it is admirably blunt (no exactly-once, no takeover, no fencing, no guaranteed watchdog liveness).

The candidate-commit rule is the standout piece of design: five lines of prose replace snapshot digests, attestations, and gate receipts, and it survives the adversarial cases I threw at it as long as a full OID is passed. `CandidateRef` and `ReviewOutcome` being explicitly labeled as conceptual boundaries rather than persisted schemas or wire formats is the correct way to satisfy the task's simultaneous demands for implementation-readiness and no-mandatory-JSON.

The no-executor-skill decision is implemented rather than merely asserted: the requirements from `execute-feature` are visibly redistributed into the goal template, project instructions, QC commands, and review lenses, and the goal template itself avoids inlining the spec while still encoding full-scope, reuse-adherence, knowledge-sync, and DoD. Naming the persistent-session path a *weaker* fallback instead of an equivalent is precisely what the task's "Что нельзя считать успехом" list demanded.

Dynamic subagent counts (0 for small, up to 6 for large) correctly refuse the ritual 6–9. The dispute ladder (reviewer rechecks → second reviewer arbitrates the specific finding → orchestrator decides reversible technical calls → user only for product meaning or irreversibility) resolves Q20 without a separate adjudicator and respects the human-time principle. The durable-rationale rule is well-bounded by three conditions, avoiding both lost context and comment noise. The pre-mortem's ten questions are a genuine structural defense rather than a slogan, and copying a short shared workflow reference into three packages instead of creating a runtime dependency is the right call for APM/skills delivery.

## Alternatives & Creative Ideas (Green Hat)

The most valuable restructuring is to **move retrieval and goal verification from the multiplexer layer to the route layer.** Rather than three backend-specific reviewer-output designs plus three goal-confirmation designs, define one route-level contract — "read the harness's own transcript file; confirm goal state from the harness's own goal store" — and let each backend skill contribute only *session-to-thread identity resolution*. This shrinks the spec, removes the regeneration hazard, and makes Paseo support largely free rather than blocked on unverified capability. It also gives the honest answer to Q33: context/turn data is available at the route layer for Codex, unavailable at the multiplexer layer, and unknown-until-probed elsewhere.

For the model helper, consider inverting the justification: instead of a helper that unifies three SDKs, make the skill read native caches directly (`~/.codex/models_cache.json` for Codex, equivalent for others), and keep code only for the one thing prose cannot do reliably — successor detection. Then confront the lineage problem honestly: derive candidate successors from slug structure but require user confirmation on any suffix change (`sol`→`terra`), suggesting silently only on pure version increments within an identical suffix. That is a rule the real catalog actually supports.

For the convergence problem, a cheap mechanism: each reviewer's second-round output must classify findings as blocking-for-this-candidate or follow-up, with follow-ups auto-routed to `docs/todo.md`. This uses the artifact the proposal already has and needs no new state.

For the watchdog, `herdr notification` plus a "watchdog writes a heartbeat line to the orchestrator pane every N minutes" convention gives user-visible liveness with zero new code, converting an acknowledged hole into a bounded one.
