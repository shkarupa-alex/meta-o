## Framing: what I could verify this round, and why it decides the comparison

Both proposals were revised again, so the fair test is whether each fixed what was previously shown to be factually wrong, and whether the new claims hold against primary sources. I re-probed the installed toolchain: `herdr 0.8.0`, `omnigent 0.6.0`, `codex-cli 0.146.0`, **`claude 2.1.222`**, `agent-browser 0.33.2`, `apm 0.27.0`; `paseo` still absent. The decisive new claim in this round is Proposal 2's Fact 3 — that `/goal` exists natively in *both* Codex and Claude Code — because it converts "emulate a persisted goal" from an open design problem into "use the vendor mechanism." I tested it directly against the installed Claude Code binary rather than accepting it.

It holds, and with more precision than Proposal 2 itself states. Strings extracted from `/opt/homebrew/Caskroom/claude-code@latest/2.1.222/claude` include `/goal`, `/goal active`, `/goal clear to stop early`, `/goal <condition> to set another`, `/goal <condition> to set one`, plus the Stop-hook machinery it is built on — `getStopHookMessage`, `executeStopHooks`, `stopHookActive`, and `stopHookBlockingCount` initialized alongside `turnCount` and `maxTurns` in the query loop. So Proposal 2's characterization (condition-based, session-scoped, implemented as a prompt-based Stop hook, turn-bounded) is correct, and the installed version 2.1.222 is consistent with its "since v2.1.139" claim. I also independently confirmed last round that `~/.codex/goals_1.sqlite` ships a migrated `thread_goals` table with `objective`, the six statuses, `token_budget`, `tokens_used`, `time_used_seconds`, plus `thread_goal_continuation_deferrals`. Proposal 2 now uses both correctly. Proposal 1 does not use either, and its capability matrix asserts the opposite for Claude.

I also found two hard preconditions **neither** proposal states, both verbatim in the binary: `"/goal is only available in trusted workspaces. Restart, accept the trust dialog, and try again."` and `"/goal can't run while hooks are restricted (disableAllHooks or allowManagedHooksOnly is set in settings or by policy)."` Proposal 2 mentions only `disableAllHooks` and never trust.

## Facts & Constraints (White Hat)

The trusted-workspace gate is not a footnote — it collides with a design choice Proposal 2 makes explicitly. Its §5.3 S2 recommends launching the *executor* as `paseo run -d --new-workspace worktree --worktree-mode branch-off --base main`, which places the executor in a brand-new directory path. Claude Code treats a new path as untrusted until a dialog is accepted, so on the Claude route `/goal` would be silently unavailable there, and the trust dialog is itself an interactive prompt that `--dangerously-skip-permissions` is not documented to bypass. The same applies wherever `herdr worktree create` or `git worktree add --detach` produces a fresh path for a role that needs `/goal`. Proposal 2's §16.3 confines worktrees to gates rather than the executor, which mostly protects it — but §5.3 contradicts §16.3 on exactly this point, and the contradiction is invisible without the trust fact.

The second constraint is epistemic and cuts against Proposal 2's strongest habit. Its `[V]` marker now covers two very different things: "I ran this on this machine" and "I read this in upstream source." For Herdr, Omnigent, Codex, Claude, `agent-browser` and `apm` — all installed — that distinction does not matter, and I verified a dozen such claims across rounds with no errors. For **Paseo it matters entirely**, because Paseo is not installed. Claims like `CODEX_GOALS_MIN_VERSION = [0,128,0]`, `DEFAULT_MAX_ITEMS = 0`, `WAIT_ACTIVITY_PREVIEW_COUNT = 5`, `DEFAULT_FOLLOW_TAIL = 10` are precisely the constants that drift between HEAD and whatever release the user installs, and the task explicitly forbids accepting backend capabilities without verification. Notably this is a *regression* from Proposal 2's previous revision, which carried `[A] Paseo CLI ... skill помечен unvalidated` in its assumptions and a "Paseo окажется несовместимым — средняя `[A]`" row in its risk table; both are now gone, replaced by unqualified `[V]`. Phase 0 still installs Paseo and runs the S1–S7 checklist, so the plan is operationally sound — but the capability tables no longer tell an implementer which Paseo facts are unproven on their machine.

On this one axis Proposal 1 is now better, and I want to credit it precisely. Its §7 introduces a four-value evidence policy (`available` = verified on the locally installed version, `inferred` = claimed by docs/source but not locally verified, `unavailable`, `fallback`), names the evidence basis per backend, states "ни одна положительная Paseo capability ниже не считается локально подтверждённой," marks every Paseo cell `inferred`, and gates the Paseo skill behind a named local validation matrix in migration step 5. That is exactly the discipline the task asked for, and it is the right vocabulary for Proposal 2 to adopt wholesale.

## Risks & Failure Modes (Black Hat)

**Proposal 1 now contains a verified false negative in its central matrix.** §9.1 records, for the Claude Code route, "Persisted automatic goal: `unavailable` — equivalent не подтверждён," and §6 lists Claude Code among the surfaces needing the weaker fallback. Against Claude Code 2.1.222 that is wrong: `/goal` exists, is condition-based, restores on `--resume`/`--continue`, and is implemented over Stop hooks. This is worse than the omission I flagged last round, because it is not silence — it is an assertion that drives the design to a weaker mechanism on the route the user's own wrapper configures for both the primary reviewer and, frequently, the executor. The proposal's own §7 policy would have caught this had `available` been tested rather than assumed absent; the framework is right and the result contradicts it.

**Proposal 1's reviewer-retrieval defect is unfixed for a third round.** §11 Herdr step 3 remains "попросить reviewer записать предыдущее сообщение verbatim в Markdown-файл" — a retrospective request to reproduce output that, if the panel lost it, is exactly the case where the model's own context may have been compacted. That is regeneration presented as retrieval, against a hard criterion ("Полные reviewer messages не теряются из-за terminal truncation"). Its §8 row even labels this `fallback` honestly, which is better bookkeeping — but the underlying mechanism is still lossy, and the `agent_session` pointer present in the Herdr API schema, plus the on-disk rollout/project JSONL, still go unmentioned. Relatedly, §6's preference for "native key-level input с отдельным Enter" for `/goal` remains contradicted by the installed skill's documented behavior that `agent prompt` "atomically submits text and encoded Enter while honoring the pane's live bracketed-paste mode" — the rejected mechanism is the safe one.

**Proposal 2's helper packaging fix introduces a new coupling defect.** Moving `mo-models.mjs` and `mo-lastmsg.mjs` into `mo-orchestrate/scripts/` is correct reasoning about how `apm` and `npx skills` copy directories — I confirmed `apm install` advertises SKILL.md support and directory-level installation. But `mo-review` standalone is a headline requirement ("`mo-review` можно запустить напрямую после быстрого fix"), Proposal 2 explicitly advertises `npx skills add --skill mo-review`, and on Herdr a standalone review needs full reviewer output, whose non-prompt-dependent path is `mo-lastmsg` — now installed only with `mo-orchestrate`. So the single most-advertised standalone use case silently loses its only non-obedience-dependent retrieval path.

**Making the STATUS block the literal goal condition creates a cheapest-path hazard.** For Claude the condition is "the transcript contains a STATUS block with SCOPE-COMPLETE: yes, TESTS: pass, QC: pass and a CLEAN COMMIT sha." The evaluator is a small model that cannot read files or run commands — Proposal 2 identifies this constraint sharply and designs around it, which is the best available answer. But it follows that the cheapest way to satisfy the goal is to *print the block*, and the evaluator cannot distinguish a truthful block from a fabricated one. The falsifiable fields are re-checked downstream (§3.3 step 5 re-runs `make mo-qc` on the candidate; `git status --porcelain` and the commit sha are checkable), so the exposure is confined to `SCOPE-COMPLETE`, which only reviewers can judge. That is acceptable — but the spec must say explicitly that the STATUS block is a handoff/liveness signal and never gate evidence, otherwise an implementer will treat "QC: pass" in the block as satisfying step 5.

**`refs/mo/candidate` remains a single global unnamespaced ref** — unfixed from last round. Two features in flight in one repository (plausible given the self-hosting scenario the task contemplates) collide silently, and a ref left from a finished feature is surfaced by §4.2's no-argument flow as unfinished work. The risk table still covers only accidental deletion.

**`interrogate fail-under=100` with `ignore-private`, `ignore-magic`, `ignore-nested-functions`, `ignore-nested-classes` and `ignore-semiprivate` all false** requires a docstring on every closure and dunder, with only a file-level exclusion list as escape. The coverage/depth split is the right decomposition and genuinely resolves the GRACE-versus-task tension, but the task also warns against "бессмысленные повторяющиеся docstrings," and a symbol-class allowance is needed alongside the file list.

**Proposal 1 still has three carried-forward process gaps**: `adopt-project` receives no audit verdict for a third round, and with no `mo-setup` equivalent the project-onboarding function (installing linter configs, creating the `docs/` layout, inserting the `AGENTS.md` fragment) has no assigned owner beyond "executor добавляет aliases"; the `mo-e2e` exit-2 sentinel still has no named consumer and it is still unstated whether `mo-qc` aggregates `mo-e2e` (if it does, every QC run fails in agent-E2E projects); and the review loop still has no convergence rule.

## Strengths & Benefits (Yellow Hat)

Proposal 2's Fact 3 is the most valuable single contribution across all rounds, and it is correct. It dissolves an entire category of proposed machinery: once persisted goals with continuation loops exist in the vendors' own SQLite, the strongest remaining argument for architecture level 3 evaporates, and the proposal says so explicitly. The derived design details are sharp rather than generic — recognizing that Codex's model performs its own completion audit while Claude's evaluator is blind to the filesystem, and therefore that the *same* STATUS block serves as a completion condition on one route and a premature-idle detector on the other, is a genuine insight I would not have derived unprompted. The mandatory `or stop after 25 turns` for Claude follows correctly from evaluator blindness. Reading the Codex goal statuses operationally (`blocked` only after three identical blockers; `usage_limited`/`budget_limited` mapping onto the user's stated subscription-exhaustion scenario; `paused` set only by humans) turns a status enum into an orchestrator playbook. And using `sqlite3 ~/.codex/goals_1.sqlite` in the recovery script (§17) means a restarted orchestrator learns whether the executor is still under an active goal, in which state, and at what token cost, without asking anyone — the best answer to Q2 in either document.

The Paseo asymmetry finding is exactly the kind of trap a specification exists to name: `logs` without `--tail` is the only unfragmented read, while `wait` (5-item preview), `send` (status line only) and foreground `run` (metadata) all look like they return the agent's answer and do not. Elevating that to the first line of the skill section is correct instructional design.

Other durable strengths: §0's demonstration that the *current* implementation's advertised full-message guarantee is broken (not merely heavy) reframes the mandate from taste to correctness; §5.4's adapter argument is empirical and now stronger with a third differentiator (`/goal` resolved provider-side only in Paseo); the `≤500 lines of methodology code` health indicator is falsifiable; the `mo-lastmsg` deletion criterion (>99% handoff reliability → delete the script) and the `mo-models` usage metric (<3 calls/month → delete) apply the pre-mortem to the proposal's own additions, which almost no proposal does; the six-canonical-frontmatter-fields rule buys portability at zero cost; and the decision *not* to install a statusLine wrapper for Claude context telemetry — documenting the technique but refusing to modify the user's personal config by default — is exactly the right instinct about whose environment this is.

Proposal 1 deserves real credit for §7's evidence-status policy and §9's 3×3 route matrix, which fix the structural gap I raised and produce a vocabulary Proposal 2 lacks. Its §22 per-file audit remains more granular than Proposal 2's family-level table, and the "Replace, do not retain" verdicts for `model-set`/`project-key`/`safe-fs` correctly prevent workflow coupling from re-entering through a "reused" module. Making the model helper fully conditional on a capability spike, with an explicit statement that vNext stays at level 1 if direct CLI suffices, is honest about its own architecture claim.

## Alternatives & Creative Ideas (Green Hat)

The cleanest fix for the trust interaction is a preflight triple rather than a single check: `command -v` for PATH resolution (already present), a trust probe for the working directory any `/goal`-bearing role will run in, and a hook-policy check for `disableAllHooks`/`allowManagedHooksOnly`. All three are cheap, all three fail *silently* today, and all three degrade `/goal` to the weaker fallback without announcing it — which is precisely the failure the task's "не выдавать fallback за эквивалент" clause targets. Corollary: never launch a `/goal`-bearing executor into a freshly created worktree path unless trust is pre-established, which resolves the §5.3-versus-§16.3 contradiction in favor of §16.3.

For the packaging coupling, the smallest fix is to place `mo-lastmsg.mjs` inside `mo-review/scripts/` (its actual consumer for the standalone case) and `mo-models.mjs` inside `mo-orchestrate/scripts/`, accepting one duplicated copy if `mo-orchestrate` also needs the former. Duplicating 80 lines of read-only code is strictly cheaper than a cross-skill runtime dependency, and it matches the document's own reasoning about copying a shared workflow reference into each package.

For evidence discipline, Proposal 2 should adopt Proposal 1's four-value vocabulary and split its `[V]` into `[V-local]` (ran here) and `[V-src]` (read upstream), restoring the Paseo risk row and the unvalidated-until-Phase-0 assumption. This costs a find-and-replace and removes the only place where Proposal 2's otherwise excellent epistemics slip.

For `refs/mo/candidate`, namespace per branch and delete on completion. For `interrogate`, add a documented symbol-class allowance. For the STATUS block, add one sentence: it is a handoff signal, never gate evidence; the orchestrator re-derives QC, commit cleanliness and sha independently.

## Completeness & Process (Blue Hat)

Proposal 2 covers all 26 required output sections and answers all 36 mandatory questions with named commands or explicit deferral, adds an interfaces/contracts section reducing the entire persistent footprint to three items (`~/.meta-o/models.json`, `refs/mo/candidate`, git-ignored `.mo/out/*.md`), and separates assumptions-to-close from open-questions-requiring-data. The dangling "§21 sources" cross-reference I flagged last round is gone. Phase 0 gating deletion behind verification remains the correct ordering, and it now includes both `apm install --dry-run` and `npx skills add ./`, live `/goal` confirmation via the SQLite row for Codex and for Claude, and the Omnigent slash-command question. The 2–3 hour estimate for installing Paseo and closing a seven-item checklist plus two lint measurements remains optimistic, but Phase 0 gates deletion rather than delivery, so slippage is harmless.

Proposal 1 improved its completeness materially (evidence policy, route matrix, per-file `.mjs` audit, human-attention policy, Paseo validation gate in the migration plan) but has now accumulated four unrepaired items across three rounds — lossy reviewer retrieval, the `send-keys`-versus-`agent prompt` contradiction, the missing `adopt-project`/project-onboarding owner, and the `mo-qc`/`mo-e2e` ambiguity — plus a newly verifiable false negative on Claude `/goal`. Its structure is sound and its deletion discipline is good; its problem is that its capability claims continue to be reasoned about rather than probed, which is the one thing the task made a hard constraint.
