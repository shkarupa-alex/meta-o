## 1. Завершение объявлено по несовместимому набору проверок

**Что произошло.** После исправлений по review появился новый candidate SHA. Оркестратор повторил QC и один review, но посчитал второй старый PASS и E2E всё ещё действительными. Feature была объявлена готовой, хотя один из изменённых участков не проверялся вторым reviewer или tester на финальной revision.

**Почему.** Связь между gate и SHA хранится только в текстовом контексте оркестратора. Правило «повторять затронутые gates» требует субъективно определить влияние исправления. После compaction или restart легко потерять, какие именно проверки относились к какому SHA. Удаление receipts разумно, но дизайн не определяет достаточно строгий финальный алгоритм проверки согласованности.

**Что изменить.** Ввести простое fail-closed правило без workflow state: любое изменение candidate SHA автоматически инвалидирует оба review и применимый E2E; QC также запускается заново. Непосредственно перед completion оркестратор должен получить свежие сообщения каждого gate с явно указанным полным финальным SHA. Оптимизацию с повтором только «затронутых» gates оставить на будущее, когда появится доказанный безопасный способ определять влияние.

## 2. Полный reviewer verdict регулярно теряется, и review loop становится непредсказуемым

**Что произошло.** Native backend export оказался усечённым или изменился после обновления. Reviewer записал результат во временный файл из `mktemp -d`, но файл исчез после reboot, оказался недоступен другой session либо reviewer не выполнил handoff. Оркестратор не мог получить authoritative verdict, поэтому повторял дорогие reviews или, под давлением длительного run, начинал принимать видимый terminal tail.

**Почему.** Baseline объявляет полное сообщение критическим требованием, но основной fallback опирается на эфемерный файл вне repository. Контракт не устанавливает единый проверяемый способ подтвердить запись до завершения reviewer session, срок жизни файла и доступность между backend sessions. При этом надёжный helper отложен до уже измеренных failures — то есть первая реализация сознательно выходит без устойчивого transport.

**Что изменить.** Сделать проверку full-output обязательным Phase 0 admission criterion для каждого поддерживаемого backend: длинный verdict, перезапуск/resume и чтение до EOF. Backend без доказанного native retrieval не объявлять полностью поддержанным. Для него сразу использовать минимальный backend-specific helper либо durable, user-readable handoff path с явным acknowledgement записи; terminal tail никогда не принимать как PASS.

## 3. Native goal перестал активироваться, а orchestrator принял преждевременный idle за candidate

**Что произошло.** После обновления Herdr, Omnigent, Paseo или underlying harness slash command стал передаваться как обычный текст, изменились trust/hooks semantics либо goal не пережил resume. Executor сделал удобную часть большой spec и остановился. Session выглядела idle/done, и orchestrator перешёл к review, хотя persisted goal фактически никогда не была активна.

**Почему.** Дизайн делает native `/goal` центральной гарантией полноты, но её подтверждение остаётся version- и surface-specific reasoning. Для Codex диагностический SQLite probe опирается на private schema, для Claude требуется корректная hook policy, а для Omnigent/Paseo transport ещё должен пройти live spike. Нет стабильного общего API, позволяющего отличить активную goal от строки, отправленной в chat.

**Что изменить.** Зафиксировать per-version executable acceptance fixture для каждого реально поддерживаемого сочетания backend и harness. Fixture должна доказывать активацию, автоматическое продолжение после намеренно неполного turn и сохранение при resume. При неизвестной версии или провале проверки автоматически переходить к честному persistent-session fallback. Независимо от goal reviewers должны сопоставлять реализованный scope со всей spec, а orchestrator — не считать native `done` доказательством полноты.

## 4. Обязательный reuse research превратился в новую тяжёлую SDD-стадию

**Что произошло.** Для задач, данных текстом или URL, researcher начал создавать tracked spec и отдельный commit даже там, где изменение было небольшим. Найденное решение позже оказалось несовместимо с технической реальностью, но executor не мог исправить read-only reuse decision. Работа останавливалась до нового research cycle либо реализация формально следовала устаревшему выбору.

**Почему.** Синтез усилил исходное требование: любая task материализуется в tracked spec, reuse получает первый отдельный commit, а затем вся spec становится read-only «без исключений». Это смешивает две разные гарантии: сохранение результата исследования и неизменность всех технических выводов. Research проводится до реализации, когда некоторые compatibility constraints ещё невозможно подтвердить.

**Что изменить.** Оставить product requirements read-only, но разрешить отдельную контролируемую поправку только раздела `Reuse research`, если implementation evidence опровергло решение. Такая поправка должна быть отдельным spec-only commit с причиной и видимым diff до продолжения implementation. Для внешней или текстовой task разрешить простой tracked research note, привязанный к task, вместо обязательного превращения всей задачи в новую полноценную spec.

## 5. `mo-models.mjs` стал скрытой конфигурационной подсистемой и разошёлся между skills

**Что произошло.** Три self-contained orchestrator skills поставляли копии `mo-models.mjs`. После обновлений одна копия иначе дедуплицировала model IDs или распознавала successors. Один backend предлагал upgrade, другой продолжал использовать старый набор, а частичные изменения `models.json` делали поведение зависимым от того, какой skill был запущен последним.

**Почему.** Дизайн одновременно требует независимой установки skills, допускает дублирование helper и возлагает на него несколько нестабильных функций: route-specific catalogs, session history, lineage, project hashing и persistence. Официальные источники неоднородны, exact lineage местами deferred, а единой реализации или schema ownership не определено. Узкий helper рискует постепенно стать общим model/config router.

**Что изменить.** Определить одного владельца helper и versioned schema `models.json`; orchestrator skills либо зависят от одного устанавливаемого model-preferences skill/package, если оба package manager это поддерживают, либо используют только локальный сохранённый default без копирования discovery-кода. Неавторитетные history hints не должны генерировать upgrade prompts. При несовместимой schema helper обязан fail closed, сохранить файл и предложить обычный текущий model set, а не автоматически мигрировать или угадывать route.
