## Рамки этого разбора

Прежде чем называть сценарии, важно зафиксировать, какие свойства предложенного дизайна делают его уязвимым — иначе pre-mortem превратится в перечень общих рисков. Дизайн сознательно убирает почти весь исполняемый слой: гарантии, которые раньше держались кодом (receipts, digest, FSM, adapter, structured findings), теперь держатся текстом skill и рассуждением агента. Это даёт гибкость, но переносит все точки отказа в три класса, где ошибка не наблюдаема механически: (1) агент честно сообщает о том, что он сделал, и ему верят; (2) capability чужого backend закодирована как проза и проверена один раз; (3) связь «какой gate проверил какой SHA» существует только в prose внутри чужих sessions. Дополнительно: методология размножена в три текстовых копии без общего исполняемого носителя, а единственный разрешённый helper получил качественный, а не контрактный admission test. Все сценарии ниже — следствия именно этих четырёх свойств, а не абстрактной «сложности».

Отдельно отмечу асимметрию: почти все удалённые гарантии действительно были не нужны, но два из них (запись «gate X прошёл на SHA Y» и fail-closed проверка активности goal) были load-bearing именно в тех сценариях, которые пользователь объявил обязательно поддерживаемыми — ручной restart и долгий ночной run. Сценарии 3 и 4 про это.

## Сценарий 1. Reviewer сам сообщает, что его verdict полный — и gate проходит по усечённому тексту

**Что произошло.** Через несколько месяцев обнаруживается, что часть review-gates проходила по неполным verdicts. Reviewer получал в initial task абсолютный path в `mktemp -d` и просьбу записать туда полный verdict verbatim. Файл существовал, был непустым, читался до EOF — и orchestrator принимал его как authoritative full output. Фактически в части случаев reviewer записал в файл сокращённую версию: три главных finding из семи, без evidence и suggested fixes, потому что продолжил рассуждать в session уже после записи файла, или потому что «сжал» вывод как обычно сжимает финальное сообщение. Executor получил неполный набор замечаний, закрыл их, оба review дали PASS, дефект дошёл до E2E или до пользователя.

**Почему.** Дизайн заменил один канал с известным дефектом (terminal tail — усечение видно) на канал, где неполнота ненаблюдаема в принципе. Проверка «файл существует и прочитан до EOF» проверяет доступность, а не полноту. При этом дизайн явно запретил обязательный structured transport и parsing layer, то есть сознательно отказался от любого механического признака завершённости — но не заменил его ничем. Fail-closed правило («не извлекли полный verdict → gate unknown») срабатывает только на missing/empty, то есть на самом маловероятном отказе. Retrospective «повтори verbatim» справедливо запрещён как regeneration, но именно prospective handoff остался без critерия целостности.

**Что можно было сделать.** Не JSON schema, а один механический признак завершённости, не требующий парсинга смысла: обязательная терминальная строка-sentinel как последняя строка файла, и жёсткое правило «нет sentinel в конце → gate unknown, review повторяется». Плюс сделать файл единственным каналом verdict (в session reviewer оставляет только «wrote verdict to `<path>`»), чтобы не было двух версий одного ответа, из которых orchestrator читает более короткую. И третье: сделать backend-native full export обязательным условием запуска review-стадии на том backend, где его полнота была доказана в Phase 0 — а file handoff оставить fallback'ом, а не рабочим путём по умолчанию для двух из трёх backends.

## Сценарий 2. «Нет executor skill» соблюдено формально: ritual переехал в goal template и `AGENTS.md`

**Что произошло.** Через полгода goal template в каждом из трёх orchestrator skills разросся до размера прежнего `execute-feature`: в него по одному добавили пункты «прочитай spec целиком», «не MVP», «не переносить сложное на потом», «обнови durable knowledge», «не push без запроса», «tests должны ограничивать новое поведение», «reuse decision обязателен», потом ещё требования, появившиеся после каждого пропущенного дефекта. Параллельно в adopting-проектах, где `AGENTS.md` не поддерживался, эти требования не существовали нигде, кроме goal — и executor систематически сдавал удобную часть scope, а reviewers ловили это через несколько итераций, дорого. В проектах, где `AGENTS.md` всё же поддерживался, он превратился в длинную methodology-инструкцию, которая теперь применяется ко всем задачам репозитория, а не только к meta-o run.

**Почему.** Дизайн корректно снял с executor зависимость от methodology skill, но требования не исчезли — таблица «outcome → где задаётся → где проверяется» распределила их по трём носителям (spec, project instructions, goal), ни один из которых не имеет владельца, размерного бюджета и review-lens на себя самого. Как только review находит систематический пробел, единственный дешёвый ход — дописать пункт в goal template. Это ровно тот failure, который в задании назван недопустимым успехом («скрыто сохранить тот же ritual в executor prompt»), и дизайн не содержит механизма, который бы это заметил: reflection пишет follow-up в `docs/todo.md`, а самый простой follow-up — «усилить goal».

**Что можно было сделать.** Во-первых, объявить ownership явно: outcome-требования живут в одном коротком tracked project-side артефакте (architecture/outcome contract, устанавливаемый и обновляемый `mo-setup`), а goal ссылается на него по path и остаётся коротким — с зафиксированным бюджетом (например, goal не длиннее одного экрана, и это проверяемое правило skill). Во-вторых, добавить review-lens на сам контракт: reviewer раз в N feature обязан спросить «не выросли ли инструкции быстрее полезной системы», иначе антибloat-принцип применяется только к коду, но не к тексту. В-третьих, в Phase 0 измерить главное допущение — ловят ли независимые reviewers scope-partial реализацию *без* executor-side инструкций; если не ловят, честный вывод — не раздувать goal, а вернуть минимальный machine-checkable scope-контракт в spec.

## Сценарий 3. Долгий gate + ручной restart = принятый stale PASS (false completion)

**Что произошло.** Feature с длинным agentic benchmark: tester работает часы. Review первого reviewer уже дал findings, executor их починил, появился новый candidate. Ночью машина перезагрузилась (сценарий, объявленный поддерживаемым). Пользователь запустил orchestrator заново с тем же prompt. Новый orchestrator восстановил реальность: branch, log, spec, живые sessions. В session tester'а он нашёл отчёт с `CANDIDATE: <SHA A>` и PASS, в session reviewer — PASS на `SHA A`, а head ветки — `SHA C`. Orchestrator сравнил diff A→C, счёл его «review fixes, не влияющие на benchmark», и завершил feature. Позже выяснилось, что именно один из fix'ов ломал поведение, покрываемое benchmark. Формально все правила соблюдены: SHA назван в каждом gate, дерево было чистым.

**Почему.** Дизайн убрал и gate receipts, и `refs/mo/candidate`, оставив единственным носителем связи {gate, SHA, verdict} прозу внутри per-actor sessions. Пока orchestrator жив, он держит эту связь в своём контексте — и это работает. Но ручной restart объявлен обычным сценарием, а после restart join между актёрами приходится восстанавливать из текста и достраивать суждением «какие gates затронуты». Правило «affected gates repeat» не операционализировано: «affected» — это оценка diff'а, которую делает тот же агент, который заинтересован завершить работу. Дополнительно дизайн разрешает перекрытие: goal живёт до candidate, fix-turns идут обычными follow-ups, и ничто не запрещает executor'у двигать head, пока идёт многочасовой gate.

**Что можно было сделать.** Два дешёвых, не-state решения, любое из которых закрывает сценарий. (а) Записывать результат gate туда, где он переживает смерть orchestrator и остаётся человекочитаемым и Git-native: trailers в commit message кандидата или одна строка в spec/`docs` («gate, SHA, verdict, дата»). Это не state machine и не receipt store — это Git-реальность, ровно тот носитель, который дизайн уже считает authoritative. (б) Запретить перекрытие вместо пост-фактум инвалидации: пока идёт долгий independent gate, candidate заморожен — executor не делает turn'ов, меняющих head; fix-batch начинается после возврата всех gates. Плюс правило по умолчанию: после restart любой gate, чья привязка к текущему SHA не подтверждена явно, считается `unknown` и повторяется — «дешевле, чем ложное завершение», без права orchestrator'у самому решать, что diff безобиден.

## Сценарий 4. Native `/goal` тихо не активировался — и premature idle принят за candidate

**Что произошло.** После обновления одного из providers/backends активация goal перестала работать: slash command ушёл как обычный текст из-за изменившейся framing/paste-семантики, либо Claude-вариант goal не поднялся, потому что в проекте оказался `disableAllHooks` / workspace не был trusted / политика hooks сменилась на managed-only. Executor получил spec как обычный prompt, реализовал удобную часть, вернулся в idle. Orchestrator увидел `idle`, прочитал результат, счёл его candidate, отправил на review. Reviewers нашли «частичную реализацию», executor дополнил её ещё частично — цикл повторился несколько раз. Пользователь наблюдал ровно тот failure, ради предотвращения которого goal и вводился, но дороже: с двумя review-итерациями на каждый недоделанный кусок.

**Почему.** Capability трёх backends и трёх providers закодирована как проза в skills и проверена один раз, в Phase 0. Дизайн честно перечисляет предусловия Claude-goal (PATH wrapper, trusted cwd, hooks не запрещены) и требует live-проверки перед implementation — но не требует runtime-проверки *в каждом run* и не описывает fail-closed поведение при неудачной активации. Так как исполняемого слоя нет принципиально, нет и места, где отказ активации мог бы сорвать запуск. Одновременно `idle` в user-facing классификации значит «нет действия», а не «работа завершена», и premature idle отличается от завершения только суждением orchestrator'а о полноте scope — то есть тем же суждением, которое goal должен был снять.

**Что можно было сделать.** Сделать активацию goal доказываемой в каждом run, а не в Phase 0: preflight проверяет три предусловия и явно печатает результат; после отправки goal orchestrator получает подтверждение активности через документированный native интерфейс, а не по факту отсутствия ошибки; при неподтверждённой активации skill не «продолжает как получится», а осознанно переключается на named fallback (persistent session + completion-oriented prompt + orchestrator-driven continuation) и говорит об этом пользователю одной строкой. Плюс версионировать capability-таблицу рядом со skill: если установленная версия backend/provider не совпадает с проверенной, goal считается `unavailable` до новой проверки — деградация становится громкой, а не молчаливой. И отдельно: правило «idle без явного executor-owned DoD statement ≠ candidate», чтобы premature idle нельзя было принять по умолчанию.

## Сценарий 5. Три текстовые копии методологии разошлись; backends второго эшелона работают по устаревшему процессу

**Что произошло.** Herdr-вариант активно использовался и улучшался: правила про полноту reviewer output, про заморозку candidate, про reuse-стадию уточнялись по мере набитых шишек. Omnigent- и Paseo-варианты обновлялись реже. Через полгода пользователь запустил Paseo-orchestrator и получил заметно более слабый процесс: старая формулировка review policy, отсутствие правил, добавленных после инцидентов, другая трактовка candidate SHA. Дефект, уже исправленный в одном skill, воспроизвёлся в другом. Параллельно шло второе расхождение: в bundle три копии `mo-models.mjs` (по одной на orchestrator skill, ради self-contained install), и они разъехались по поведению после первого же изменения.

**Почему.** Дизайн — правильно — отказался от общего исполняемого router/adapter, но общую часть методологии оставил в «небольшом textual reference, который может дублироваться», а distribution-раздел прямо институционализировал дублирование: «маленькое безопасное дублирование дешевле скрытой cross-skill dependency». Для helper'а это, возможно, верно; для самой методологии — нет: она и есть продукт, и она обязана быть одинаковой во всех трёх входных точках, потому что задание требует «одну методологию, разные mechanics». Ничто в дизайне не отвечает на вопрос, кто и когда синхронизирует три копии, и как обнаружить расхождение. Отсутствие executable adapter обосновано; отсутствие *single source of truth для текста* не обосновано — это разные вещи, и они были склеены в одно решение.

**Что можно было сделать.** Развести два вопроса: shared executable adapter — нет; shared canonical methodology text — да, один файл, из которого backend-specific skills собираются или на который ссылаются документированным для целевых skill managers способом; при невозможности ссылки — генерация копий из одного источника на этапе сборки `dist`, с проверкой идентичности, а не ручное дублирование. Плюс дешёвый детектор расхождения: одна строка версии методологии в каждом orchestrator skill, и правило preflight «если версии не совпадают между установленными skills — предупредить». То же — для helper'а: одна копия как источник, сборка распределяет.

## Что из удалённых гарантий оказалось нужным

Из перечисленного в дизайне списка «сознательно удалённых гарантий» четыре сценария выше указывают на две, которые стоит вернуть в минимальной, не-runtime форме: durable связь {gate, SHA, verdict}, переживающая смерть orchestrator (сценарий 3), и fail-closed проверка того, что заявленная native capability действительно активна в этом run (сценарий 4). Обе можно реализовать без state machine, receipts store и adapter — Git trailers/строка в docs и явный preflight-assert соответственно. Остальные два сценария (1 и 2) — не про удалённые гарантии, а про то, что дизайн заменил проверяемые артефакты самоотчётом агента (полнота verdict) и распределённым текстом без владельца (executor obligations); лечится не возвратом кода, а одним механическим признаком завершённости и явным ownership с бюджетом размера.
