# Задача консилиума: упростить AI-driven development workflow и вернуть skills-first архитектуру

## Статус задания

Approach council и pre-mortem уже запущены по явной команде пользователя.
Текущий файл остаётся входным заданием для final-spec council. Раздел
«Уточнения после approach/pre-mortem» в конце является superseding addendum:
при конфликте он имеет приоритет над более ранними формулировками (в частности,
над Paseo и прежними `*-orchestrate-*` именами). Historical council artifacts не
переписываются задним числом.

## Цель

Критически пересмотреть существующую AI-driven методологию разработки из
`spec/2026-07-24-ai-driven-development-workflow/` и подготовить её следующую
версию.

Текущая спецификация является стартовой точкой, а не неприкосновенным решением.
Нужно сохранить полезные требования и рабочие идеи, исправить замечания
пользователя и радикально сократить собственный tooling там, где ту же задачу
уже решают skills, агентное рассуждение или существующие CLI вроде Herdr, Git и
Make.

Нужно также предложить implementation/migration plan для перехода от текущей
реализации к пересмотренной. Обратная совместимость с существующими командами
`meta-o`, форматом `~/.meta-o`, state-файлами и установленными skills не нужна.
Консилиум вправе рекомендовать удаление или полную замену текущего кода.

  `skills/orchestrate-feature-herdr/SKILL.md`;
- текущие `src/`, `quality/`, `templates/`, `install.sh`, `update.sh`,

Herdr/Omnigent/Paseo без проверки. Не считать наличие уже написанного кода
аргументом в пользу его сохранения.

## Исходная проблема

Пользователь ожидал methodology bundle, в котором основным продуктом являются
skills, а scripts появляются только там, где без детерминированного кода
действительно нельзя обойтись. В результате была реализована большая
промежуточная система: публичный `meta-o` CLI, собственная FSM, state/config,
adapter interface, validators, receipts, reconcile/write-ahead protocol,
capability suite и watchdog runtime.

Нужно выяснить:

1. какие исходные пользовательские цели породили каждый из этих механизмов;
2. какие цели всё ещё актуальны после новых уточнений пользователя;
3. что можно выразить непосредственно в skills через существующие CLI;
4. где небольшой `.mjs` объективно полезнее prompt-инструкции;
5. какие части являются proxy/wrapper layers без достаточной самостоятельной
   ценности и должны быть удалены;
6. какие гарантии текущей спеки следует осознанно ослабить или отменить ради
   более гибкого и понятного процесса.

## Hard constraints и подтверждённые предпочтения пользователя

### 1. Skills first

Основным интерфейсом и носителем workflow должны быть короткие skills.

Важное исключение: executor не должен придерживаться отдельного methodology
skill вообще. Не заменять текущий длинный `execute-feature` более коротким
обязательным executor skill и не делать его скрытой зависимостью запуска.
Исполнитель получает:

- исходную spec/task;
- долгоживущую goal;
- обычные project instructions (`AGENTS.md`, `CLAUDE.md` и эквиваленты), если
  они есть в проекте;
- полный доступный native tool/skill catalog выбранного агента;
- последующие исходные замечания reviewers и результаты E2E.

Этого должно быть достаточно: путь реализации исполнитель выбирает сам, а
обязательные свойства результата проверяются project QC, reviewers и E2E.
Методология не должна зависеть от того, помнит ли executor содержание
workflow skill после compaction.

У orchestrator может быть отдельный skill управления executor и остальными
ролями, если он действительно помогает компактно удерживать общий процесс.
Однако сам факт наличия orchestrator role ещё не доказывает необходимость
собственного skill: консилиум должен сравнить минимальный backend-specific
orchestrator skill с вариантом, где агент читает native backend skill, исходную
task/spec и прямые project instructions. Не создавать orchestrator skill только
ради пересказа очевидной последовательности или переименования native CLI.

`.mjs` допустим, если:

- требуется действительно жёсткая детерминированная последовательность или
  алгоритм, который ненадёжно каждый раз воспроизводить prompt-ом;
- нужной возможности нет у уже используемых инструментов;
- это самостоятельный процесс, которому объективно нужен исполняемый runtime,
  например один из возможных вариантов watchdog.

`.mjs` или другой custom code вызывает большие сомнения, если он только
оборачивает существующее API/CLI Herdr, Git, Make или другого инструмента.
Такие wrappers часто ограничивают возможности агента: при нестандартной
ситуации агент вынужден менять wrapper либо писать ещё один script вместо
прямого использования исходного CLI.

Каждый предлагаемый custom script обязан получить отдельное обоснование:

- какую конкретную операцию нельзя надёжно выполнить прямыми командами;
- почему skill с примерами существующего CLI недостаточен;
- какие invariants script гарантирует;
- как часто агенту понадобится отклоняться от его happy path;
- не превращается ли script в proxy API или скрытый control layer;
- какова стоимость его поддержки при изменении backend CLI.

### 2. Не проксировать orchestration backends

Если Herdr предоставляет собственный skill с описанием команд, методология не
должна создавать поверх него общий proxy CLI только ради переименования
`herdr agent/pane/...` в `meta-o session/...`.

Backend-specific orchestration skill может:

1. проверить, что skill Herdr установлен;
2. предложить пользователю или агенту установить его, если он отсутствует;
3. потребовать прочитать его перед работой;
4. привести несколько коротких частоупотребимых примеров;
5. затем позволить агенту напрямую использовать полный Herdr interface.

Тот же принцип обязателен для Omnigent и Paseo. Paseo уже поставляет собственный
skill, который учит агентов использовать его orchestration interface, а его CLI
предоставляет native `run`, `ls`, `logs`, `wait`, `send`, workspaces и другие
операции. Новый skill сначала использует/требует прочитать этот native skill и
docs, а не переписывает их в proxy API.

Omnigent уже является самостоятельным meta-harness с sessions, sub-agents,
разными coding harnesses, CLI/UI и persistent history. Новый skill должен
работать через его реальные native primitives и встроенные agent tools, а не
эмулировать поверх них Herdr или собственный общий session protocol.

Целевой bundle должен поддерживать три альтернативных backend-specific
orchestrator skills:

1. Herdr — текущий первый target;
2. Omnigent — следующий implementation target;
3. Paseo — следующий implementation target.

Они реализуют одну методологию и одинаковые смысловые роли, но не обязаны иметь
одинаковые команды, lifecycle details или session model. Пользователь выбирает
один orchestration backend для конкретного запуска; запуск всех трёх сразу не
является целью.

Рабочая naming hypothesis: сохранить короткий основной вызов `mo-orchestrate`
для Herdr-варианта и добавить явно backend-specific имена для Omnigent и Paseo.
Консилиум должен проверить, не яснее ли симметричные короткие имена для всех
трёх, но не создавать generic runtime router только ради единого имени.

Не вводить общий `SessionAdapter` только ради переносимости между этими тремя
backend. Общая часть должна жить в небольшом shared textual reference либо
повторяемых ясных skill instructions; backend-specific операции остаются в
соответствующем skill. Если появится предложение shared executable adapter, для
него требуется то же отдельное доказательство необходимости, что и для любого
другого wrapper.

Native возможность пользователя открыть Herdr/Omnigent/Paseo session, прочитать
её и самому написать actor уже покрывает требование ручного наблюдения и
вмешательства. В Herdr пользователь и сейчас может найти нужного actor и
отправить ему сообщение напрямую. Здесь нет противоречия, которое надо
исправлять новым UI или control layer. Нужно лишь убедиться, что выбранный
backend сохраняет эту возможность, и кратко документировать native способ ею
воспользоваться. Не дублировать backend UI/history собственным интерфейсом.

### 2.1. Обязательный поиск готовых решений до реализации

Для каждой feature до начала реализации запускается отдельный reuse-research
skill в самостоятельном CLI instance и отдельном контексте. Рабочее короткое
имя можно выбрать позднее, например `mo-reuse`; название должно ясно передавать
узкое назначение поиска и переиспользования готовых решений.

Задача researcher — проверить, нельзя ли выполнить существенную часть spec с
помощью уже существующего хорошего решения вместо нового собственного кода. Он
исследует как минимум:

- уже существующий код и abstractions проекта;
- прямые и транзитивно доступные dependencies;
- зрелые libraries, tools и open-source projects;
- maintenance status, compatibility, license, ограничения и стоимость
  интеграции найденных вариантов.

Researcher имеет право изменить только специальный человеко-читаемый раздел
feature-spec, например:

```markdown
## Reuse research

- Existing project capabilities: ...
- Evaluated solutions: ...
- Decision: reuse | extend | build
- Chosen solution and rationale: ...
- Constraints, risks and rejected alternatives: ...
```

Если подходящего решения нет, раздел всё равно фиксирует проверенные варианты и
причину решения `build`. Это защищает от повторного поиска и от бездоказательного
«напишем сами».

Если spec tracked в репозитории, reuse research оформляется первым отдельным
commit feature branch до implementation commits. Этот commit меняет spec и не
смешивается с реализацией. Если spec внешняя либо task первоначально дана
текстом, консилиум должен предложить столь же простой способ получить
обновлённую читаемую spec до запуска executor, не вводя spec blob/digest/state
protocol только ради этого случая.

После reuse commit/итерации обновлённая spec становится read-only для executor.
Дополнение исследовательского раздела само по себе не требует синхронного
approval человека, пока не меняет product behavior, scope или другие
утверждённые требования; такие изменения эскалируются пользователю.

Executor получает уже дополненную spec и использует выбранное решение при
реализации. Reviewers отдельно проверяют, что reuse decision не проигнорирован,
а отклонение от него имеет убедительное техническое основание. Не оставлять
результат исследования только во временном decision log или сообщении session.

### 2.2. Subscription-first остаётся требованием к выбранному backend

Не нужно раздувать эту итерацию отдельной абстракцией billing/routes. Herdr,
Omnigent или Paseo должны запускать локально настроенные пользовательские CLI и
использовать их обычную authentication/subscription model. Методология не
должна незаметно подменять worker sessions собственным LLM API proxy.

Это прежде всего capability/selection requirement orchestration tool, а не
основание писать дополнительный `meta-o` слой. Достаточно проверить и честно
описать поведение каждого backend; усиливать его собственным runtime пока не
требуется.

### 3. Автоматическое crash recovery не является целью

Если оркестратор умер сразу после отправки prompt, это приемлемый operational
risk. Пользователь вручную запускает оркестратор заново с тем же исходным
prompt/task.

Новый оркестратор должен уметь разумно восстановить контекст по доступной
реальности, например:

- текущему Git branch;
- истории и содержимому commits;
- рабочему дереву;
- feature-spec либо исходному пользовательскому тексту;
- живым Herdr/Omnigent/Paseo sessions и их полному последнему output;
- результатам `make`/tests и обычным файлам проекта.

Это же является требуемым уровнем восстановления после перезагрузки компьютера
или потери orchestrator session: пользователь запускает нового orchestrator с
тем же исходным prompt/task, а агент самостоятельно разбирается, где работа
остановилась. Нативное сохранение sessions полезно, но exact session-fidelity,
checkpoint replay и автоматическое восстановление всех actors не являются
обязательными. Если реальности недостаточно или она противоречива, новый
orchestrator задаёт пользователю конкретный вопрос, а не симулирует уверенность.

Не требуется обеспечивать exactly-once delivery, автоматический takeover,
write-ahead backend operations, generation fencing, собственную durable queue,
сложный reconcile или полное восстановление без участия пользователя.

Ручное вмешательство допустимо и иногда желательно. Не оптимизировать процесс
так, будто любая ручная проверка является failure.

Оркестратор должен проверить, что заданная spec/task доступна и понятна ему как
вход. Не вводить обязательное копирование спеки в content-addressed storage,
SHA-256, mutation detection или иной immutable-input protocol без отдельного
практического failure scenario. Пользователь не хочет такого уровня
формализации только ради того, чтобы передать агенту путь или текст задачи.

### 4. State и settings не считать необходимыми заранее

Пользователь склоняется к отказу от отдельного operational state и сохранённых
settings, но хочет понять, зачем они были введены.

Консилиум обязан составить разбор каждого вида текущего состояния:

- какую исходную проблему он решал;
- нужна ли эта проблема в новой модели;
- можно ли восстановить нужный факт из Git, feature-spec, Makefile, backend
  sessions или диалога с пользователем;
- что конкретно потеряется при удалении;
- оправдывает ли оставшаяся польза отдельный state/config artifact.

Default hypothesis для проверки, но не заранее утверждённый ответ: workflow
может работать без FSM/run state, findings ledger и gate receipts. Нужность
самого `~/.meta-o` и узких persistent settings нужно решить отдельно.

После дополнительного уточнения project settings нельзя удалять одной общей
группой с runtime state: сохранённый выбор моделей может быть оправданным узким
назначением `~/.meta-o`, даже если `state.json`, FSM и run artifacts исчезнут.
Нужно рассмотреть минимальный layout, в котором persistent settings и runtime
state не смешиваются.

### 4.1. Выбор моделей: редко меняющаяся настройка

Model selection важен, но не должен превращать каждый запуск в длинную
конфигурационную процедуру.

При обычном старте `mo-orchestrate` показывает компактное предложение:

```text
Use this model set or choose another?
executor: opus-5-high
reviewer-1: opus-5-high
reviewer-2: gpt-5.6-sol-medium
...
```

Default — минимальный/быстрый/ранее использованный подходящий набор. В
большинстве проектов набор одинаков и меняется редко. Пользователь может:

- подтвердить его коротким ответом;
- текстом заменить одну или несколько ролей;
- запросить полный список ролей и доступных вариантов по vendors/CLI.

Ожидаемые реальные причины изменения:

- вышел новый релиз той же model line, например `opus-4.8 → opus-5` или
  `gpt-5.5 → gpt-5.6-sol`, а не просто альтернативная модель другого семейства;
- закончились лимиты одной подписки, и пользователь временно выбирает route с
  другой подпиской/provider, например OpenCode + GLM.

Допустим небольшой model-discovery helper, использующий официальные SDK Claude,
Codex и OpenCode. Он должен исследовать доступные модели и deduplicate как
минимум:

- модели, использованные за последний месяц;
- модели из последних примерно десяти sessions;
- одинаковые effective models, увиденные через разные источники одного route.

Нужно проверить реальные SDK capabilities и не выдумывать единый API там, где
его нет. Helper не должен запускать/проксировать worker sessions или становиться
общим workflow CLI.

Пользователь допускает сохранение выбранного набора в `~/.meta-o` в разрезе
проекта, где project key выводится из hash абсолютного пути. Нужно сравнить:

- global default + редкий project override;
- только per-project setting;
- последний использованный набор без отдельного global config.

Желательное поведение: если discovery обнаружила вероятный новый major/minor
release выбранной model line, оркестратор ненавязчиво спрашивает, не обновить ли
набор. Нужно определить, как отличать настоящий successor release от просто
другой модели, как избежать ложных предложений и нужен ли для этого cache
последнего model catalog.

Не сохранять в model settings progress feature, findings, gate status или
session runtime только потому, что каталог `~/.meta-o` уже существует.

### 4.2. Context/cache economics исследуется отдельно для каждого backend

Управление context и cache остаётся важным вопросом, но не должно порождать
общий state machine с выдуманной универсальной telemetry. Консилиум обязан
исследовать отдельно для Herdr, Omnigent и Paseo и для поддерживаемых ими
Claude/Codex/OpenCode routes:

- можно ли получить размер или заполненность context;
- доступно ли время последнего turn и признаки native compaction;
- что известно о cache TTL и цене cold resume в подписочном режиме;
- сохраняется ли goal/session state после native resume;
- когда выгоднее продолжить старую session, сделать native compact либо
  поднять fresh actor с task/spec и Git reality;
- какие данные реально доступны через native CLI/skill/API, а какие только
  предполагаются;
- можно ли сохранить тёплый context без искусственных пустых turns и лишней
  суеты.

Для каждого backend итог должен содержать честную capability table:
`available | inferred | unavailable`, практическую рекомендацию и fallback.
Не переносить thresholds между провайдерами без измерений и не создавать
собственный cache tracker, если backend не даёт надёжных исходных данных.

### 4.3. Время человека дороже токенов

Вернуть этот принцип как явный критерий всех design decisions. По умолчанию
лучше дополнительная автоматическая проверка или самостоятельный agent turn,
чем обязательное ручное дежурство пользователя. При этом не путать полезное
ручное вмешательство с ритуальными confirmations.

Каждый обязательный user gate должен отвечать на вопросы:

- какое решение действительно может принять только человек;
- что сломается, если agent примет обратимое техническое решение сам;
- можно ли использовать ранее подтверждённый default;
- насколько часто этот gate будет останавливать ночной или долгий run.

Обычные технические развилки, чтение/запуск tools и подтверждение уже выбранных
defaults не должны постоянно расходовать внимание человека. Продуктовый смысл,
необратимые/дорогие действия и реальная внешняя блокировка остаются поводом для
эскалации.

### 4.4. Permissions задаются пользовательскими PATH wrappers

Методология не должна сама конструировать универсальный набор sandbox/approval
flags. На компьютере пользователя `which`/`command -v` уже разрешает имена CLI
в пользовательские wrappers:

```text
claude → /Users/alex/bin/claude
codex  → /Users/alex/bin/codex
```

Проверенное на 2026-08-05 поведение:

- wrapper Claude вызывает `/opt/homebrew/bin/claude` с
  `--dangerously-skip-permissions`;
- wrapper Codex вызывает `/opt/homebrew/bin/codex` с
  `--dangerously-bypass-approvals-and-sandbox`.

Orchestration backend и skills должны запускать `claude`, `codex` и другие
агенты через обычный `PATH`, сохраняя пользовательскую command resolution. Они
не должны обходить wrappers, самостоятельно находя Homebrew/app binary по
absolute path, либо заменять пользовательские flags своими более ограниченными
defaults.

Preflight может показать resolved command path и предупредить об очевидно
неожиданном resolution, но не должен просить отдельное approval на каждое
действие и не должен копировать содержимое wrapper в methodology config.
Permission policy является ответственностью локального окружения пользователя;
методология отвечает только за то, чтобы не обходить это окружение.

### 5. Review findings передаются без обязательного Structured JSON

Первоначальное намерение: оркестратор получает полное последнее сообщение
каждого reviewer и передаёт его исполнителю максимально близко к исходному виду,
не теряя замечания, аргументы, evidence, caveats и suggested fixes.

Не вводить обязательный `Finding` JSON, severity schema, отдельный findings
store или parsing/validation layer без нового убедительного обоснования.
Reviewer может использовать удобную Markdown-структуру, но transport не должен
зависеть от того, удалось ли распарсить custom JSON schema.

Критическое техническое требование: оркестратор должен прочитать именно полное
последнее сообщение reviewer, а не только видимую часть terminal pane и не
фиксированное число последних строк. Способ будет backend-specific и должен
быть исследован отдельно для Herdr, Omnigent и Paseo. Нельзя молча считать
truncated tail полным результатом.

Нужно сравнить варианты:

- backend-native получение полного последнего turn/message;
- prompt envelope/marker без общего proxy CLI;
- небольшой backend-specific helper, только если native interface
  действительно не позволяет надёжно получить полный result;
- ручное открытие/прочтение session как допустимый fallback.

### 5.1. Самостоятельный переиспользуемый review skill

Нужен отдельный короткий skill review loop, рабочее имя `mo-review`. Один и тот
же skill должен быть доступен в двух режимах использования:

1. `mo-orchestrate` вызывает его как обязательный review stage полного feature
   workflow;
2. пользователь запускает его напрямую после быстрого fix или для уже
   существующего результата без запуска полного orchestrator flow.

Skill должен организовать независимые reviews, передать полные исходные
замечания исполнителю/автору, повторить проверку после fixes и помочь разрешить
спор. Он не должен требовать `state.json`, snapshot registry, E2E metadata или
активный full-feature run только ради возможности провести review.

Сохранить исходную модульность review cube: нужно исследовать, как применять
тот же механизм не только к Git code change, но и к spec, документу,
презентации или другому явно указанному artifact. Code-specific проверки могут
быть conditional частью skill, а не обязательным input contract всех reviews.

Первый проход разных reviewers остаётся независимым. Structured JSON не
становится обязательным transport format standalone skill.

### 6. Назначение оркестратора

Главная задача оркестратора — правильно управлять агентами, чтобы они выполнили
спеку или пользовательскую задачу, а затем независимо проверили полноту и
качество результата.

Оркестратор не обязан быть транзакционным workflow engine. Он может применять
рассуждение, смотреть реальное состояние проекта и задавать пользователю
вопросы при неопределённости.

Нужно пересмотреть прежний жёсткий запрет оркестратору читать что-либо в
проекте. Как минимум он должен иметь право читать Git status/history, branch,
feature-spec, Makefile и operational project documentation. При этом он не
должен превращаться в основного implementer или самостоятельно проводить
полный code review.

### 6.1. Executor запускается с долгоживущей goal, а не обычным prompt

Это требование было явно сформулировано в исходном
`spec/2026-07-24-ai-driven-development-workflow/task-description.md` и
`docs/references/my-opinion.md`: один сильный executor получает всю spec в
отдельной долгоживущей goal-session и не останавливается после удобной части.
Однако в authoritative master/orchestration specs оно потерялось, а текущие
`skills/orchestrate-feature-herdr/SKILL.md` и `skills/execute-feature/SKILL.md`
не требуют активировать native goal mode. Текущий `meta-o session send`
передаёт обычный framed prompt и не имеет отдельного goal contract или
проверенной capability активации `/goal`.

Для Codex executor orchestrator должен запускать задачу через native `/goal`,
если эта capability доступна в выбранной surface. По актуальной документации
Codex Goal mode является stable и доступен в Codex app, interactive CLI и IDE;
goal text становится одновременно первым prompt и completion criteria:
https://learn.chatgpt.com/docs/long-running-work.

Goal не должна содержать полную большую spec как продублированный inline blob,
если executor может прочитать её по path. Она должна требовать:

- прочитать всю указанную spec/task и обычные project instructions целиком до
  реализации; отдельного обязательного executor skill нет;
- реализовать полный scope, а не MVP или удобную часть;
- не переносить сложные обязательные пункты на потом без внешней блокировки;
- сохранить оговорённые architecture, compatibility и project constraints;
- выполнить executor-owned checks, включая typecheck/lint/tests/QC и простой
  E2E smoke, если он применим;
- синхронизировать durable knowledge и получить проверяемый candidate;
- продолжать самостоятельно, пока executor-owned definition of done не
  достигнут либо не возникла реальная `needs_attention` блокировка.

Goal mode не расширяет permissions и не устраняет необходимость в
orchestrator: executor всё ещё может остановиться на вопросе, нехватке доступа
или внешнем failure. Обычные tool approvals должны быть уже сняты
пользовательским PATH wrapper; если backend обошёл wrapper и вернул approval
prompts, это configuration failure, а не ожидаемая стадия workflow.
Orchestrator наблюдает native session state, отвечает и возобновляет работу.

Не считать строку `/goal` универсальным протоколом всех агентов. Консилиум
должен исследовать отдельно:

- как надёжно активировать `/goal` через direct Herdr control Codex-session, не
  превратив slash command в обычный текст из-за paste/framing semantics;
- какие native persistent-goal/automatic-continuation mechanisms существуют у
  Claude Code и OpenCode;
- как Omnigent и Paseo передают slash commands либо предоставляют собственную
  goal/session continuation semantics для каждого underlying harness;
- как проверить, что goal действительно активна, без нового `goal.json`, FSM
  или proxy CLI;
- сохраняется ли active goal при native resume и что доступно новому
  orchestrator после ручного restart.

Если backend не имеет native goal mode, нужен честно названный fallback:
долгоживущая executor session, жёсткий completion-oriented initial prompt и
orchestrator-driven продолжение при преждевременном idle. Не выдавать такой
fallback за эквивалент persisted automatic goal и не писать новый workflow
engine только ради эмуляции этой capability без отдельного решения.

Отдельный важный вопрос — granularity goal. Консилиум должен сравнить:

1. одну feature-level goal, которая остаётся активной через implementation,
   review fixes и E2E fixes до общей готовности;
2. initial implementation goal до candidate, затем отдельные короткие goals для
   каждого batch review/E2E fixes;
3. initial goal до executor-owned definition of done и обычные follow-up turns
   в той же сохранённой session.

Нужно избежать обеих крайностей: преждевременного завершения большой spec без
goal и бесконечного automatic continuation, когда executor уже должен ждать
независимое review либо E2E result. Reviewers по умолчанию не требуют goal mode;
для долгого agentic benchmark/tester это решается отдельно по реальной задаче.

### 6.2. Рефлексия после существенных сбоев

Вернуть потерянный этап рефлексии, но не превращать каждый run в обязательный
ретроспективный отчёт. Существенный или повторяющийся сбой должен вызвать
короткий разбор:

- что произошло;
- почему обычные checks/review/E2E не поймали проблему раньше;
- является ли это локальной ошибкой реализации или системным дефектом
  methodology, project instructions, skill, QC, knowledge либо orchestration
  backend;
- какое конкретное изменение способно предотвратить повторение;
- где зафиксировать actionable follow-up так, чтобы он не потерялся.

Нужно определить минимальный trigger и формат. Не хранить полные transcripts и
не создавать отдельный lessons database без необходимости. Предпочтение —
короткая понятная запись в обычном `docs/todo.md` либо другом уже существующем
человеко-читаемом источнике, с причиной и предлагаемой отдельной feature.

Рефлексия не расширяет текущую feature автоматически. Она либо приводит к
локальному исправлению в текущем scope, либо фиксирует отдельное улучшение,
которое пользователь позднее явно подхватит.

### 6.3. Методология применяется к себе только по воле пользователя

`meta-o`, его skills и сама методология могут дорабатываться с применением этой
же методологии: отдельная spec/task, executor, QC, независимый review и реальная
проверка результата. Это полезный self-hosting принцип, но не автоматическая
рекурсия.

Только пользователь решает, когда найденный methodological follow-up брать в
работу и запускать через полный flow. Оркестратор не должен самовольно
расширять текущую продуктовую feature изменениями собственного workflow или
запускать бесконечное самоулучшение.

### 7. Интерфейс `mo-orchestrate`

Желаемое короткое имя главного skill — `mo-orchestrate`.

Если пользователь вызывает skill без feature-spec или task, агент должен:

1. прочитать skill и выполнить необходимый минимальный preflight;
2. понять, есть ли очевидная текущая незавершённая работа;
3. спросить пользователя, что требуется сделать или продолжить.

После этого пользователь может:

- дать путь/ссылку на feature-spec;
- описать задачу обычным текстом;
- сказать продолжать текущую работу.

Нужно предложить короткие последовательные имена остальных final skills. Имена
не должны описывать backend или внутреннюю архитектуру длиннее, чем это нужно
пользователю. Backend-specific детали могут жить внутри skill либо в отдельно
подключаемом reference/skill.

### 8. Makefile как обнаруживаемый project interface

На старте оркестратор должен прочитать Makefile и найти доступные project
commands: QC, lint, typecheck, test, build, smoke, E2E и другие применимые
проверки.

Если нужных targets нет, оркестратор предлагает их настроить. Если аналогичная
команда существует под другим именем, он спрашивает, использовать ли её вместо
default target.

Нужно исследовать предпочтительный контракт, при котором methodology targets
имеют короткий namespace, например:

```text
mo-qc
mo-lint
mo-typecheck
mo-test
mo-build
mo-smoke
mo-e2e
```

Эти targets могут:

- вызывать уже существующие Make targets;
- непосредственно запускать принятые в проекте команды;
- отсутствовать, если соответствующая проверка объективно неприменима и это
  явно согласовано.

Нужно определить:

- должен ли оркестратор сам изменять Makefile или поручать это executor;
- когда требуется пользовательское подтверждение;
- как избежать дублирования существующего project interface;
- нужен ли обязательный `mo-qc`, агрегирующий применимые проверки;
- как отличить отсутствующую проверку от той, что имеет другое имя;
- как это работает в проектах без Make либо с другим task runner.

### 8.1. Три формы E2E и условная роль tester

Новая спецификация должна различать как минимум три формы E2E:

1. короткая детерминированная console/shell проверка, например перезапустить
   Docker, вызвать один endpoint и проверить output;
2. полноценный benchmark для agentic или иного недетерминированного поведения;
3. browser E2E через установленный `agent-browser` и его skill.

Правила ролей:

- короткую понятную console E2E запускает executor;
- если есть короткий и стабильный E2E smoke, он может входить в `mo-qc` либо
  другую обычную QC-команду;
- benchmark и browser E2E выполняет отдельная agent role/session;
- решение, нужна ли отдельная role для конкретного проекта/изменения, принимает
  оркестратор по проектному E2E contract и фактическому способу выполнения;
- обычные lint/typecheck/unit/integration tests выполняют executor и при
  необходимости reviewers; для них отдельный E2E tester не создаётся.

Для benchmark и browser flow `make mo-e2e` не обязан пытаться выполнить E2E
без агента. Он может выводить короткий project-specific help:

- что именно считается E2E в этом проекте;
- какие prerequisites нужны;
- какой skill/tool должен прочитать tester;
- какую команду, benchmark или browser-сценарий запускать;
- где смотреть результат и как выполнить cleanup.

Нужно сделать этот контракт наглядным и простым, без обязательного E2E registry
или orchestration schema.

Текстовые browser E2E scenarios предпочтительно хранить в одном из двух
масштабируемых layouts:

```text
docs/e2e.md
```

либо:

```text
docs/e2e/index.md
docs/e2e/<scenario-group>.md
```

`index.md` содержит базовое описание environment, prerequisites, запуск,
cleanup и каталог групп. Отдельные файлы содержат тематические группы
проверяемых сценариев, чтобы agent tester мог выбрать релевантный subset по
изменению, а не каждый раз выполнять всё подряд.

Выбор layout должен зависеть от размера, а не от заранее навязанной структуры:
несколько коротких сценариев живут в `docs/e2e.md`; при появлении нескольких
независимых групп материал переносится в `docs/e2e/index.md` и group files.
Каждая группа должна объяснять, когда её выбирать. Полный прогон всех групп не
является default, если задача затрагивает только ограниченную часть системы.

Benchmark также может запускаться одной или несколькими отдельными командами и
обычно занимает много времени. Его command set и selection rules можно описать
текстом рядом с E2E instructions; сам факт наличия benchmark не требует JSON
registry.

Отдельно проверить целесообразность `e2e.json`: пользователь пока не видит
необходимости в нём даже для browser/benchmark flow. JSON должен остаться только
если judges покажут функцию, которую нельзя достаточно хорошо выполнить через
читаемые scenario docs, Make help и agent selection.

### 9. Проверки одного и того же результата

Текущая спецификация вводит snapshot digest, attestations и gate receipts, чтобы
доказать, что QC, два review и E2E относятся к одному содержимому.

Пользователь не считает доказанным, что для этого нужен отдельный state/control
layer. Консилиум обязан не повторять прежний тезис как аксиому, а показать
конкретные failure scenarios:

- когда reviews или E2E фактически могут проверить разные revisions;
- почему Git branch/commit SHA и последовательная работа оркестратора
  достаточны или недостаточны;
- что происходит, если executor внёс fixes между gates;
- нужен ли detached worktree либо достаточно явно переданного commit;
- какой минимальный механизм предотвращает false completion;
- какая часть проверки может быть простым правилом skill, а какая действительно
  требует кода.

Решение должно быть пропорционально реальному риску. Не требовать
криптографического workflow ledger, если тот же практический результат даёт
простое правило: зафиксировать candidate commit, не менять его во время gates и
повторить invalidated проверки после нового commit.

Пользователь не понимает отдельной ценности `snapshot_digest`. Нужно объяснить,
какую задачу он решает сверх обычного Git commit SHA. Возможность сохранять
старые attestations после rebase/amend сама по себе не считается достаточным
основанием. Default preference — использовать commit/branch reality и удалить
snapshot digest, если council не покажет более существенный failure mode.

Fresh detached worktrees полезны для фиксации revision и изоляции, но могут
усложнить работу агента, environment setup и восстановление контекста. Нужно
сравнить:

- работу всех ролей в текущей feature branch/worktree с дисциплиной commits;
- отдельный worktree только для действительно изолируемых deterministic gates;
- отдельные worktrees для reviewers/E2E;
- полный отказ от обязательных worktrees на этом этапе.

Не считать fresh detached worktree обязательным для E2E tester до принятия
общего решения по worktrees.

### 10. Watchdog как отдельный skill/session

Желаемое имя — `mo-watchdog`.

Предполагаемый пользовательский flow:

1. пользователь запускает `mo-orchestrate`;
2. оркестратор готовится запустить executor;
3. оркестратор спрашивает, запускать ли watchdog;
4. при согласии оркестратор создаёт отдельную native
   Herdr/Omnigent/Paseo tab/pane/session;
5. в ней запускается агент, читающий `mo-watchdog`;
6. watchdog получает минимальную информацию, позволяющую найти и наблюдать
   конкретного оркестратора;
7. пользователь также может отдельно попросить запустить watchdog либо
   проверить, что он существует и работает.

Нужно спроектировать назначение и пределы watchdog заново. Не считать заранее,
что ему нужны systemd/launchd, глобальный multi-project config, FSM mutation,
deterministic service или собственный runtime. Одновременно проверить, способен
ли отдельный LLM agent/session надёжно выполнять ожидаемое наблюдение и что
происходит при его собственной остановке.

Default preference — связь `one watchdog session → one orchestrator session`.
Не требовать от одного process наблюдения нескольких projects/runs, если это
усложняет identification, recovery или implementation. Multi-project watchdog
можно оставить только как отдельно доказанное расширение, а не baseline.

Если standalone `.mjs` всё же требуется, обосновать, какую функцию невозможно
выполнить отдельным skill/session или native backend notification mechanism.

### 11. Project knowledge: простая видимая структура

Предпочтительный верхнеуровневый layout:

```text
docs/business.md
docs/glossary.md
docs/todo.md
docs/architecture/
```

Business, glossary и todo должны находиться непосредственно под `docs/`, потому
что это документы, которые пользователь может и должен часто читать. Отдельный
уровень `docs/knowledge/` кажется лишним. Если кроме architecture в нём нет
другого самостоятельного слоя, architecture должна жить просто в
`docs/architecture/`.

Нужно пересмотреть все остальные обязательные knowledge artifacts и оставить
только те, которые имеют понятного читателя, момент обновления и защиту от
конкретного drift.

Термин `knowledge sync` сейчас недостаточно понятен. Консилиум обязан определить
его простыми словами и решить:

- какие устойчивые факты из feature-spec действительно переносятся в
  `business.md`, architecture docs и code purpose;
- в какой момент это делает executor;
- как избежать копирования feature-spec целиком;
- когда старая tracked spec удаляется или перестаёт быть активным источником;
- как обрабатывается task, заданная обычным текстом без spec-файла;
- как reviewers проверяют, что durable знания соответствуют реализации и не
  потеряли важный смысл.

Внешний `KnowledgeImpactPlan` кажется лишним для тонкого оркестратора. Нужно
спроектировать knowledge update без отдельного plan artifact, если нет
доказанного сценария, где executor и reviewers не справляются через spec, diff
и обычные docs.

Отдельно проверить необходимость:

- `e2e.json`;
- `adoption-manifest.json`;
- feature retirement metadata;
- verification registries;
- отдельного knowledge checker сверх обычных linters и review.

`docs/todo.md` является понятным местом для обнаруженного debt и follow-ups вне
scope текущей feature. Методология обязана не потерять проблему, но не обязана
сама планировать или автоматически запускать её исправление. Пользователь
отвечает за последующий выбор и запуск таких задач.

Запись должна быть достаточно содержательной, чтобы её можно было позднее
превратить в spec без восстановления исчезнувшей session: area/path, проблема,
практический risk или symptom и ожидаемая форма исправления. Не требовать
отдельный debt registry, status machine или автоматический backlog scheduler.

### 11.1. Архитектурные требования живут в project instructions и проверке

Вернуть исходное требование проектировать архитектуру уже в постановке, но не
через обязательный executor skill. Компактные постоянные тезисы проекта могут
жить в обычных `AGENTS.md`, `CLAUDE.md` или эквивалентных project instruction
files, которые выбранные агенты и так умеют читать.

Тезисы должны требовать при проектировании и реализации явно подумать:

- на какие компоненты и модули естественно делится изменение;
- где проходят границы ответственности;
- какие зависимости допустимы между слоями;
- какие части должны меняться независимо;
- не создаются ли god-files, god-objects и чрезмерная связность;
- как feature встраивается в существующую архитектуру вместо очередного слоя;
- какие устаревшие ветвления, обходы или временные abstractions можно упростить
  в пределах scope.

Feature-spec должна отражать применимые к конкретному изменению архитектурные
вопросы. Обязательный reuse researcher не отвечает за общее проектирование
спеки: его узкая роль — поиск готовых решений. Executor читает обычные project
instructions, но не methodology skill. Reviewers получают
architecture/necessity как явный review lens и проверяют не только соответствие
написанной spec, но и качество её архитектурного решения. Orchestrator может
читать project instruction files при ответах на вопросы executor и разрешении
технических развилок.

Консилиум должен решить, как избежать drift и дублирования между `AGENTS.md` и
`CLAUDE.md`: один canonical shared fragment, короткое согласованное
дублирование, generated links либо другой нативный для проекта вариант. Не
создавать новый центральный instructions runtime ради синхронизации двух
небольших файлов.

### 11.2. Глобальная архитектурная гигиена — отдельный будущий инструмент

Еженедельный или иной периодический аудит всего проекта не входит в feature
orchestration и не должен усложнять `mo-orchestrate`. Для него позже нужен
отдельный инструмент/skill, который ищет архитектурную деградацию, monolith
growth, duplication, устаревшие обходы и отработавшие feature flags, а после
удаления flag проверяет упрощение code/config/tests/logs.

В этой итерации достаточно сохранить эту явную границу и future requirement.
Не симулировать глобальный аудит локальными per-feature manifests и не включать
его design/implementation в обязательную поставку текущей revision.

### 12. Purpose должен передавать смысл GRACE, а не compliance-текст

Судьи обязаны внимательно изучить смысл, заложенный в
`docs/references/grace.md`, и проверить, что новая спецификация сохраняет его, а
не только синтаксическую обязанность иметь docstring.

Purpose должен объяснять, зачем существует module/class/function/method, какую
роль он играет в системе и почему его нельзя бездумно удалить или изменить. Он
не должен пересказывать реализацию.

Требование нужно усилить:

- overloaded declarations/methods также обязаны нести purpose; прежнее
  исключение «overload declaration при документированной реализации» не
  принимается автоматически;
- private, tests и другие first-party symbols проверяются согласно принятому
  coverage policy;
- mechanical checker проверяет доступную ему структуру и наличие, но reviewers
  обязательно критикуют semantic adequacy, cargo-cult text и drift purpose;
- reviewers проверяют не только соответствие feature-spec, но и вопрос
  «зачем эта сущность/абстракция/изменение вообще нужно?».

Нужно определить реалистичный coverage и исключения так, чтобы требование не
превратилось в бессмысленные повторяющиеся docstrings, но не потеряло исходную
важность causal context.

Если проверяется Markdown, использовать нормальный Markdown parser с AST, а не
набор регулярных выражений. Консилиум должен проверить фактическую реализацию
текущих parsers и решить, нужны ли эти проверки вообще в новом наборе.

### 13. QC tooling: готовые инструменты прежде custom project code

Текущий `.quality/qc-manifest.json` и machine-readable gate results вызывают
сомнения. Нужно объяснить, какую практическую проблему они решают и нельзя ли
получить достаточный результат через Make targets, exit codes и чтение полного
output агентом.

В текущем желаемом процессе не определён внешний machine consumer manifest:
оркестратор, executor и reviewers сами читают Makefile, команды и полный output.
Поэтому наличие такого consumer нельзя использовать как аргумент по умолчанию.
Если council предлагает сохранить manifest, он обязан назвать конкретного
consumer и действие, которое без manifest нельзя надёжно выполнить.

Default preference:

- не создавать project-owned AST purpose checker;
- не создавать project-owned knowledge/E2E metadata checker;
- перевозить общий набор best-practice checks вместе с соответствующим skill
  или минимальным tool package;
- включать/выключать и настраивать их через native project config, например
  `pyproject.toml`;
- по умолчанию включать полезные checks;
- использовать готовые lint/plugins/tools прежде написания своего кода;
- писать custom checker только когда готовый инструмент или небольшой plugin
  объективно не может выполнить требование.

Исходно нужны были, в частности:

- наличие и базовая форма purpose;
- размеры files/classes/functions/methods;
- cyclomatic complexity;
- при необходимости зависимости/boundaries/cycles.

Нужно провести исследование готовых Python tools/plugins для этих задач,
включая import graph / architecture boundaries. Не принимать custom Import
Graph Algorithm из текущей спеки как обязательный, пока не проверены готовые
решения.

Также проверить необходимость regression baseline вроде
`.quality/code-health-baseline.json`. Не вводить baseline только ради brownfield
adoption; объяснить, какую пользу он даёт, как не превращается в вечное
разрешение старого debt и можно ли начать с обычных configurable thresholds.

### 13.1. TypeScript QC: отдельный first-class profile

Новая спецификация должна продумать QC не только для Python, но и для
TypeScript/JavaScript projects. Исследование должно опираться на актуальные
primary docs на момент запуска консилиума, а не переносить Python-specific
предположения в JS ecosystem.

Минимальный project-facing contract остаётся простым и language-neutral:

```text
make mo-typecheck
make mo-lint
make mo-test
make mo-qc
```

Имена могут проксировать уже существующие project targets/scripts. В проектах
без Make допустим эквивалент через native task runner, но orchestrator должен
сначала обнаружить существующие `package.json` scripts, workspace runner и
package manager, а не устанавливать второй параллельный toolchain.

Research snapshot от 2026-08-05, который нужно перепроверить и развить:

- canonical typecheck baseline — отдельная команда TypeScript compiler, обычно
  `tsc --noEmit` с project `tsconfig.json`; существующие project references,
  `tsc -b` и framework-specific checkers вроде `vue-tsc` нужно обнаруживать и
  сохранять. Для нового code предпочтителен `strict`, а дополнительные
  strictness flags оцениваются по совместимости проекта:
  https://www.typescriptlang.org/tsconfig/noEmit.html и
  https://www.typescriptlang.org/tsconfig/strict.html;
- mature compatibility-first lint path — ESLint flat config плюс
  `typescript-eslint` typed linting (`recommendedTypeChecked` и
  `parserOptions.projectService: true`):
  https://eslint.org/docs/latest/use/configure/configuration-files и
  https://typescript-eslint.io/getting-started/typed-linting/;
- fast modern lint path — Oxlint. Его type-aware linting объявлен stable в июле
  2026 и близок, но пока не полностью равен typescript-eslint rule coverage.
  Отдельный `tsc --noEmit` не удалять только потому, что Oxlint имеет
  `--type-check`: сначала проверить maturity, TypeScript version constraints и
  config compatibility:
  https://oxc.rs/docs/guide/usage/linter/type-aware.html;
- Biome можно сравнить как integrated formatter/linter, но не объявлять
  эквивалентом полного TypeScript typechecker или typed ESLint/Oxlint без
  проверки реально нужных rules;
- для formatting отделять formatting от correctness lint. Если выбран Prettier
  вместе с ESLint, выключать конфликтующие stylistic rules через
  `eslint-config-prettier`, а не запускать formatter как lint rule:
  https://prettier.io/docs/integrating-with-linters.html;
- test runner сначала переиспользуется существующий: не мигрировать Jest или
  другой рабочий stack только ради стандартизации. Для greenfield Node-only
  проекта сравнить stable built-in `node:test` с Vitest. `node:test` уменьшает
  dependency surface; Vitest даёт более богатый TS/Vite-oriented workflow,
  mocking и coverage. Runtime execution TS tests не заменяет typecheck: Vitest
  прямо указывает, что обычный test run transpiles TypeScript, но не type-checks
  его:
  https://nodejs.org/api/test.html и
  https://vitest.dev/guide/learn/writing-tests;
- coverage является отдельным осознанным gate, а не обязательным процентом без
  смысла. Если он нужен, thresholds относятся к критичным modules/risks и
  native coverage facility выбранного runner; не принимать `100%` как default.

Готовые lint rules должны также быть первым выбором для общих code-health
ограничений. В ESLint уже есть `complexity`, `max-lines`,
`max-lines-per-function` и `max-statements`; прежде custom TS AST checker нужно
проверить их и соответствующие Oxlint rules. Thresholds нельзя копировать из
Python mechanically: council должен предложить defaults, exceptions для
generated/config/declaration files и способ не превратить metrics в цель сами
по себе.

Консилиум должен сравнить минимум два реальных TypeScript profiles:

1. compatibility profile: `tsc` + ESLint/typescript-eslint + existing test
   runner;
2. fast profile: `tsc` + Oxlint + existing test runner.

Для greenfield отдельно дать правило выбора `node:test` или Vitest. Не вводить
собственный JS/TS QC wrapper: результат должен выражаться обычными project
scripts/Make targets и native config files выбранных tools.

### 14. Actor status, review depth и disputed findings

Для orchestration пользователя в первую очередь интересует, требует ли actor
внимания:

```text
idle | needs_attention
```

Нужно проверить, достаточно ли этого operational view поверх native backend
status. Оркестратор должен вместо пользователя смотреть sessions, которые не
idle или явно требуют внимания. Не вводить большую собственную status taxonomy,
если она не меняет действие оркестратора.

Reviewers должны проводить самостоятельную архитектурную критику, включая
вопросы:

- зачем вообще нужна предложенная сущность или abstraction;
- решает ли она реальную задачу или только формально следует spec;
- не додумал ли executor лишнее там, где spec неполна;
- можно ли получить тот же результат проще;
- не растёт ли tooling/harness быстрее полезной системы;
- адекватны ли purpose и durable project knowledge.

Нужно отдельно решить использование subagents reviewers. Claude часто активно
использует subagents по умолчанию, Codex может не использовать их без прямой
инструкции. Сравнить:

- не предписывать subagents и оценивать только результат;
- рекомендовать ограниченное параллельное исследование аспектов;
- явно просить примерно 6–9 subagents, сгруппированных по независимым lenses;
- динамически выбирать число по размеру diff/spec.

Если subagents рекомендуются, ограничить fan-out, duplication и context cost;
это не должно становиться ритуальным числом для маленькой задачи.

Текущий `adjudicate-technical` / fresh technical adjudicator непонятен
пользователю. Нужно объяснить исходный failure mode: затянувшийся спор reviewer
и executor, который тонкий orchestrator не может надёжно разрешить сам. После
этого решить, нужен ли отдельный skill/role либо достаточно:

- попросить reviewer проверить ответ executor;
- предпочтительно спросить второго reviewer;
- поручить короткое независимое исследование subagent;
- на худой конец позволить оркестратору принять техническое решение;
- эскалировать пользователю только если спор затрагивает продуктовый смысл или
  остаётся действительно неразрешимым.

Первый проход обоих reviews остаётся независимым. Но при разборе уже возникшего
конкретного спора второму reviewer разрешено показать finding первого reviewer
и rebuttal/evidence executor, чтобы второй reviewer выступил арбитром по этому
пункту. Это targeted dispute resolution, а не обмен findings до независимого
первого verdict.

Если executor/автор сознательно не исправляет substantive замечание и причина
выбранной конструкции не очевидна из самого кода, rationale нужно оставить на
уровне кода рядом с соответствующим решением. Иначе временная переписка
исчезнет, а следующий reviewer снова увидит ту же подозрительную конструкцию без
контекста. Комментарий обязан объяснять `why`, constraint или rejected safer
alternative, а не пересказывать механику реализации.

Консилиум должен сформулировать правило так, чтобы оно сохраняло durable
rationale и одновременно не засоряло код комментариями для чисто вкусовых
suggestions. Простое отклонение finding во временном run-state не считается
достаточным, если аргумент останется важен для будущих изменений.

Не сохранять отдельный adjudication skill без доказанной частоты и пользы.

Ограничение optional handoff `≤4 KiB` также не считать принятым. Нужно выяснить,
зачем handoff вообще нужен при доступных Git/spec/sessions, и либо удалить его,
либо обосновать сам artifact и способ удерживать его компактным без случайной
магической границы.

### 15. Distribution без собственных installer/update scripts

`install.sh` и `update.sh` не должны входить в новую поставку.

Пользователь будет устанавливать skills непосредственно из `dist` через:

- `apm`: https://github.com/microsoft/apm
- `skills`: https://github.com/vercel-labs/skills

Нужно спроектировать layout `dist`, совместимый с такими способами доставки,
и определить, как рядом со skill поставляются действительно нужные references,
assets и private helpers. Не создавать собственный package/update lifecycle и
не запускать скрытые capability suites при установке.

## Требование провести tooling audit

Для каждого текущего компонента или семейства компонентов дать решение:

```text
keep as-is | keep but move into skill | replace with direct CLI |
replace with smaller helper | delete | defer
```

Минимально классифицировать:

- публичный `meta-o` CLI и каждую крупную группу его commands;
- FSM/routing core;
- `~/.meta-o` project/run state и settings;
- ModelSet discovery, persistence и upgrade suggestions;
- findings/decisions/gate records;
- snapshot digest и metadata guard;
- detached worktree helpers;
- Herdr adapter и `SessionAdapter` abstraction;
- отдельные direct integration flows для Herdr, Omnigent и Paseo;
- capability suite;
- текущий обязательный `execute-feature` skill и все требования, которые нужно
  перенести из него в spec/project instructions/review вместо замены другим
  executor skill;
- обязательный pre-execution reuse-research skill и первый spec-only commit;
- standalone `mo-review` как полный review loop, а не skill одной reviewer role;
- executor goal-mode activation, continuation и native resume behavior;
- PATH resolution и сохранение пользовательских permission wrappers;
- per-backend context/cache/compaction capabilities;
- complete reviewer output retrieval;
- installer/update scripts;
- watchdog code и service units;
- project QC helpers;
- `.quality/qc-manifest.json` и machine-readable results;
- `KnowledgeImpactPlan`;
- `e2e.json` и verification metadata;
- `adoption-manifest.json`;
- code-health baseline;
- custom import graph implementation;
- Markdown parsing approach;
- Python и TypeScript QC templates/config recommendations;
- knowledge/purpose checks;
- минимальный reflection/lessons flow и durable rationale отклонённых findings.

Для `delete` и `replace` указать, чем покрывается нужная функция после удаления.
Для `keep` указать конкретный пользовательский риск, который оправдывает код.

## Что нельзя считать успехом

- Переименовать большой `meta-o` CLI во «внутренний helper», сохранив тот же
  control surface.
- Разбить proxy layer на большее число scripts внутри skill directories и
  объявить это skills-first архитектурой.
- Заменить `execute-feature` другим обязательным executor skill либо скрыто
  сохранить тот же ritual в executor prompt.
- Сохранить custom adapter только потому, что он уже написан.
- Требовать Structured JSON только потому, что его проще валидировать.
- Автоматизировать recovery, которого пользователь не просит.
- Хешировать и копировать feature-spec без конкретной необходимости.
- Считать любое ручное вмешательство дефектом методологии.
- Механически реализовывать каждое предложение спецификации без оценки цены и
  реального failure mode.
- Сохранять обратную совместимость ценой дополнительной сложности.
- Возить собственные install/update scripts вместо стандартной skill delivery.
- Делать отдельного E2E tester для lint/unit tests или короткой smoke-команды.
- Отправлять большую spec executor обычным one-shot prompt, когда выбранный
  agent имеет native persisted goal mode, и считать это эквивалентным `/goal`.
- Эмулировать отсутствующий backend goal mode новым общим FSM/runtime, не
  сравнив сначала persistent session плюс orchestrator-driven continuation.
- Провести reuse research, но не записать его в отдельный раздел spec/первый
  commit либо не передать выбранное решение executor и reviewers.
- Обходить пользовательские `claude`/`codex` PATH wrappers прямым запуском
  Homebrew/app binary и затем компенсировать это собственным permission layer.
- Считать запись debt или methodological lesson потерянной только потому, что
  пользователь, а не автоматический scheduler, решает, когда взять её в работу.
- Предлагать формальную точность без объяснения, какую практическую ошибку она
  предотвращает.

## Требования к вариантам

Сравнить минимум три архитектурных уровня, не принимая ни один заранее:

1. почти pure-skills с прямыми вызовами backend/project CLI;
2. skills плюс несколько строго обоснованных private helpers;
3. небольшой explicit workflow engine для тех гарантий, которые невозможно
   получить иначе.

Текущую реализацию использовать как контрольный пример более тяжёлого варианта,
а не как обязательную основу. Для каждого уровня показать:

- пользовательский flow;
- состав skills и scripts;
- recovery semantics;
- review/E2E flow;
- адаптацию нестандартных проектов;
- стоимость сопровождения;
- какие гарантии теряются и почему это приемлемо или неприемлемо.

## Требования к итоговой спецификации

Финальный документ пишется по-русски; имена skills, commands, файлов и схем —
по-английски.

Итог должен содержать:

1. компактную master-spec следующей версии workflow;
2. точный список final skills с короткими именами, triggers, inputs, outputs и
   ответственностью;
3. два alternative backend-specific orchestrator skills/flows: `mo-herdr` и
   `mo-omnigent`, каждый использующий native skill, CLI/MCP и session model
   напрямую там, где это возможно;
4. executor goal lifecycle: native Codex `/goal`, проверенные backend-specific
   equivalents/fallbacks, initial goal template, continuation и resume rules;
5. обязательный pre-execution reuse-research skill, формат человеко-читаемого
   раздела spec, первый отдельный commit и lifecycle передачи обновлённой
   read-only spec executor;
6. явное отсутствие обязательного executor skill и карта переноса полезных
   требований текущего `execute-feature` в spec, project instructions, QC и
   review;
7. самостоятельный `mo-review`, вызываемый и orchestrator, и пользователем без
   полного feature run;
8. минимальный model-discovery/settings design и ненавязчивый model upgrade
   flow;
9. правила получения полного последнего сообщения worker/reviewer;
10. Makefile/task-runner discovery и setup protocol;
11. классификацию console smoke, agentic benchmark и browser E2E с условной
   tester role;
12. review и E2E lifecycle, включая минимальную защиту от проверки разных
   revisions;
13. recovery flow после ручного перезапуска оркестратора/перезагрузки на уровне
    самостоятельного восстановления по Git, spec/task и native sessions;
14. простой project knowledge layout и lifecycle durable knowledge;
15. architecture instruction contract для `AGENTS.md`/`CLAUDE.md` и явный
    architecture/necessity lens reviewers;
16. purpose contract, сохраняющий смысл GRACE, включая overloads;
17. optional `mo-watchdog` design с baseline `1:1`;
18. per-backend context/cache/compaction capability analysis и fallback rules;
19. PATH-wrapper/permission contract без собственного approval runtime;
20. минимальный reflection flow, user-owned follow-up и durable code rationale
    для осознанно отклонённых substantive findings;
21. QC/tool research с предпочтением готовых linters/plugins, включая отдельные
    Python и TypeScript profiles (`typecheck`, `lint`, `test`, aggregate QC);
22. distribution layout для APM/skills без `install.sh`/`update.sh`;
23. tooling audit с `keep/replace/delete/defer` решениями;
24. implementation/migration plan без backward-compatibility constraints;
25. decision ledger и явно rejected/deferred alternatives;
26. pre-mortem против повторного появления wrapper/control-layer bloat.

Спецификация должна быть implementation-ready, но не должна заранее требовать
реализацию собственных CLI, state machine или JSON protocols. Любая такая часть
появляется только после отдельного доказательства необходимости.

## Критерии качества результата

- Пользователь может объяснить весь workflow без перечисления десятков
  внутренних commands.
- Агент может отклониться от happy path и использовать полный native CLI, не
  переписывая proxy wrapper.
- Одна и та же methodology доступна через отдельные Herdr и Omnigent
  skills, но ни один из них не проходит через общий executable adapter только
  ради унификации названий.
- Вызов `mo-herdr` без аргументов приводит к понятному вопросу о новой или
  текущей работе.
- Codex executor с большой spec получает native `/goal` с полным outcome,
  constraints и verification criteria; activation goal доказана выбранной
  surface, а не только присутствием строки `/goal` внутри обычного prompt.
- Executor не читает и не обязан помнить methodology skill; обязательные
  требования приходят через spec/task, project instructions и проверяемый
  outcome.
- Отдельный CLI instance до реализации исследует готовые решения, записывает
  выбор в специальный раздел spec и отдельный первый commit; reuse decision
  видят executor и reviewers.
- `mo-review` можно запустить напрямую после быстрого fix без создания full run
  state и без обязательного E2E lifecycle.
- Backend без native goal mode использует явно описанный weaker fallback, и
  orchestrator распознаёт premature idle вместо принятия частичного результата.
- Ручной restart оркестратора является поддержанным обычным сценарием.
- После reboot новый orchestrator способен восстановить ход работы по реальным
  Git/spec/session фактам либо задать точный вопрос пользователю; exact replay
  старого управляющего context не обещается.
- Herdr/Omnigent запускают agent commands через пользовательский `PATH` и
  не обходят локальные permission wrappers.
- Для каждого backend честно описаны доступность context/cache signals и
  fallback при их отсутствии.
- Полные reviewer messages не теряются из-за terminal truncation.
- Reviewers проверяют purpose/knowledge и задают архитектурный вопрос «зачем?».
- Make/project commands обнаруживаются и переиспользуются до создания новых.
- TypeScript project получает понятные native `typecheck`, `lint`, `test` и QC
  commands; runtime tests не выдаются за typecheck, а выбор ESLint/Oxlint и
  `node:test`/Vitest обоснован типом проекта и уже существующим stack.
- Простая console E2E не требует отдельной tester session; browser/benchmark
  получают отдельного agent tester.
- Model choice обычно подтверждается одной короткой репликой, а полный catalog
  показывается только по запросу или при вероятном meaningful upgrade.
- Число обязательных user attention gates минимально и каждый имеет конкретное
  решение, которое нельзя безопасно принять автоматически.
- Существенный повторяемый failure оставляет короткий actionable follow-up, а
  не исчезает вместе с session; брать его в работу решает пользователь.
- Осознанно сохранённая спорная конструкция содержит durable `why` рядом с
  кодом, если без него будущий reviewer снова потеряет контекст.
- Каждый оставшийся custom script имеет конкретное независимое назначение.
- Удаление state/CLI не маскирует неразрешённый hard requirement: потерянная
  гарантия названа явно и принята осознанно.
- Migration plan позволяет удалить лишний код, а не консервирует его через
  compatibility adapters.
- Верхнеуровневые business/glossary/todo docs легко найти и читать.
- Skill bundle устанавливается стандартным package manager без собственных
  install/update scripts.
- Новая спецификация заметно короче и проще текущей, сохраняя основной смысл:
  сильный executor, независимые reviews, E2E и завершение только после реальной
  проверки результата.

## Уточнения после approach/pre-mortem

- Paseo исключён из текущей итерации; `-orchestrate-` не используется в именах.
- Final backend skills называются `mo-herdr` и `mo-omnigent`.
- `mo-setup` также инициализирует knowledge/docs layer, `AGENTS.md`/`CLAUDE.md`,
  проверяет PATH wrappers Claude/Codex, workspace trust и hook availability.
- Wrapper permission bypass не подменяет нативное принятие Claude workspace
  trust и не должен автоматически мутировать приватную `~/.claude.json`.
- `mo-herdr` обязан извлекать полное последнее завершённое сообщение Claude,
  Codex и OpenCode через Herdr agent read/scroll surfaces. Он находит обе границы
  последнего turn и копирует весь непрерывный интервал; provider session
  JSONL/SQLite/hooks не являются штатным или fallback интерфейсом.
- Отдельный verdict file, `mktemp`, nonce и completion marker не используются:
  orchestrator копирует authoritative full response прямо в следующий prompt.
- В Herdr 0.8.0 `--lines N` возвращает последние N rendered rows, а не native
  `from/to` range. Интервал выделяется из увеличиваемого окна либо собирается из
  последовательных `visible` окон при Herdr-controlled alternate-screen scroll;
  между окнами требуется overlap без пропусков.
- Локально подтверждено, что `opencode export` 1.18.10 обрезает длинные sessions,
  поэтому он не используется как fallback для `mo-herdr`.
- `mo-reuse` делает по умолчанию три адаптивных search rounds. Каждый round
  показывает агенту первую страницу GitHub результатов по языкам проекта,
  отдельный Rust search и native registry search каждого ecosystem. GitHub
  сортируется по stars; registry popularity используется только если она реально
  доступна. Rust оценивается и по наличию/стоимости bindings.
- Любой новый candidate SHA инвалидирует все gates.
- Executor никогда не меняет/удаляет spec; retirement, если понадобится, —
  отдельная операция.
- Watchdog admission решается ранним live spike. Если skill-only next-turn loop
  не работает, минимальный state-free 1:1 `.mjs` helper входит сразу, а не после
  production failure.

## Финальные уточнения пользователя

Этот раздел заменяет противоречащие ему более ранние требования задания:

- project QC и короткий smoke выполняют executor и/или reviewers там, где это
  полезно; отдельная orchestration-фаза и отдельная роль для них не обязательны;
- direct `mo-review` запускается в той же coding session, которая сделала
  небольшой fix: session совмещает orchestrator с executor, запускает двух
  независимых reviewers, сама исправляет замечания и повторяет review до их
  исчезновения;
- `AGENTS.md` и `CLAUDE.md` должны быть byte-for-byte идентичными; provider CLI
  читает свой project-instruction file сам, поэтому orchestrator не обязан
  вручную передавать оба файла в prompt;
- оба instruction files требуют записывать в `docs/backlog.md` всё, что по любой
  причине отложено, не сделано, заблокировано или оставлено неисправленным;
  прежнее имя `docs/todo.md` больше не используется;
- `mo-reuse` не запускается автоматически и не является обязательной стадией:
  пользователь вызывает его сам, либо orchestrator предлагает его, если в spec
  ещё нет reuse research;
- reviewer output не содержит обязательных полей `CANDIDATE`/`WORKTREE`; каждое
  замечание обязано содержать concrete evidence, impact и ожидаемое исправление.

После внесения этих уточнений master-spec считается готовой и утверждённой
пользователем.
