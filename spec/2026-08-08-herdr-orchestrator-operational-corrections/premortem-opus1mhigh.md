## Framing before conclusions

Every scenario below has to be judged against three structural facts this design deliberately accepts. First, the orchestrator is the only component that holds run state (candidate ID, gate states, round history), and the contract forbids a state store, registry, or run file — so that state lives exclusively in one agent's volatile context. Second, essentially all of the new behaviour is prose in Markdown skills, while the deterministic gate (`mo-qc`) can only compare bytes, diff a generated tree, and grep authored text; every behavioural rule in §1, §3, §5, and §6 is enforced by the same agent it constrains, with the E2E evidence in §11 largely self-attested. Third, the design closes every escape hatch it identified as unsafe (headless review, verdict files, sentinels, nonces, ambient SDK, default-branch fallback) without adding a bounded degradation path, so any failure inside a mandatory path has only one exit: repeat, or `needs_attention`. The failure modes worth naming are the ones that fall out of those three facts rather than out of any individual rule being wrong.

## Scenario 1 — The relay eats the orchestrator's own memory, and recovery makes it worse

**What happened.** On a moderately large feature the run reaches review round two. Reviewer A emits four batches, reviewer B three, each up to the conservative 180-row limit, and each is copied verbatim into the executor. The orchestrator's context auto-compacts partway through. After compaction it no longer holds which gates were green for the current object ID, or which batch of reviewer B had already been forwarded. Following §6 ("unknown gates for the current commit are repeated") it re-runs both reviews of the same frozen candidate — producing another seven batches of relay traffic, another compaction, another repeat. The user finds a run that has been "reviewing" the same SHA for hours, with duplicate findings pasted into the executor two and three times.

**Why it happened.** §1 says the orchestrator's "durable context contains only actor names, lifecycle state, current candidate ID, gate states, and short blockers" and that it "discards" relayed chunks from its working summary. That is not a property an agent can have: a transcript is append-only, and every byte of every relayed batch stays in it until a lossy compaction removes exactly the wrong things. The design simultaneously made the orchestrator the highest-volume text pipe in the system and its only memory, then forbade the one mechanism (any persisted run state) that would let it survive its own throughput. The clarification "its context must not be filled with large documents" was honoured for specs and code and then violated by review transport, which is the largest document stream in the workflow.

**What would have prevented it.** Make run state reconstructible from durable external facts rather than from the orchestrator's memory — for example, deriving gate status from what is already observable (branch tip object ID plus per-actor session transcripts addressed by round), so a compacted or restarted orchestrator re-reads rather than re-runs. Alternatively, keep the relay out of the orchestrator's context entirely: an untracked, worktree-local findings file written by the reviewer and read by the executor is not the rejected "verdict file with a completeness sentinel" — it is a volume decision, and the design conflated the two when it rejected them together. At minimum, cap total relayed volume per round and treat exceeding it as a named condition rather than as ordinary transport.

## Scenario 2 — A verified SHA that does not implement the task

**What happened.** A run completes cleanly: executor settles, declares `CANDIDATE` with `QC: passed`, `SMOKE: not-applicable`, `E2E: not-applicable`, worktree clean, declared ID equals `git rev-parse HEAD`. Two reviewers from different vendors return "no further findings remain". The orchestrator reports one full object ID. The user opens the branch and finds a third of the spec unimplemented — the executor read the task, silently scoped it down, and reported completion honestly against its own reduced scope. Nothing in the run was violated.

**Why it happened.** The firewall removed spec access from the orchestrator (correctly, per the clarification) but never reassigned the spec-conformance duty to anyone. §1 gives the executor "locating and reading the complete task" and "deciding and reporting QC, deterministic smoke, and E2E applicability" — the author grades its own scope. §5 gives reviewers "independent criticism and technical adjudication" of the candidate, with no stated obligation to read the task and check coverage, and no requirement that a `not-applicable` declaration be confirmed by anyone. §4 is explicit that the orchestrator "verifies only metadata" and "does not assess the checks". So the sole cross-check between intent and result is the executor's own judgement, and the compact handoff format is designed to make that judgement unauditable by construction.

**What would have prevented it.** Name spec conformance as an explicit reviewer gate: pass the task path (not its contents) to both reviewers and require each verdict to cover whether the candidate implements the declared scope, with `E2E: not-applicable` and `SMOKE: not-applicable` treated as claims a reviewer must confirm rather than as facts the orchestrator forwards. That keeps the orchestrator ignorant while restoring an independent reader of the spec — which is what the firewall actually requires, as opposed to no reader at all.

## Scenario 3 — The transport-completeness gate livelocks, and the human gets nannied anyway

**What happened.** With a real provider TUI, the 180-row conservative limit means almost every review is multi-batch, and the §5 step-3 proof (prompt boundary, finished response, lower settled boundary, continuous order, row cap did not hide history) fails intermittently on repaint. Each failure is `UNKNOWN`, and the prescribed remedy is "request a fresh, shorter re-evaluation of the same frozen candidate". The reviewer, re-evaluating from scratch, emits a slightly different finding set each time. There is no retry budget and no convergence criterion anywhere in the design, so rounds accumulate. Eventually the orchestrator surfaces a `needs_attention` that says, in effect, "the reviewer's output could not be read" — the user is interrupted for a transport defect, which is exactly the babysitting the original report asked to eliminate.

**Why it happened. ** The design promoted transport reliability to a gate condition ("a gate whose full verdict cannot be read is `unknown` and is repeated", "there is no partial pass") while rejecting every mechanism that would make completeness cheap to establish — sentinels, footers, verdict files, headless retrieval. §11 acknowledges the limit must come from fixtures, but §5 ships a guessed number (180) as the starting point and defers the evidence. The result is a mandatory path with a probabilistic failure rate, no bounded retry, and no permitted alternative channel. The `UNKNOWN`-and-repeat rule is a stricter cousin of the original waiting bug: a loop whose exit condition is not guaranteed to occur.

**What would have prevented it.** Establish the compact-turn limit from recorded fixtures *before* the review gate depends on it, and give the transport a bounded budget — N re-evaluation attempts per batch, after which the design permits a named, still-visible degraded channel (the reviewer's own session writing an untracked file, retrieved by path) rather than escalating to a human over a rendering artefact. Separately, add a non-convergence condition: a round count or a repeated-finding signal that becomes `needs_attention` with a *process* explanation, not a transport one.

## Scenario 4 — The bundled catalogue answers the wrong question, and vendor diversity silently lapses

**What happened.** `mo-models.mjs` bundles the pinned Claude Agent SDK and reliably enumerates models — the original complaint is fixed. Months later the pinned SDK version drifts from the installed system CLI, or `supportedModels()` returns identifiers the user's current subscription tier cannot actually run. Preflight validates the saved role preference against that catalogue, the model looks available, the session starts, and the first turn fails on entitlement. §7 says a saved-model miss falls back to "the native configured default … report one compact status line, and do not rewrite preferences" — so the reviewer route quietly collapses onto the same vendor as the executor. The run still produces two reviews and one object ID; the different-vendor requirement, which §7 says makes verified completion impossible when unmet, was never re-evaluated after the fallback.

**Why it happened.** The design treats "enumerable in the catalogue" as equivalent to "runnable on this subscription", and it makes catalogue-driven fallback non-blocking (one status line) even though the same section states that single-vendor operation forecloses verified completion. Nothing deterministic notices the drift: §7's own gate checks byte-identical builds, isolated loading, and absence of runtime package lookup — none of which observes what the SDK returns — and the live `supportedModels()` check is explicitly demoted to an agentic fixture. So the one class of error the bundle was meant to eliminate (a wrong or unverified model claim) reappears as a silent downgrade rather than an honest gap.

**What would have prevented it.** Separate enumeration from entitlement: treat first-turn failure as a catalogue-invalidating event, and re-evaluate the vendor-diversity constraint *after* every fallback rather than only at preflight, escalating to `needs_attention` when the fallback collapses vendor diversity. Pin the SDK against an asserted contract (shape and non-emptiness of the returned catalogue) that a deterministic test can check offline, so drift surfaces at build time rather than mid-run.

## Scenario 5 — The firewall is prose, so it erodes and nothing detects the erosion

**What happened.** Over months, runs quietly regress toward the reported bugs. Because §2 requires the interface be "discovered from its current help/schema rather than blindly copying stale CLI flags", different runs discover different operations; on some Herdr versions the atomic prompt operation is harder to find than `send-keys`, and an orchestrator resolves the ambiguity by writing text and keys separately — the missed-Enter bug returns. Another run, blocked on an ambiguous reviewer finding, opens the diff "just to route the finding correctly", which is exactly the behaviour the user reported. The user notices only by watching panes. `make mo-qc` stays green throughout, because its behavioural check is a grep for forbidden headless commands in the authored skill text — and the authored text was never wrong.

**Why it happened.** §1 encodes roughly twenty prohibitions as prose obeyed by the agent they constrain, and §11 assigns their verification to agent-run E2E: "orchestrator command history stays inside the role firewall" is the orchestrator's own transcript, judged by an agent, on a run that has every incentive to be judged complete. Meanwhile §2's semantic-not-syntactic rule — sound as protection against stale flags — removes the one thing a deterministic check could anchor on, since there is no fixed command string to assert. The design's two enforcement surfaces are therefore a static grep over text that is correct by construction, and self-attestation.

**What would have prevented it.** Anchor compliance to an artefact the orchestrator does not author: have a second actor (the reviewer already on hand, or the existing optional watchdog) audit the orchestrator's actual command history and pane transcript against the firewall list, and make that audit a gate rather than a narrative claim. For the interface-discovery problem, record the discovered operation names per Herdr version as a fixture the run reads and asserts against, so an unexpected substitution (`send-keys` for a prompt, a down split for a right split) is a detectable deviation instead of a judgement call the agent makes silently each run.

## The common thread

Four of these five failures share one root: this design corrected the *content* of the agent's behaviour (don't read the spec, don't judge findings, don't wait on a predicted SHA, don't ask menus) but left the *enforcement and state* model unchanged — one agent, one context, prose rules, no persisted run state, and no bounded budgets anywhere. The original waiting bug was not really about a bad predicate; it was about an unbounded loop with no external check. The design fixes that specific predicate and then reintroduces the same shape in review retry (§5), round convergence (§5–6), and gate re-verification after context loss (§6). Adding two things — a durable, externally reconstructible notion of "which gates hold for this object ID", and an explicit budget on every repeat-until-clean loop — would remove the mechanism behind Scenarios 1, 3, and much of 5, without introducing the orchestration daemon or state store the contract forbids.
