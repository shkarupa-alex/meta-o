Оба исследующих агента вернулись; вместе с полным прочтением `my-opinion.md`, `sdd-issues.md`, `my-memory-layers-scratchpad.md` и GRACE у меня достаточно материала. Прежде чем излагать дизайн, зафиксирую рамку, в которой он обязан оставаться, потому что именно она, а не абстрактная «правильность», определяет каждое решение ниже.

Ключевое напряжение задачи такое. С одной стороны — жёсткие ограничения автора: один полный процесс без режимов; тонкий оркестратор, который не читает код; сильный исполнитель со свободой пути, но без права урезать объём; обязательное кросс-ревью на другом вендоре и отдельный E2E; неизменяемая feature-спека как вход; бизнес-слой как верхняя точка истины; purpose механически обязателен для каждой сущности; работа без CI; ядро не зависит от CLI и от Herdr/Omnigent; не писать новый runtime. С другой стороны — уроки `sdd-issues.md` (спека-ископаемое, моделирование ради моделирования, harness как самоцель, false precision, семантический fan-out, потеря человеческого внимания) и уроков `Ouroboros` (дерево `epic/feat/task-NNN`, markdown-галочки, одноразовые субагенты с 4–7-кратным перечитыванием, gate-файл-в-gate-файл), которых надо избежать. Всё, что я предлагаю, должно защищать инварианты автора **механически и через независимую критику**, а не через ритуал, который исполнитель «помнит» сквозь компакции. Ниже — целостный дизайн, затем обязательная критика слабых мест самого автора.

# Предложение: методология и toolkit `meta-o`

## 1. Краткое резюме подхода

Методология `meta-o` — это тонкий долгоживущий оркестратор поверх Herdr/Omnigent, который ведёт одну неизменяемую feature-спеку через детерминированный конечный автомат «реализация → чередующиеся контуры кросс-ревью и E2E → сходимость на одной Git-ревизии», где все обязательные требования вынесены из памяти исполнителя в **три внешних механических гейта** (линтеры code-health + purpose/anchor-lint, независимые ревьюеры с коротким rubric, отдельный E2E-тестировщик). Живой слой знаний — это компактная grep-цепочка `business (§B-*) → architecture (§A-*) → module → symbol`, синхронизируемая пропорционально реальным изменениям кода, плюс эфемерные decision-log и review-findings и компактный verification-state; старые спеки после интеграции удаляются из поискового контура, а история остаётся в Git. Инструментальный слой — набор тонких skills-«кубиков» и standalone-JS-скриптов, поставляемых вместе, при этом ядро говорит с сессиями через один абстрактный `SessionAdapter`, чтобы смена backend меняла адаптер, а не методологию.

## 2. Структура поставки: master-spec и подспеки

Я предлагаю разложить систему на master-spec и шесть implementation-ready подспек. Каждая самодостаточна и имеет собственный Definition of Done; между собой они связаны только через машинные контракты (JSON-схемы и интерфейсы), а не через прозу.

| Документ | Назначение | Основной машинный контракт |
|---|---|---|
| `master-spec.md` | Принципы, роли, инварианты, глоссарий, карта эскалаций, границы ответственности, ссылки на подспеки | `RunState`, taxonomy эскалаций |
| `subspecs/lifecycle.md` | Конечный автомат одной feature, гейты, критерии остановки, failure/recovery | `RunState`, `Phase`, transition table |
| `subspecs/knowledge-layer.md` | Слои знаний, якоря, правила sync, decision-log, verification-state, retirement старых спек | anchor-grammar, `VerificationRecord`, `DecisionLogEntry` |
| `subspecs/orchestration.md` | Сессии, `SessionAdapter`, протокол событий, model-set, backend-адаптеры, watchdog | `SessionAdapter`, `SessionEvent`, `WatchdogConfig` |
| `subspecs/code-health-qc.md` | Механические проверки, purpose-lint, anchor-check, contract-sweep, пороги, размещение гейтов | `HealthReport`, `pyproject.toml` схемы |
| `subspecs/review-e2e.md` | Rubric, контракт findings, разрешение споров, чередование, завершение | `Finding`, rubric, alternation-инвариант |
| `subspecs/skills-tooling.md` | Интерфейсы skills, install/update-скрипт, TS→JS сборка, CLI | skill-I/O-контракты, CLI-команды |

Один codename для методологии в прозе — **HELIX** (две нити контроля — review и E2E — сходятся на одной ревизии); toolkit, plugin-namespace и CLI называются `meta-o`.

## 3. Архитектура и компоненты

### 3.1. Роли (каждая — отдельная сессия backend)

- **Orchestrator** — тонкий управляющий контекст. Держит `RunState`, ведёт конечный автомат, отвечает на технические вопросы исполнителя, передаёт findings адресно, разрешает споры, классифицирует сбои, эскалирует. **Не читает код.** Живёт дольше остальных (целевой бюджет контекста конфигурируемый, иллюстративно ≤250k). Его единственный «тяжёлый» вход — компактный управляющий skill `meta-o:orchestrate`.
- **Implementer** — сильная модель в goal-сессии. Свобода инженерного пути, запрет на тихое урезание объёма. Ведёт собственный маленький progress-файл (не task-дерево). Может порождать собственные субагенты для изолированных задач (это его дело, а не протокол методологии).
- **Reviewer-A (same family)** и **Reviewer-B (cross-vendor, обязательно другой вендор)** — независимые сессии с чистым по отношению к реализации контекстом на первом проходе; сохраняются между итерациями; заменяются свежими при накоплении bias.
- **Tester** — отдельная сессия E2E: сборка, docker, миграции, тесты, браузер, сценарии, evidence.

Оркестратор **не** является ещё одним код-агентом: когда для решения спора нужно понять код, он порождает эфемерный `adjudicator`-субагент (read-only, видит только спорный регион + пункт спеки + оба аргумента) и получает структурный вердикт — сам в код не входит.

### 3.2. Тонкое ядро и абстракция backend

Ядро (skills + скрипты + протокол) не знает про конкретный CLI (Claude/Codex/OpenCode) и про конкретный meta-framework. Единственный шов — интерфейс `SessionAdapter` (см. §4.1). Herdr и Omnigent — две реализации адаптера. **Мы не пишем runtime**: spawn/resume/доставка событий/управление сессиями — ответственность backend. Наши добавки поверх backend, не нарушающие этого правила: (1) **reconciliation-петля** оркестратора (периодический `status()` в сравнении с ожидаемым `turnSeq`) как страховка от потерянного события завершения turn — это критический дефект по мнению автора; (2) внешний **watchdog** для восстановления после лимитов.

Заимствую из сравнения SDD-инструментов идею **LLM-as-relay с внешним payload**: оркестратор передаёт findings и вопросы не «втягивая» чужой контекст в свой, а по ссылке на файл/структуру (`context_files`, `result_dir`) — это прямо реализует принцип «оркестратор не копается в коде».

### 3.3. Слой skills (тонкие «кубики» + namespace-роутеры)

Заимствую из GSD идею **namespace-роутеров**: тонкие входные skills, а не один большой ритуал.

| Skill | Кто вызывает | Роль |
|---|---|---|
| `meta-o:orchestrate` | Orchestrator | Управляющий протокол: автомат, эскалации, retry-классы |
| `meta-o:review-loop` | Orchestrator / standalone | Самостоятельный кубик кросс-ревью (можно вызвать после внешнего быстрого фикса или на документе) |
| `meta-o:e2e-verify` | Tester | Протокол E2E + запись `verification-state` |
| `meta-o:implement-goal` | Orchestrator → Implementer | Шаблон goal (жёсткая формулировка «сделать всё, не урезать»), не тяжёлый ритуал |
| `meta-o:knowledge-sync` | Implementer/Reviewer | Правила обновления цепочки `§B→§A→module→symbol` |
| `meta-o:reuse-scan` | Orchestrator (стартовая опция) | Поиск готовых библиотек/проектов до кодинга |

Критично (урок GRACE-3809 и самого автора): **ничего обязательного не прячется только в необязательном skill**. Skills — это `guide`; `gate` — это линтеры и ревьюеры; `goal` — это спека и жёсткая цель. Разделение GOAL/PROTOCOL/GUIDE явно маркируется.

### 3.4. Слой скриптов (standalone JS, поставляются со skills)

Исходники на TypeScript, компилируются в автономный JS без runtime-зависимостей. Единый CLI `meta-o`:

- `meta-o qc` — агрегатор всех механических проверок → `HealthReport` (единый JSON на всех языках).
- `meta-o purpose-lint` — наличие purpose + ссылки у каждой сущности.
- `meta-o anchor-check` — целостность §-цепочки (мёртвые/дублирующие/сиротские якоря, `§*-TODO-*` в merged-коде, прямые ссылки из кода на `§B-*`).
- `meta-o contract-sweep` — механический анти-дрейф: сверка ссылок docstring с реальными сигнатурами/импортами/тестами.
- `meta-o verify-state` — чтение/запись `verification-state.json`.
- `meta-o watchdog` — внешний демон восстановления.
- `meta-o models` — показать/подтвердить/сохранить model-set.

Языко-специфичные анализаторы (ruff/pylint/radon/import-linter для Python) вызываются как подпроцессы; JS их нормализует. Если анализатор не установлен — `meta-o qc` не «молча зелёный», а рапортует отсутствие и эскалирует (реальная несовместимость → агент эскалирует, проект версию не пинит).

## 4. Ключевые интерфейсы и модели данных

### 4.1. `SessionAdapter` (шов backend) и протокол событий

```ts
type Role = "orchestrator" | "implementer" | "reviewer_a" | "reviewer_b" | "tester" | "adjudicator";
type SessionState =
  | "running" | "awaiting_input" | "turn_complete"
  | "transient_error" | "quota_exhausted" | "external_block" | "dead";

interface SpawnOpts { role: Role; vendor: string; model: string; cwd: string; initialPrompt: string; }

interface SessionStatus {
  id: string;
  state: SessionState;
  turnSeq: number;            // монотонно растёт с каждым завершённым turn
  lastTurnAt: string;         // ISO
  contextTokens?: number;     // если backend умеет; иначе оценка ядром
  cacheLikelyWarm?: boolean;  // по времени последнего turn + провайдерное окно
  pendingQuestion?: string;   // текст вопроса/эскалации, если awaiting_input
}

interface Ack { deliveryId: string; acceptedAtTurnSeq: number; }

type SessionEvent =
  | { kind: "turn_complete"; id: string; turnSeq: number }
  | { kind: "awaiting_input"; id: string; question: string }
  | { kind: "error"; id: string; class: ErrorClass }
  | { kind: "dead"; id: string };

type ErrorClass = "retryable" | "quota_exhausted" | "external_block" | "unknown";

interface SessionAdapter {
  capabilities(): Promise<AdapterCaps>;                 // что backend реально умеет
  spawn(opts: SpawnOpts): Promise<string>;              // -> sessionId
  send(id: string, msg: string, o?: {expectTurn?: boolean}): Promise<Ack>;
  status(id: string): Promise<SessionStatus>;
  events(): AsyncIterable<SessionEvent>;                // push; reconciliation дублирует pull
  interrupt(id: string): Promise<void>;
  requestSummary(id: string): Promise<string>;          // предкомпакционное резюме
  compact(id: string): Promise<void>;
  kill(id: string): Promise<void>;
  resume(id: string): Promise<SessionStatus>;           // после падения/перезагрузки
}

interface AdapterCaps {
  pushEvents: boolean; reportsContextTokens: boolean;
  canCompact: boolean; canResumeAfterReboot: boolean;
}
```

**Ошибки:** `SessionNotFound`, `SpawnFailed`, `DeliveryUnacked`, `BackendUnavailable`, `CapabilityUnsupported`. Деградация: если `pushEvents=false`, оркестратор целиком полагается на reconciliation-петлю (`status()` каждые N сек); если `reportsContextTokens=false` — оценивает тяжесть контекста по числу turn и размеру транскрипта. **Идемпотентность возобновления:** перед повторным `send("продолжай")` оркестратор проверяет `turnSeq`; если он вырос с момента последней доставки — предыдущий ход выполнился, повтор не отправляется (защита от двойного продолжения).

### 4.2. `RunState` и конечный автомат feature

```ts
type Phase =
  | "INIT" | "REUSE_SCAN" | "KNOWLEDGE_PROJECTION"
  | "IMPLEMENTING" | "IMPL_READY"
  | "REVIEW" | "REVIEW_FIXING" | "REVIEW_CLEAN"
  | "E2E" | "E2E_FIXING" | "E2E_CLEAN"
  | "DONE"
  | "RETRY_WAIT" | "QUOTA_WAIT" | "PAUSED_EXTERNAL" | "ESCALATED" | "FAILED_INFEASIBLE";

interface ModelRef { vendor: string; model: string; }
interface ModelSet {
  orchestrator: ModelRef; implementer: ModelRef;
  reviewer_a: ModelRef;   // same family as implementer
  reviewer_b: ModelRef;   // MUST differ in vendor from implementer
  tester: ModelRef;
}

interface RunState {
  run_id: string;
  spec_ref: string;            // path | url; неизменяемая
  spec_locator_kind: "repo_path" | "external_untracked";
  models: ModelSet;
  handoff_file?: string;       // опциональный компактный handoff, выбор пользователя при старте
  phase: Phase;
  head_rev: string;            // текущий HEAD
  review_clean_rev?: string;   // ревизия, на которой оба ревьюера подтвердили чистоту
  e2e_clean_rev?: string;      // ревизия, на которой E2E подтверждён
  reuse_scan: "skipped" | "done";
  sessions: Partial<Record<Role, string>>;   // role -> sessionId
  open_escalations: Escalation[];
  retry?: { class: ErrorClass; attempts: number; next_at: string };
  cycle_budget: { review_cycles: number; e2e_cycles: number; max: number };
  updated_at: string;
}
```

**Инвариант завершения (жёсткая констрейнт автора):**
`DONE ⇔ review_clean_rev === e2e_clean_rev === head_rev`.

**Инвалидизация:** любой commit, меняющий *код* (пути по конфигу `code_globs`), обнуляет применимость `review_clean_rev`/`e2e_clean_rev`, не равных новому `head_rev`. Уточнение (моё улучшение): commit, меняющий только *знания/доки* (`doc_globs`) и не трогающий `code_globs`, **не инвалидирует** E2E (поведение не изменилось), но требует дешёвого re-review только diff знаний. Это снимает бесконечное перезапускание тяжёлого E2E из-за обновления `§A-*`.

**Таблица переходов (сокращённо):**

| Из | Событие | В |
|---|---|---|
| INIT | model-set подтверждён | REUSE_SCAN (если включён) → иначе KNOWLEDGE_PROJECTION |
| KNOWLEDGE_PROJECTION | спроецированы §B/§A-TODO | IMPLEMENTING |
| IMPLEMENTING | implementer: `IMPL_READY` + `meta-o qc` PASS | IMPL_READY |
| IMPLEMENTING | вопрос TECH_SIMPLE | оркестратор отвечает, остаётся IMPLEMENTING |
| IMPLEMENTING | вопрос BUSINESS_IMPACT / SPEC_CONTRADICTION | ESCALATED |
| IMPLEMENTING | спека нереализуема | FAILED_INFEASIBLE (стоп+эскалация) |
| IMPL_READY | запуск двух ревьюеров | REVIEW |
| REVIEW | есть подтверждённые findings | REVIEW_FIXING |
| REVIEW | оба чисто на `head_rev` | REVIEW_CLEAN (set `review_clean_rev=head_rev`) |
| REVIEW_FIXING | исполнитель зафиксил, новый `head_rev` | REVIEW (те же ревьюеры перепроверяют) |
| REVIEW_CLEAN | первый тяжёлый E2E | E2E |
| E2E | найдены проблемы | E2E_FIXING |
| E2E | чисто на `head_rev` | E2E_CLEAN (set `e2e_clean_rev=head_rev`) |
| E2E_FIXING | зафиксил, новый `head_rev` | E2E (повтор), при этом `review_clean_rev` устарел |
| E2E_CLEAN | `review_clean_rev≠head_rev` | REVIEW (снова) |
| E2E_CLEAN | `review_clean_rev===head_rev` | DONE |
| * | `429`/overload | RETRY_WAIT → назад |
| * | лимит подписки | QUOTA_WAIT → (watchdog) → назад |
| * | внешняя блокировка | PAUSED_EXTERNAL → (человек) → назад |
| REVIEW/E2E | `cycle_budget.max` превышен | ESCALATED (анти-loop) |

**Анти-loop (урок GRACE-3695):** спека — неизменяемый acceptance-oracle; исполнитель не может ослабить критерии; `cycle_budget` ограничивает число итераций до эскалации; при повторяющемся споре форсируется `adjudicator`; «вкусовые» findings не блокируют.

### 4.3. Слой знаний: якоря, слои, sync

**Грамматика якорей (grep-friendly, machine):**
```
anchor      := "§" layer "-" TOPIC "-" NN
layer       := "B" | "A"
TOPIC       := [A-Z][A-Z0-9]*         (например CONTEXT, TIME, ENV, OUTCOME)
NN          := [0-9]{2,}
todo-anchor := "§" layer "-TODO-" TOPIC "-" NN
grep-all    := rg -o '§[AB](-TODO)?-[A-Z0-9-]+' docs src tests
```

**Слои (переработка scratchpad с использованием идей GRACE, без XML):**

1. **L1 Business** — `docs/knowledge/business.md`, якоря `§B-*`. Обязательная верхняя истина. Отвечает: какую проблему, для кого, какой результат, **что станет лишним при отказе**. Нельзя описывать модули/классы/функции. Правит человек; агент — пропорционально.
2. **L2 Architecture** — тематические `docs/knowledge/*.md`, якоря `§A-*`. Каждое `§A-*` в обычной прозе называет, какие `§B-*` реализует; фиксирует инварианты, границы, non-goals и «что удалить/упростить при отмене решения». Никаких служебных блоков `Status/Derived from`.
3. **L3 Module purpose** — module docstring. Ссылается только на `§A-*` (одна ссылка вверх), не на L1. Отвечает: зачем модуль, какую часть `§A-*` реализует, граница, что станет мёртвым при отмене решения.
4. **L4 Symbol purpose** — docstring символа (модуль/класс/функция/метод, включая private). Purpose = **причина существования**, не механика. Ссылка на один уровень вверх (module или `§A-*`); дальние ссылки допустимы при нужде.

**Динамическая гранулярность (примирение с GRACE):** одна строка purpose обязательна везде (линтер), но расширенные поля (invariants, rationale, отвергнутые альтернативы, `SFT_HINT`) добавляются только там, где будущий агент правдоподобно выберет неверное поведение; их смысловую адекватность проверяет ревьюер, а не линтер.

**Правила sync (`meta-o:knowledge-sync`):** объём дописанного текста пропорционален объёму изменений кода (правило автора против «10 абзацев на 1 строку»). Перед работой: `rg §B` → `rg §A` → `rg §A в src/tests` → проверить цепочку. После: обновить `§B` только если изменился бизнес-смысл; `§A` — если изменилось решение/инвариант/граница; module/symbol docstrings затронутых сущностей. **Запрет:** будущий code-level contract не пишется заранее в docstring существующего кода.

**Эфемерные артефакты (не ledger):**
```ts
interface DecisionLogEntry {   // run/decision-log.md, живёт только в течение feature
  id: string; ts: string;
  kind: "orchestrator_answer" | "tech_decision" | "reuse_choice";
  question?: string; decision: string; rationale: string;
  durable_target?: string;     // §A-*, куда мигрирует устойчивое содержание на DONE
}
interface Finding {            // передаётся оркестратором между сессиями, после закрытия исчезает
  id: string;
  severity: "blocker" | "major" | "minor" | "taste";
  evidence: string;            // конкретно: file:line, repro, diff
  spec_or_risk_link: string;   // пункт спеки ИЛИ инженерный риск
  reviewer: Role; status: "open" | "fixed" | "disputed" | "wontfix_documented";
  resolution?: string;         // при wontfix обязателен in-code комментарий «почему так»
}
```

**Долгоживущий, но компактный verification-state** (`docs/knowledge/verification-state.json`):
```ts
interface VerificationRecord {
  scenario_id: string;    // VP-BS-020
  business_link: string;  // §B-*
  git_rev: string;        // проверенная ревизия
  date: string;           // ISO
  status: "pass" | "fail" | "stale";  // stale выставляется автоматически при git_rev != HEAD

```

**Retirement старых спек:** после DONE устойчивое знание пропорционально интегрируется в `§B/§A/module/symbol`, затем спека удаляется из поискового контура (если это repo_path — удаляется из рабочих путей; провенанс остаётся в Git — урок sdd-issues «историю хранит Git»). `anchor-check` на гейте DONE запрещает `§*-TODO-*` в merged-коде и мёртвые ссылки на удалённую спеку.

### 4.4. Code-health и QC

**`HealthReport` — единый кросс-язычный контракт:**
```ts
interface HealthFinding {
  tool: string; rule: string; severity: "error" | "warn";
  file: string; line?: number; symbol?: string;
  metric?: string; value?: number; limit?: number; message: string;
}
interface HealthReport {
  ok: boolean; language: string; ran: string[];      // какие анализаторы отработали
  missing_tools: string[];                            // отсутствующие → эскалация, не «зелёный»
  findings: HealthFinding[];
  summary: { errors: number; warns: number };
}
```

**Механические проверки (что проверяем):** размер файла, размер функции/метода/класса, число параметров, цикломатическая и когнитивная сложность, глубина вложенности, границы модулей, запрещённые импорты, циклы. Плюс `purpose-lint`, `anchor-check`, `contract-sweep`.

**Конкретная реализация для Python (`pyproject.toml`):**

**Будущие адаптеры (разумная основа):**
- **PHP:** `phpmd` (cyclomatic/npath, ExcessiveClassLength/MethodLength, coupling), `phpstan`/`psalm` (уровень), `deptrac` (слои+циклы), `phpcs` custom sniff для purpose; конфиг в `phpmd.xml`/`deptrac.yaml`.
- **JS/TS:** `eslint` (`complexity`, `max-lines`, `max-lines-per-function`, `max-depth`, `sonarjs/cognitive-complexity`), `dependency-cruiser` (границы+циклы), `eslint-plugin-jsdoc` для наличия docstring; конфиг в `.eslintrc`/`.dependency-cruiser.js`.

**Размещение гейтов — сравнение и решение:**

| Слой | Что | Скорость | Роль |
|---|---|---|---|
| `meta-o qc` | Полный набор + purpose/anchor/contract-sweep | секунды–минуты | **Авторитетный обязательный gate** |
| pre-commit | Быстрое подмножество на changed-files (format, purpose-lint, anchor-check, ruff C901) | <5с | Тесная петля исполнителя |
| pre-push | Полный `meta-o qc` | как qc | Backstop перед share |
| CI | Дубликат `meta-o qc` | — | Опционально |

**Решение и обоснование:** авторитет — `meta-o qc`, вызываемый как гейт автомата (перед REVIEW; ревьюеры и tester перезапускают его же). Он работает без CI (жёсткая констрейнт). pre-commit держим **быстрым**, потому что агент делает много локальных коммитов; тяжёлые проверки там замедлят inner loop и спровоцируют `--no-verify`. pre-push не может быть первичным, т.к. push — только по просьбе пользователя. CI лишь дублирует. Git: агент делает локальные коммиты; push/PR — только по отдельной просьбе.

**Семантика vs механика:** линтер проверяет *наличие* purpose и ссылки; *смысловую адекватность и дрейф* purpose проверяют ревьюеры (пункт rubric). `contract-sweep` ловит механически то, что можно (мёртвая ссылка `§A`, модуль заявляет `§A-X` без связанного `VP-*`), но семантику не берёт.

### 4.5. Review, E2E, завершение

**Короткий единый rubric (порядок анализа свободный):**
1. Соответствие `§B-*` (бизнес-смысл) — приоритет.
2. Соответствие `§A-*` (архитектурные инварианты, границы, связность, циклы, god-файлы).
3. Соответствие спеке и её обязательным пожеланиям (в т.ч. что reuse-находки не проигнорированы).
4. Корректность/безопасность/регрессии.
5. Purpose-дрейф: purpose объясняет причину, не механику; не устарел.
6. Долговременная сопровождаемость: локальность будущих правок, дублирование, временные слои.

**Контракт finding** — см. `Finding` (§4.3): severity + конкретное доказательство + связь со спекой/риском. Все подтверждённые дефекты (включая minor) фиксятся; не блокируют только доказанно вкусовые; wontfix требует in-code комментария «почему так».

**Разрешение споров:** в большинстве — оркестратор (сопоставляет спеку, аргумент ревьюера, ответ исполнителя, других ревьюеров, тесты, принцип production-ready). При нужде понять код — `adjudicator`-проба. Человек — только при отсутствии надёжного технического ответа, продуктовой семантике, необратимости.

**Чередование:** первый тяжёлый E2E — после первого чистого кросс-ревью; далее REVIEW и E2E чередуются; любое изменение кода инвалидирует подтверждение другого контура; DONE по инварианту §4.2. Повторное ревью — те же сессии (дёшево, есть контекст), при накоплении bias — свежие.

**E2E-протокол (`meta-o:e2e-verify`):** собрать, поднять docker/сервисы, применить миграции, тесты/бенчмарки, браузер/сценарии, интеграции; собрать evidence (команды, статусы, ключевые логи, скриншоты) и записать `VerificationRecord`. Из GRACE беру: immutable acceptance-oracle, независимый валидатор, запрет «зелёный статус = успех» без бизнес-evidence, и (опционально) mutation-тесты со скрытыми от генератора мутантами против overfitting.

### 4.6. Watchdog (полностью спроектирован, включается пользователем)

```ts
interface LimitPattern { provider: string; kind: ErrorClass; regex: string; reset_hint_regex?: string; }
interface WatchdogConfig {
  runs: string[];                 // директории RunState нескольких проектов
  poll_interval_sec: number;
  patterns: LimitPattern[];       // версионируемая таблица известных сообщений
  classifier_model?: ModelRef;    // локальная модель для неоднозначных случаев (гибрид)
  wake_command_template: string;  // идемпотентная команда продолжения
  push_notify?: { channel: string };
}
```

**Сравнение вариантов:**
- **Детерминированный скрипт** — дёшев, предсказуем, но хрупок к смене текстов ошибок.
- **Локальная модель (Ollama/LM Studio)** — устойчива к формулировкам, но добавляет вероятностного агента, который тоже надо стеречь.
- **Гибрид (рекомендую):** детерминированный автомат по версионируемой таблице `patterns` для известных состояний; неоднозначный вывод отдаётся маленькой локальной модели **только для классификации** (никогда — для проектного контекста). Watchdog не зависит от исчерпанного лимита оркестратора; сам стережётся ОС-супервизором (`launchd`/`systemd`) — это и есть ответ на «кто стережёт watchdog». Один watchdog обслуживает несколько проектов (список `runs`). Пробуждение идемпотентно: перед `send` проверяет `turnSeq`.

## 5. Ключевые компромиссы

Прежде чем перечислить компромиссы, отмечу принцип, которым я руководствовался при каждом выборе: там, где инвариант автора можно защитить механически (линтер, автомат, git-hook) или независимой критикой (ревьюер/tester/adjudicator), я всегда предпочитаю это ритуалу в памяти агента — потому что именно память сквозь компакции автор считает ненадёжной, и именно артефакт-ради-артефакта `sdd-issues` считает главным ядом.

- **Enforcement вне памяти исполнителя, а не большой обязательный skill.** Цена: нужно строить и поддерживать линтеры/hooks/скрипты (инженерия toolkit). Выигрыш: обязательное переживает компакцию; исполнитель остаётся «художником». Это прямо разрешает конфликт «позвольте творить» ↔ «purpose обязателен везде».
- **Единый `meta-o qc` как авторитет, CI лишь дублирует.** Цена: локальный запуск может быть медленнее централизованного CI-кэша. Выигрыш: работа без CI (констрейнт) и одинаковое поведение у исполнителя/ревьюера/tester.
- **Тонкий оркестратор + adjudicator-проба вместо оркестратора-в-коде.** Цена: лишняя эфемерная сессия на спор. Выигрыш: чистый управляющий контекст на многодневный цикл; меньше риск неверного вердикта вслепую.
- **Динамическая гранулярность purpose (строка везде + расширение по риску).** Цена: линтер не измеряет «достаточность» расширенных полей — это на ревьюере. Выигрыш: нет бюрократии на тривиальных getter’ах (урок GRACE), но трассируемость 100% (констрейнт автора).
- **Знания синхронизируются пропорционально и удаляются из поиска, а не архивируются рядом.** Цена: «пропорционально» — субъективно, нужен явный порог. Выигрыш: нет дрейфа и спека-ископаемого (`sdd-issues`).
- **Единый `SessionAdapter` вместо привязки к Herdr/Omnigent.** Цена: адаптер + reconciliation — дополнительный код. Выигрыш: смена backend меняет адаптер, а не методологию (констрейнт), и страховка от потерянного turn-события (критический дефект по автору).

## 6. Критика решений автора (обязательный раздел)

Для каждого пункта: (1) слабость и отказ; (2) лучший вариант в рамках ограничений; (3) альтернатива, возможно нарушающая исходное решение; (4) отделение hard-констрейнта от пересматриваемого решения; (5) цена/последствия.

### 6.1. Тонкий оркестратор разрешает технические споры «вслепую»
1. **Слабость/отказ:** оркестратор, который принципиально не читает код, при споре ревьюер↔исполнитель выберет более убедительный, но неверный аргумент (автор сам это признаёт). Отказ: закреплён дефект, обе стороны «правы на словах».
2. **Лучший вариант (в рамках):** обязательный `adjudicator` — эфемерная read-only-сессия, видит только спорный регион, пункт спеки и оба аргумента, возвращает структурный вердикт с доказательством; оркестратор решает на доказательстве, не входя в код сам.
3. **Альтернатива (может нарушать):** дать самому оркестратору строго ограниченный, эфемерный, read-only бюджет на чтение спорного diff — нарушает «оркестратор не в коде», зато без лишней сессии.
4. **Констрейнт vs решение:** hard — «оркестратор сохраняет чистый управляющий контекст»; пересматриваемо — «оркестратор *никогда* не касается кода даже точечно».
5. **Цена:** adjudicator — +1 сессия и латентность на спор; прямой доступ оркестратора — риск постепенного раздувания его контекста, который автор считает главной деградацией управления.

### 6.2. Обязательная дисциплина держится на «спека + результат» при запрете обязательного skill
1. **Слабость/отказ:** если purpose/anchor/knowledge-sync не гейтятся механически, исполнитель со свободой пути произведёт большой diff, который поздно упадёт на линтере или всплывёт у ревьюеров → дорогая переделка в конце.
2. **Лучший вариант (в рамках):** сделать эти правила **механическими гейтами** (`meta-o qc` + pre-commit fast-subset), а goal лишь называет их как gate. Дисциплина не зависит от памяти — что и требует сам автор.
3. **Альтернатива (может нарушать):** тонкий детерминированный «protocol-reminder» через harness/pre-commit hook, который на каждом turn/коммите вновь показывает 5 строк обязательных гейтов — формально это «навязанный ритуал», но переживает компакцию.
4. **Констрейнт vs решение:** hard — «обязательное не должно держаться на памяти большого skill сквозь компакции»; пересматриваемо — «исполнителю вообще ничего не напоминать в процессе».
5. **Цена:** механические гейты — стоимость поддержки линтеров; hook-reminder — небольшой шум в контексте против позднего дорогого дрейфа.

### 6.3. Два ревьюера: same-family может быть избыточен
1. **Слабость/отказ:** ревьюер той же модельной семьи коррелирует по ошибкам с исполнителем; риск платить за третью сессию, дублирующую слепые зоны.
2. **Лучший вариант (в рамках):** сохранить обоих, но развести по **линзам**: Reviewer-B (cross-vendor) — бизнес/архитектура/спека; Reviewer-A (same family) — корректность/безопасность/детали реализации, где знакомство с семьёй исполнителя даёт глубину. Разнесение снижает избыточность без потери числа глаз.
3. **Альтернатива (может нарушать):** один cross-vendor ревьюер + усиленный механический второй проход (`contract-sweep` + mutation-тесты) — нарушает «всегда два ревьюера», экономит сессию.
4. **Констрейнт vs решение:** hard — «минимум один ревьюер на другом вендоре» и «независимость ошибок»; пересматриваемо — «ровно два независимых ревьюера-сессии всегда».
5. **Цена:** two-lens — прежняя стоимость, выше отдача; один+механика — дешевле, но риск пропуска классов ошибок, которые ловит только вторая модель.

### 6.4. TODO-проекция спеки в слои знаний в начале feature
1. **Слабость/отказ:** ранняя проекция спеки в `§B/§A` до кода — это тот самый риск `sdd-issues`: false precision и «моделирование ради моделирования»; документация опережает реализацию и дрейфует, а автор к тому же запрещает заранее писать code-level contract.
2. **Лучший вариант (в рамках):** проецировать **только якоря + одну строку намерения** как `§B-TODO-*`/`§A-TODO-*` (не полные контракты, не docstrings), и жёстко гейтить их снятие: `anchor-check` на DONE запрещает `§*-TODO-*` в merged-коде. Это даёт ранние grep-якоря для трассировки, но исключает бюрократию.
3. **Альтернатива (может нарушать):** вообще не проецировать заранее — обновлять `§B/§A` только по факту post-реализации; нарушает гипотезу автора, зато полностью исключает опережающий дрейф.
4. **Констрейнт vs решение:** это гипотеза, а не констрейнт (автор прямо просит не принимать её заранее). Hard рядом — «бизнес-слой обязателен как верхняя истина».
5. **Цена:** лёгкая проекция — минимальный риск дрейфа + ранняя навигация; полный отказ — риск потерять архитектурный фокус «в постановке» до кода.

### 6.5. Асинхронное авто-обновление бизнес-слоя без синхронного gate
1. **Слабость/отказ:** бизнес-смысл — верхняя истина, но агент правит `§B-*` сам, а человек видит diff лишь после workflow или на недельном аудите. Риск: молчаливый семантический fan-out/дрейф именно в самом дорогом слое (`sdd-issues §5,§1`).
2. **Лучший вариант (в рамках):** оставить асинхронность, но добавить механический guard: изменения `§B-*` обязаны попасть в компактный `§B`-diff финального run-report; `anchor-check` запрещает сиротство/мёртвые ссылки; ревьюер обязан проверить `§B`-дрейф (пункт rubric). Человек всё ещё читает diff, но не синхронно.
3. **Альтернатива (может нарушать):** ввести **точечный синхронный ack** человека только на *создание нового* `§B-*` или *смену смысла* существующего (не на `§A` и ниже) — нарушает «не синхронный gate», но защищает самый дорогой слой.
4. **Констрейнт vs решение:** hard — «бизнес-слой обязателен и является верхней истиной»; пересматриваемо — «человек подключается к бизнес-слою только асинхронно».
5. **Цена:** guard-only — минимум трения, остаточный риск позднего обнаружения дрейфа; точечный ack — +редкие человеческие точки против почти нулевого риска бизнес-дрейфа.

### 6.6. Один исполнитель на всю спеку при жёстких лимитах контекста
1. **Слабость/отказ:** для большой brownfield-feature один исполнитель упрётся в «безопасный» контекст (сам автор ставит 250–350k как сигнал) и/или в связность; результат — компакция исполнителя посреди сложного места и тихое недоделывание.
2. **Лучший вариант (в рамках):** не навязывать декомпозицию, но санкционировать паттерн **vertical-slice**: цель формулируется как «реализуй всю спеку срезами `§B`-сценарий за раз, каждый срез доведи до qc-чистоты», плюс исполнителю разрешены собственные субагенты для изолированных частей (его свобода). Это удерживает контекст без task-дерева.
3. **Альтернатива (может нарушать):** ввести лёгкий gate PBS-декомпозиции **только для очень больших спек** (порог по числу `§B`/оценке) — нарушает «без глубокой декомпозиции», зато спасает контекст на гигантских feature.
4. **Констрейнт vs решение:** hard — «один сильный исполнитель, свобода пути, запрет урезать объём»; пересматриваемо — «никакой явной декомпозиции никогда, даже для очень крупной спеки».
5. **Цена:** vertical-slice — почти бесплатно, снижает риск; PBS-gate — возвращает часть SDD-веса, который автор осознанно отвергает.

### 6.7. Удаление старых спек из поискового контура
1. **Слабость/отказ:** «пропорциональная интеграция, затем удаление» — правильная цель, но «пропорционально» неизмеримо; риск удалить спеку раньше, чем знание реально перенесено (потеря провенанса решений).
2. **Лучший вариант (в рамках):** гейт retirement: спека удаляется из путей только когда (а) все её `§*-TODO-*` сняты, (б) `anchor-check` не находит мёртвых ссылок, (в) есть ≥1 `VerificationRecord`, связывающий её `§B-*` с фактом. Провенанс — в Git.
3. **Альтернатива (может нарушать):** держать спеки в отдельном, недоступном агенту хранилище вне репозитория (внешний untracked-контур) вместо удаления — нарушает «удаляется из рабочего контура репозитория», зато сохраняет читаемый людьми провенанс.
4. **Констрейнт vs решение:** hard — «старые спеки не остаются рядом как исторические источники поиска»; пересматриваемо — «их надо именно удалять, а не выносить наружу».
5. **Цена:** гейт — небольшая проверка на DONE; внешнее хранилище — операционные накладные, но нулевая потеря истории.

## 7. Риски и меры

- **Пропущено событие завершения turn (критический дефект по автору).** Мера: push-события `SessionAdapter` **и** reconciliation-петля (`status()`↔`turnSeq`); почти одновременные завершения обрабатываются очередью событий с dedupe по `(id, turnSeq)`.
- **Двойное продолжение хода.** Мера: идемпотентный `send` — проверка `turnSeq` перед повтором; watchdog использует ту же проверку.
- **Оркестратор дошёл до компакции.** Мера: бюджет контекста в `RunState`, компактные статусы вместо логов, передача findings по ссылке (relay-payload), эскалация до опасной границы, а не после.
- **Спека потеряла важное.** Мера: reuse-находки и обязательные пожелания — отдельные пункты rubric; ревьюеры проверяют, что они не проигнорированы. (Полноту спеки методология не валидирует — констрейнт.)
- **Кодовая база растёт быстрее архитектуры.** Мера: блокирующий `meta-o qc` (размеры, сложность, `import-linter` циклы/границы) во время разработки + архитектурный фокус rubric; глобальный аудит вынесен в отдельный инструмент (out of scope).
- **E2E только на словах.** Мера: `VerificationRecord` с проверенной `git_rev` + evidence-ref; immutable oracle; запрет «зелёный = успех».
- **Бесконечный цикл вкусовых findings.** Мера: severity-классификация, `cycle_budget`, taste не блокирует, wontfix с in-code обоснованием.
- **Backend ненадёжен / несовместим.** Мера: `capabilities()` + graceful degradation; отсутствующий анализатор → эскалация, не «зелёный»; skill self-check контракта.
- **Watchdog/оркестратор не проснулись после лимита.** Мера: гибридный watchdog вне лимита оркестратора, под ОС-супервизором.
- **Дрейф знаний.** Мера: `anchor-check` + `contract-sweep` + пропорциональность + ревью `§B/§A`.

## 8. Открытые вопросы и предположения

**Предположения (консервативные, реализация-готовые):**
- Backend (Herdr/Omnigent) предоставляет spawn/resume/события и хотя бы `status()`-poll; иначе ядро полагается на reconciliation. Мы не пишем runtime.
- Пороги контекста (250–350k оркестратор, ~100k re-warm) — конфигурируемые, не константы кода.
- Python — первичный стек с конкретной реализацией; PHP/JS — адаптеры на предложенной основе.
- Спека передаётся по `spec_ref` и неизменяема; при нереализуемости — `FAILED_INFEASIBLE` + эскалация.
- `reuse-scan` — стартовая опция оркестратора; находки, меняющие бизнес-смысл, эскалируются, простые технические — решает оркестратор.
- Model-set (5 ролей, `reviewer_b.vendor ≠ implementer.vendor`) хранится в `meta-o.models.json`; на каждом старте/продолжении показывается для подтверждения/смены.
- Финальные документы — по-русски; идентификаторы/команды/схемы — по-английски (сделано).
