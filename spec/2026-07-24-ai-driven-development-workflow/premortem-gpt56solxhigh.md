Провал, скорее всего, произошёл не из-за качества отдельных моделей, а из-за несовпадения строгих инвариантов методологии с её минимальным control plane и обычным Git-процессом.

### 1. Оркестратор регулярно зависал после сбоев backend

**Что произошло.** После перезапуска Herdr/Omnigent или оркестратора `state.json` показывал, что сообщение ещё не отправлено, хотя backend уже принял его. Повторная отправка запрещена, доказать результат через `status/read` невозможно. Run либо навсегда уходил в pause/escalation, либо запускал новую session, дублирующую работу.

**Почему.** Atomic `tmp → fsync → rename` защищает только локальный JSON. Между изменением backend и записью состояния нет транзакции, operation ID, durable outbox или монотонного event cursor. Native resume не гарантирует exactly-once delivery.

**Что следовало сделать.** Сделать idempotency keys, query-by-operation-ID и устойчивый event cursor обязательными completion-critical capabilities backend. Backend без них должен быть `unsupported`, а не `degraded`. Альтернатива — минимальный write-ahead operation journal, хотя это уже осознанное смягчение запрета на собственный control layer.

### 2. Аттестация переставала быть действительной при обычном PR workflow

**Что произошло.** Локально ревизия `R` прошла QC, два review и E2E, затем появился metadata commit `M`. После rebase или squash перед PR хеш `R` исчезал, хотя содержимое могло не измениться. `verification.json` указывал на недоступную ревизию. Команда либо повторяла весь дорогой цикл, либо принимала результат, формально нарушавший главный completion invariant.

**Почему.** `contentRevision` фактически отождествлён с Git commit ID. Commit ID идентифицирует не только содержимое, но и историю. При этом workflow заканчивается до отдельно запрашиваемых push/PR операций и не определяет последующую повторную аттестацию.

**Что следовало сделать.** Аттестовать Git tree OID, сохраняя commit ID только как provenance. После rebase сравнивать tree: идентичное дерево сохраняет подтверждения, изменившееся — сбрасывает их. Также нужен явный post-rebase verification step перед push/PR.

### 3. QC оставался зелёным при росте циклов и связанности

**Что произошло.** Через несколько месяцев модули оставались ниже лимитов LOC и complexity, но изменения стали вызывать каскадные правки по проекту. Возникали новые dependency cycles и высокая fan-out связанность, при этом `./tools/qc` проходил.

**Почему.** Ruff, LOC/nesting checks и Import Linter проверяют разные частичные свойства. Import Linter обнаруживает лишь нарушения заранее описанных contracts. Дизайн не требует полного распределения модулей по слоям, построения dependency graph, SCC-проверки или метрик coupling. Неописанная связь остаётся невидимой.

**Что следовало сделать.** Добавить обязательный graph gate:

- 100% first-party modules должны принадлежать архитектурной boundary;
- новые SCC и dependency cycles запрещены;
- контролируются fan-out/fan-in и запрещённые lateral edges;
- baseline фиксирует существующие edges, а не только превышения LOC;
- неизвестный модуль или неполный contract считается QC failure.

### 4. All-symbol purpose превратился в compliance theatre

**Что произошло.** Brownfield adoption затронул почти каждую функцию, private method, test helper и dunder. Агенты массово создавали формально корректные причинные docstrings. Линтер их принимал, а reviewers тратили основную часть времени на проверку тысяч purpose-текстов и всё равно пропускали семантический дрейф. Команды начали обходить основной workflow.

**Почему.** Механика способна проверить только наличие текста и ссылки; смысл полностью возложен на двух reviewers. При этом purpose debt baseline запрещён, а staged adoption упомянут, но не имеет точного контракта для зависимостей между adopted и unadopted roots.

**Что следовало сделать.** Не ослабляя hard constraint, определить `adoption-manifest.json`: сертифицированные dependency-closed roots, их покрытие и запрет feature-изменений вне сертифицированного closure. Для каждого этапа нужны inventory, ограниченный diff и отдельная semantic review.

Заслуживающая рассмотрения альтернатива — обязательный purpose только для публичных, архитектурно значимых и рискованных symbols. Она нарушает исходный hard constraint, но существенно снижает cargo-cult документацию.

### 5. После cleanup терялся исходный acceptance oracle

**Что произошло.** Внешняя feature-spec позже становилась недоступна, а run blob и decision log уже были удалены. Компактный knowledge layer сохранял устойчивый смысл, но не каждую acceptance-деталь. При последующей регрессии невозможно было доказать, являлось ли поведение намеренным.

**Почему.** Дизайн приравнял удаление спеки из рабочего поискового контура к удалению последней гарантированной копии. Для tracked specs остаётся Git history, для external specs такой гарантии нет. В durable verification metadata не сохраняется достаточная связь с исходным oracle.

**Что следовало сделать.** Хранить immutable content-addressed cold archive вне repository search roots и вне обычного agent context. В долговечном manifest достаточно оставить spec digest, archive locator, финальный tree OID и mapping на созданные `§B/§A` anchors. Это сохраняет provenance, не превращая старые спеки в конкурирующий knowledge layer.
