Наиболее вероятный итог — не пропуск единичного бага, а постепенная непригодность workflow к повседневной работе.

1. Run регулярно застревает в `PAUSED_BACKEND_UNCERTAIN`

**Что произошло.** Backend принял сообщение исполнителю, но оркестратор завершился до обновления `state.json`. После восстановления видно лишь, что session `running` или `complete`, но нельзя доказать, к какой команде относится состояние. Повторная отправка запрещена, watchdog только уведомляет, поэтому требуется ручное разбирательство.

**Почему.** Запись backend-команды и atomic update локального состояния не образуют одну транзакцию. В контрактах нет обязательных `operation_id`/idempotency key и durable in-flight intent. Capability suite проверяет возможности backend, но не устраняет crash window.

**Что изменить.** Сделать native correlation и idempotency completion-critical capability. Перед отправкой сохранять компактный intent с `operation_id`, после — acknowledgement/result. Если это считается недопустимым control layer, разрешать только backend с эквивалентной нативной гарантией; остальные отмечать `unsupported`.

2. Один revision проходит QC на одном компьютере и не проходит на другом

**Что произошло.** Исполнитель получил `./tools/qc PASS`, но другой разработчик или reviewer увидел иной набор purpose/knowledge violations. Иногда код с фактическим нарушением был принят, потому что CI необязателен и повторной общей проверки не было.

**Почему.** Общий репозиторий не фиксирует и не проверяет версии skills и поставляемых с ними standalone-линтеров. `snapshot_digest` идентифицирует содержимое проекта, но не реализацию QC, её schema version или toolchain. Следовательно, `QC(S) PASS` не является воспроизводимым утверждением.

**Что изменить.** Как минимум сохранять в `RevisionResult` hashes и contract versions всех QC-инструментов и запрещать смешивать несовместимые результаты. Надёжный вариант — пересмотреть hard constraint: репозиторий должен фиксировать версию QC-контракта и hashes автономных JS-файлов, даже если сами agent skills обновляются независимо.

3. Feature не может выйти из review/E2E loop

**Что произошло.** Reviewer находит minor, исправление инвалидирует подтверждения, новый проход обнаруживает следующее замечание. После потери session свежий reviewer повторно открывает уже разобранный вопрос или классифицирует его иначе. После трёх циклов возникает эскалация, но завершить run всё равно нельзя: подтверждённый defect оставлять запрещено.

**Почему.** Findings намеренно не имеют даже временного устойчивого identity/disposition state. При этом adjudication зависит от числа rebuttal cycles и предыдущих решений. `state.json` хранит только итоговые confirmations, поэтому процесс не способен отличить новый дефект от повторно открытого или уже признанного taste.

**Что изменить.** Хранить до cleanup run-local finding set: fingerprint, evidence, revision, disposition и adjudication. Это не project ledger и не долговременная история. Независимость сохраняется: reviewers не видят findings друг друга до собственных первоначальных отчётов. Решение полностью не сохранять findings следует пересмотреть.

4. Brownfield adoption блокирует обычную разработку

**Что произошло.** Dependency-closed adoption одного участка втянул значительную часть связанного проекта. Для всех modules, tests, private methods, nested functions и dunder потребовались purpose и anchors без baseline. Adoption превратился в огромный semantic-review проект, а product features либо остановились, либо стали выполняться через внешний «быстрый фикс».

**Почему.** Hard constraint all-symbol purpose соединён с отсутствием временного purpose baseline и запретом затрагивать unadopted closure. В плотно связанном brownfield «ограниченная closure» может практически совпасть со всем проектом.

**Что изменить.** Специфицировать миграцию по SCC и архитектурным boundaries с измеримыми волнами, отдельной пропускной способностью и явным exit plan. Если closure всё равно слишком велика, потребуется нарушающая исходное решение альтернатива: frozen purpose-debt baseline с запретом регрессий и обязательным покрытием каждого изменяемого symbol. Иначе методология формально строга, но фактически не внедряема.

5. Через полгода невозможно восстановить исходный acceptance oracle

**Что произошло.** External locator перестал существовать либо tracked spec исчезла после squash/history cleanup. Run blob уже удалён. Остались `spec_sha256`, provenance и сокращённые `§B/§A`, но спорное acceptance-условие восстановить невозможно. Команда не может доказать, является текущее поведение регрессией или исходным намерением.

**Почему.** Дизайн приравнял удаление спеки из рабочего поискового контура к удалению последних доступных байтов. Digest подтверждает совпадение только при наличии исходного содержимого. Git provenance также не гарантирует сохранение blob при squash и изменении истории.

**Что изменить.** Перемещать immutable spec blob в cold content-addressed archive вне repository search roots и не показывать его агентам без явного retrieval. Это совместимо с исходным запретом на старые спеки как живой источник знания: архив остаётся доказательством, а не частью рабочего knowledge layer.
