# meta-o

Устанавливаемые агентские скилы ведут фичу от задачи или спецификации до одного
проверенного коммита-кандидата через сессии Orca. Meta-O поддерживает только
Orca: его публичная поверхность ответа квалифицирована, но каждый кандидат всё
равно требует нового вердикта текущего запуска.

Поддержка Herdr и Paseo удалена как невостребованная до появления надёжных
публичных поверхностей полного ответа. Последнее дерево, содержащее их скилы
оркестрации и проверки, находится в полном коммите
`2eb85bebe14aa35419db192db66938e14e0be6f1`.

В Meta-O процессом управляют прежде всего скилы: методология не добавляет CLI
оркестрации, прокси поставщиков, фоновую службу, общее хранилище состояния
процесса или слой адаптеров. У watchdog есть единственное узкое исключение:
ограниченные хеши сообщения и нормализованного состояния, нужные только для
подавления повторной подсказки между запусками.

Проект хранит исходный запрос пользователя и последующие уточнения дословно,
потому что спецификация — это сжатие с потерями. Один проверенный результат —
один полный Git SHA; новый коммит обнуляет его QC, ревью и E2E. Два независимых
ревьюера работают на моделях разных поставщиков, и хотя бы один поставщик
отличается от поставщика исполнителя реализации.

Последнее дерево с удалённым Omnigent находится в полном коммите
`61c39304a7e80e5350e8ffd43110a2ac1cac62b7`.

## Установка

Из проекта, которому нужны скилы, установите локальную рабочую копию:

```bash
apm install /path/to/meta-o
apm install /path/to/meta-o --skill mo-review-orca
```

Локальная установка в одноразовое окружение покрыта тестами. Публикация и
проверка удалённой установки остаются ответственностью владельца проекта:

```bash
npx skills add shkarupa-alex/meta-o
apm install shkarupa-alex/meta-o
```

Для сборки нужен Node.js 22 или новее. Помощнику проверки готовности поставщика
требуются Bash 3.2+, стандартные утилиты POSIX и Zsh, если запрошена матрица
запусков Zsh. Watchdog дополнительно требует `jq` для проверки нативного JSON и
`flock` для последовательной отправки подсказок по указателю.

## Скилы

| Скил                  | Назначение                                                  |
| --------------------- | ----------------------------------------------------------- |
| `find-reuse`          | Переносимый поиск готового решения только для чтения.       |
| `mo-orchestrate-orca` | Маршрут фичи через полный Orca `worker_done`.               |
| `mo-review-orca`      | Отдельная проверка через Orca с получением полного ответа.  |
| `mo-setup`            | Проверка и исправление готовности проекта и окружения.      |
| `mo-e2e`              | E2E-сценарии, которым действительно нужен агент.            |
| `mo-watchdog`         | Наблюдение Orca-сессий без облачного запуска модели.        |
| `senior-jsts`         | Проверка существенного изменения JS/TS по доказательствам.  |
| `senior-python`       | Проверка существенного изменения Python по доказательствам. |

Механика Orca отделена от общих правил жизненного цикла и проверки. У общих
правил один источник в `shared/`, чтобы оркестрация и отдельная проверка не
расходились.

Управляющий исполняемый файл и обязательный внешний companion-скил — разные
зависимости:

| Бэкенд | Управление            | Companion-скил  |
| ------ | --------------------- | --------------- |
| Orca   | `orca` или `orca-cli` | `orchestration` |

## Жизненный цикл фичи

```text
готовность проекта/задачи
  → перенос исходных данных и G0: пустой закоммиченный блокнот фичи
  → короткий начальный /goal для исполнителя реализации
  → исполнитель коммитит чистый кандидат
  → фиксируется один полный SHA
  → параллельно запускаются две изолированные проверки
  → обе завершаются до освобождения любой из них
  → исправления создают новый SHA и перезапускают все проверки
  → детерминированный QC и применимые E2E
  → GC: повторное доказательство пустоты backlog для точного SHA
  → G1/G2 перед созданием или слиянием MR агентом со сверкой удалённого HEAD
  → понятный человеку проверенный результат или needs_attention
```

Оркестратор управляет процессом, но не читает, не оценивает и не редактирует
продуктовый код. Репозиторий читают исполнитель реализации, ревьюер и
E2E-исполнитель. Единицей извлечения служит полный финальный ответ; ограниченный
предпросмотр терминала или закрытая расшифровка поставщика не доказывают поддержку.
Полный вид сессии остаётся доступным для редкой диагностики.

## Структура репозитория

```text
src/skills/   авторские входные скилы
shared/       единые владельцы общих references и runtime-помощников
skills/       сгенерированное устанавливаемое дерево, закоммичено и побайтово проверяется
tools/        инструменты сборки, не поставляются
docs/         бизнес-контекст, словарь, архитектура, backlog и критерии приёмки
spec/         игнорируемые закрытые рабочие пакеты; основная активная спецификация лежит в docs/
```

`skills/` строится автоматически и никогда не редактируется вручную. Каждый
установленный скил самодостаточен: вместе поставляются его `SKILL.md`, нужные
`references`, `scripts` и `licenses`.

## Разработка

```bash
npm install
make skills
make mo-qc
make mo-e2e
make mo-eval-cases
```

`make mo-qc` — авторитетная детерминированная проверка, не изменяющая файлы.
`make mo-e2e` печатает сценарии, которым нужен агент, и завершается с кодом 2,
поэтому его невозможно принять за успешный прогон.

`make mo-backlog` — отдельная проверка закрытия жизненного цикла, не изменяющая
файлы. Она читает `HEAD:docs/backlog.md`; обычный `make mo-qc` намеренно
допускает корректные временные записи фичи.

`make mo-eval-cases` без сети проверяет встроенный корпус из 24 случаев для
восьми скилов. Команды реального GPU-запуска и проверки внешних доказательств в
JSON описаны в `docs/e2e.md`; сама цель модель не запускает.

Каждый устойчивый бизнес-тезис постановки несёт id `§B-*`, каждое архитектурное
решение — свой `§A-*` и имена тезисов, которым служит, а назначение модуля
называет решение. Поэтому путь от строки кода до бизнес-смысла проходится
обычным `rg`.
