# Инструкция по сопровождению слоя знаний

Этот каталог хранит не полное описание кода, а компактную цепочку причин, по
которой кодовый агент может:

- понять, зачем существует поведение;
- проверить новую реализацию сначала против бизнес-смысла, затем против
  архитектурного решения;
- найти код, который станет лишним или должен быть упрощён при отказе от
  требования либо решения;
- обновить знания после изменения фичи без переписывания больших документов.

Документация рассчитана на кодовых агентов. Она должна хорошо находиться через
`rg`, оставаться короткой и описывать причины, границы и инварианты, а не
пересказывать реализацию.

## Уровни знаний

### Уровень 1 — бизнес-смыслы и исходные постановки

Устойчивые постановки живут в `_buisiness.md`. Незавершённые постановки с
якорями `§B-TODO-*` живут в `todo.md` и после реализации либо удаляются, либо
переносятся в `_buisiness.md`, если стали постоянной бизнес-возможностью.

Каждая самостоятельная постановка получает уникальный grep-friendly якорь с
символом параграфа:

```markdown
## §B-OUTCOME-01 — Проверять фактический результат работы BitrixGPT
```

Уровень отвечает на вопросы:

- какую проблему решаем;
- для кого и зачем она важна;
- какой бизнес-результат ожидается;
- что перестанет быть нужным, если от постановки отказаться.

Здесь нельзя описывать модули, классы, функции и детали текущей реализации.

### Уровень 2 — архитектурные решения и свойства системы

Живёт в тематических Markdown-файлах непосредственно в `docs/`, без отдельной
папки и без обязательной общей карты.

Каждое самостоятельное решение получает якорь:

```markdown
## §A-ENV-02 — Точное состояние сценария принадлежит самому тесту
```

Описание решения обычным текстом объясняет, из какой постановки уровня 1 оно
следует:

```markdown
Это решение реализует §B-REALISM-01 и §B-OUTCOME-01: общий baseline создаёт
реалистичный шум, а детерминированные фикстуры задают проверяемое состояние
конкретного сценария.
```

Не добавлять служебные блоки вида `Status`, `Derived from`, `Implemented by` или
`Related`. Связи должны читаться как нормальный текст.

Каждое архитектурное решение должно кратко фиксировать:

- зачем оно принято и на какие `§B-*` опирается;
- обязательные инварианты и границы;
- что намеренно не входит в решение;
- как проявляется в системе на уровне крупных компонентов;
- что можно удалить, упростить или пересмотреть, если решение отменяется.

Последний пункт формулируется явно, например:

```markdown
Если отказаться от §A-ENV-02, self-seeding helpers и lifecycle подготовки
фикстур становятся лишними; кейсы придётся перенести в курируемые baseline.
```

Не перечислять все функции реализации. Пути к основным модулям допустимы в
обычном тексте, если помогают найти границу ответственности.

### Уровень 3 — назначение модуля

Живёт в начале исходного файла в module docstring или комментарии.

Модуль ссылается только на решения уровня 2. Он не должен повторно ссылаться на
бизнес-уровень: цепочка уже существует через `§A-*`.

Пример:

```python
"""Управляет подготовкой точного состояния eval-кейса.

Нужен для §A-ENV-02: применяет детерминированные фикстуры после восстановления
baseline и до отправки запроса Марте.

Если §A-ENV-02 отменяется, модуль можно удалить вместе с вызовом fixture-фазы
из runner lifecycle.
"""
```

Описание должно отвечать:

- зачем существует модуль;
- какую часть `§A-*` он реализует;
- что является его границей ответственности;
- что станет лишним при отмене соответствующего решения.

### Уровень 4 — назначение функции, класса или метода

Живёт в docstring символа. Ссылается на уровень 3 либо, если отдельного
модульного смысла недостаточно, непосредственно на `§A-*`. На уровень 1 не
ссылается.

Пример:

```python
async def setup_case_fixtures(...):
    """Создаёт данные кейса перед prompt-фазой модуля fixture lifecycle."""
```

Не документировать очевидную механику. Docstring нужен, когда без него неясно:

- почему символ существует;
- какой инвариант он защищает;
- почему более простая реализация недостаточна;
- можно ли удалить символ при отказе от функции модуля или `§A-*`.

## Документы уровня 2

Документы лежат плоско в `docs/`:

- `runtime.md` — границы системы, жизненный цикл прогона, изоляция слотов,
  параллелизм, reset, pause/resume и обработка инфраструктурных сбоев;
- `test-environment.md` — baseline, per-test фикстуры, время, воспроизводимость,
  версии данных и компонентов;
- `evaluation.md` — state/trace/answer, итоговый verdict, LLM-судья, побочные
  действия, безопасность и метрики;
- `experiments.md` — сравнение моделей и версий, ручные предрелизные проверки,
  scheduled-прогоны, отчёт «было / стало», оповещения и ресурсные ограничения.

При изменении архитектуры обновлять тематический документ, а не создавать новый
обзор ради одной фичи. Новый файл уровня 2 нужен только для самостоятельной
области с несколькими устойчивыми решениями.

Не создавать отдельный архитектурный индекс. Существующие узкие документы
(`marta_chat_contract.md`, `rollout-capture.md`, `page-context-capture.md`,
`drift_policy.md`) остаются подробными контрактами и эксплуатационными
нюансами. Тематические документы уровня 2 должны ссылаться на них, а не
дублировать содержимое.

`howto-tests.md` — практическое руководство по написанию eval-кейсов:
рекомендации, паттерны, антипаттерны и проверенные лайфхаки. Это не источник
архитектурной истины; при конфликте приоритет у `§A-*`.

`todo.md` содержит только незавершённые задачи, а `known-issues.md` — только
актуальные ограничения и способы их обхода. Это статусные документы, не новые
слои архитектуры. После реализации задача удаляется из TODO, после устранения
ограничения — из known issues; завершённые расследования туда не архивируются.

## Как изменять код и документацию

Перед разработкой или ревью:

1. Найти релевантные `§B-*` в `_buisiness.md`.
2. Найти производные `§A-*` через `rg '§B-[A-Z0-9-]+' docs`.
3. Найти модули уровня 3 через `rg '§A-[A-Z0-9-]+' src tests`.
4. Проверить, соответствует ли предлагаемое изменение всей цепочке.

После изменения:

1. Обновить существующий `§B-*`, только если изменился бизнес-смысл.
2. Обновить или добавить `§A-*`, если изменилось архитектурное решение,
   инвариант либо граница системы.
3. Обновить module docstring всех затронутых модулей.
4. Добавить или изменить docstring символа только там, где изменилось его
   назначение либо причина существования.
5. Обновить `howto-tests.md`, если появился повторяемый практический паттерн,
   антипаттерн или полезный приём.
6. Проверить ссылки:

```bash
rg -o '§[AB]-[A-Z0-9-]+' docs src tests | sort
```

## Правила компактности

- Один `§B-*` — одна устойчивая бизнес-постановка.
- Один `§A-*` — одно архитектурное обязательство или существенное решение, не
  одна функция и не один класс.
- Не копировать код, схемы данных и CLI reference без необходимости.
- Не фиксировать детали, которые очевидно и надёжно находятся через `rg`.
- Не создавать документ ради одной функции.
- Не дублировать узкий контракт в обзорном документе.
- Планируемое поведение явно отличать от фактически реализованного обычным
  текстом.
- При отказе от решения не оставлять мёртвые ссылки: указать замену либо удалить
  всю зависимую цепочку уровней 3–4.

## Порядок изменений

При реализации новой задачи нужно сначала проходить по всем уровням начиная с бизнеса и фиксировать TODO если задача меняет/добавляет что-то.
После реализации нужно актуализировать все слои документации, убирать TODO, фиксировать текущее состояние.

Важно: объем "дописанного" текста должен соответствовать объему реальных изменений в коде. Не нужно описывать исправление 1й строчки 10ю абзацами.

## Проверка при ревью

Ревьюер сначала проверяет соответствие `§B-*`, затем `§A-*`, и только потом
локальное качество реализации.

Если код формально корректен, но не поддерживает исходный смысл или нарушает
архитектурный инвариант, это является дефектом. Если `§B-*` или `§A-*` больше не
актуальны, сначала меняется решение и явно определяется, какие нижележащие
модули и символы нужно удалить или упростить.
