# Сквозная проверка

`make mo-qc` — детерминированная продуктовая проверка. `make mo-e2e` намеренно
не запускает агентские сценарии: он печатает точку входа этого документа и
выходит с кодом 2. E2E-исполнитель выполняет применимые сценарии на одном
именованном полном SHA кандидата, не меняет его и сообщает понятные человеку
доказательства.

## Общие доказательства

Каждый сценарий фиксирует бэкенд, версию управляющего файла, обнаруженный
companion-скил, среду агента, поставщика модели, запрошенный и фактический
маршруты, модель и уровень рассуждения, точный SHA кандидата, действие,
наблюдаемый публичный результат и `PASS`, `FAIL` или `UNKNOWN`. Отсутствующий
полный вердикт — `UNKNOWN`; такой сценарий повторяется, частичного прохождения
нет. Закрытые расшифровки поставщика, хранилища hooks и выведенные из наблюдений
базы сессий запрещены как доказательства.

Используйте фикстуру обычного полного финального ответа и фикстуру на три-четыре
экрана с узнаваемыми маркерами `BEGIN`, `MIDDLE` и `END`. Полный вид сессии
проверяется отдельно как диагностика.

## Модельные исполнители для оценки скилов

Каждый случай с моделью сначала доказывает применимость: именованное поведение
нельзя равноценно проверить детерминированной фикстурой. Для обычного скила
выполняются три ограниченных случая `positive`, `forbidden` и `degraded` на
`claude/opus[1m]/low` и `codex/gpt-5.6-sol/low`. Координаты желаемых Codex
`gpt-5.6-luna/max` и OpenCode/Qwen всегда материализуются минимум как
`not_available`. Неприменимый случай получает `not_applicable`; отсутствующая
обязательная настройка — `blocked|not_run`. Резервного пути нет. Qwen из B22
остаётся отдельным критическим исполнителем оркестрации.

### Встроенный корпус и команда реального запуска

Каждый устанавливаемый скил владеет `evals/cases.json` v2 с тремя ограниченными
случаями: `positive`, `forbidden`, `degraded`, каждый со списком `contracts`.
`make mo-eval-cases` проверяет точный набор из 8 скилов и 24 случаев без сети и
ничего не запускает. Сгенерированный скил получает тот же корпус через обычный
`make skills`.

Реальный запуск выполняется из чистой рабочей копии замороженного кандидата.
Сначала средство запуска создаёт один ограниченный `prompt` с пакетом
инструкций, неизменяемыми входными метаданными и незаполненными полями
`execution` и `result`. Модель получает фактическую идентичность только из
нативного результата среды агента и возвращает `envelope` доказательства JSON v3
с `tier` и `matrixProfile`:

```bash
node tools/skill-evals.mjs --prompt <skill> \
  --expectations-out <coordinate-expectation.json> \
  --candidate <full-sha> \
  --tier <required|desired|critical> --matrix-profile <name> \
  --route <route> --model <provider/model> --effort <level> \
  --harness <name> --harness-version <version> \
  --profile-version <profile-version> --quantization <value> \
  --context <value> --sampling <value> \
  --tool-permissions <comma-separated> --repetition 1
```

`--expectations-out` создаёт новый закрытый файл и отказывается перезаписывать
существующий. Его сохраняют до хода модели как замороженный вызывающей стороной
ввод, а записи всех координат объединяют во внешний неотслеживаемый массив JSON.
`prompt` передают одобренной пользователем среде агента без изменения рабочей
копии. Ответ сохраняют во внешнем неотслеживаемом JSON-файле. Вызывающая сторона
отдельно, не копируя вывод модельного исполнителя, собирает из публичных
нативных наблюдений запуска и процесса точный `execution` каждой координаты
(`id`, `source`, интервал, код выхода, фактическая идентичность, доступность и
её доказательство) в закрытый неотслеживаемый массив JSON вида
`[{"coordinate":"<skill>:<profile>:1","execution":{...}}]`. После хода модели
вызывающая сторона подставляет тот же независимо наблюдаемый `execution` в
`envelope` доказательства; управляемое модельным исполнителем несовпадение
идентификатора в происхождении случая остаётся ошибкой. Доказательства
проверяют:

```bash
node tools/skill-evals.mjs --validate-evidence <evidence.json> \
  --expectations <all-coordinate-expectations.json> \
  --execution-observations <all-coordinate-executions.json> \
  --candidate <full-sha> --require-all \
  --critical-profile <configured-orchestrator-route/model/effort>
```

Валидатор требует отдельную принадлежащую вызывающей стороне запись `execution`
для каждой координаты и побайтово по смыслу сверяет её с `envelope`. Затем он
связывает доказательства с ревизией Git-дерева каждого скила и дайджестом точных
входов случая, запроса и среды агента; требует нативные идентификаторы
выполнения, интервал и код выхода, наблюдаемую фактическую идентичность и
отдельное доказательство для каждого `oracle` `must`/`mustNot`. `--require-all`
требует все 32 координаты: обязательные и желаемые для каждого из 8 скилов;
желаемое отсутствие сохраняется в `envelope` с `NOT_AVAILABLE`, а не пропуском.
Такой `envelope` несёт `effective: null`, ненулевой код выхода нативной проверки
доступности и типизированную причину; он не выдумывает версию среды агента или
фактическую модель. Отсутствующий нативный исполняемый файл материализуется без
хода модели:

```bash
node tools/skill-evals.mjs --availability-probe <skill> \
  --expectations-out <coordinate-expectation.json> \
  --candidate <full-sha> --tier desired --matrix-profile <name> \
  --route <route> --model <provider/model> --effort <level> \
  --harness <name>
```

Успешная нативная проверка запрещает ложный `NOT_AVAILABLE`. `PASS` не
предзаполняется и невозможен при пустом наблюдении или неподтверждённом условии.
Критическая идентичность сравнивается с явно переданным принадлежащим
пользователю профилем Orchestrator, а не с жёстко заданной отображаемой
подписью. Полные расшифровки, секреты и абсолютные пути машины запрещены. Любой
`FAIL`, `UNKNOWN` или `NOT_RUN` делает команду реального запуска ненулевой.
Обоснованный `NOT_APPLICABLE` обязан содержать наблюдение с применённым правилом
и остаётся валидным завершением неприменимого случая; для рекомендательных
случаев инженер отдельно решает смысловое замечание, но исполняемый сбой
безопасности или контракта остаётся блокирующим. Доказательства хранятся в
текущем запуске или финальном результате, не в Git.

## Сценарии установки

Локальная установка в одноразовое окружение должна доказать точный набор
самодостаточных скилов с принадлежащими им `references` и `scripts`. Удалённую
установку выполняет владелец проекта после публикации; процесс не отправляет
изменения ради фикстуры.

## Перенос проверки только для документации

E2E можно перенести на более поздний коммит только с документацией, если оба
ревьюера финального SHA явно подтвердили, что изменение не влияет на поведение
исполняемого кода, скил, инструкции агента, критерии приёмки или этот контракт.
Финальный отчёт называет проверенный SHA и причину. При любом сомнении E2E
запускается заново.
