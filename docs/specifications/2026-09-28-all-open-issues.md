# Спецификация: исправление 25 открытых issues Meta-O

Статус: дизайн согласован владельцем; три раунда проверки консилиумом
завершились без единогласного принятия, после R3 внесены ограниченные правки по
названным замечаниям; финальный просмотр владельца впереди. Дата: 2026-09-28.
Исходный набор: GitHub `shkarupa-alex/meta-o`, открытые #18–#43 на дату снимка
(`open-issues.json` в закрытом пакете консилиума). Новые issues после снимка
проходят обычную маршрутизацию и не меняют этот список молча.

## Цель и границы

Исправить все 25 открытых issues с проверяемой отдельной приёмкой. Работа
делится на независимо интегрируемые существенные срезы; у каждого issue ровно
один срез-владелец (см. трассировку). Действующая иерархия: бизнес-требования
`docs/business.md` → архитектурные решения → скилы и помощники. Оркестрация
остаётся в скилах и рассуждениях (§A-ORCHESTRATION-01): новый движок, прокси
Orca, постоянное хранилище состояния и безымянные манифесты не вводятся.
`src/skills/` и `shared/` — исходники; `skills/` пересобирается. Знания для
человека пишутся на русском, имена протоколов и код — на английском. Каждое
связное проверенное приращение коммитится в `feature/<short-slug>` от актуальной
`develop`; push по запросу.

Общее «все issues исправлены» нельзя объявить, пока для каждого issue нет
доказательства положительного пути. Особенно #29, #33, #43 могут требовать
изменения Orca вне этого репозитория: локальный безопасный отказ не равен
восстановлению штатного сценария. Внешняя зависимость получает конкретный
контракт, владельца, issue правильного проекта и план повторной приёмки;
остальные готовые срезы могут интегрироваться раньше, но эти три issue остаются
открытыми до live PASS. Внешнюю зависимость и её отсутствие подтверждают по
§B-PORTABILITY-06: дефект чужого инструмента уходит в Issue его владельца и не
обходится у нас.

### Исходы финального цикла

Финальный цикл на кандидатном полном SHA S получает ровно один из трёх
именованных исходов:

- `complete` — для всех 25 issues положительный путь доказан на S, и все
  проверки раздела «Оценка и контроль качества» прошли. Только этот исход
  разрешает сообщать «все открытые issues исправлены».
- `needs_attention/external_blocked` — выполнены все условия `complete`, кроме
  положительного пути для поимённо перечисленных issues, чья блокировка доказана
  внешней возможностью Orca. На S для каждого из них должны быть доказаны:
  fail-closed поведение (детерминированно и в live E2E); записи о точном
  недостающем контракте, наблюдаемой версии Orca, внешнем владельце и ссылке на
  Issue; тест совместимости; событие повторной приёмки. Итоговое сообщение
  перечисляет интегрированные и заблокированные issues поимённо, а задача не
  называется завершённой. Этот исход не является `PASS` и не закрывает
  заблокированные issues.
- `needs_attention/verification_blocked` — любой обязательный QC, независимый
  reviewer, обязательная модельная координата или применимый E2E не дал
  принимаемого доказательства; либо положительный Orca путь недоступен и потому
  нельзя получить два авторитетных reviewer body. Называются точный
  отсутствующий gate, последнее наблюдение и следующий проверяемый шаг. S
  остаётся кандидатом, а не «проверенным S»; `--require-all` не ослабляется,
  issues без положительной приёмки не закрываются.

Чтобы внешняя блокировка не делала остальную матрицу недостижимой, oracle
skill-eval cases проверяют только локальный контракт: отказ при неизвестном
draft, запрет сырого `codex exec`, валидацию полученного body. Такие cases не
зависят от невыпущенной возможности Orca и должны пройти на S в обоих исходах.
Положительный путь, который зависит от внешней возможности, оформляется как B/W
сценарий в `docs/e2e.md` с типизированным результатом
`blocked:external_capability`. Этот результат допустим только при исходе
`needs_attention/external_blocked` и никогда не считается `PASS`. Любой другой
`blocked`, `FAIL`, `UNKNOWN` или `NOT_RUN` ведёт к
`needs_attention/verification_blocked`, а не к `complete` или
`external_blocked`.

Повторная приёмка после появления внешней возможности зависит от того, менялся
ли код:

- код репозитория не менялся — на том же S повторяются все live E2E и cases,
  затрагивающие Orca (review body, доставка, жизненный цикл пары, trust), на
  новой версии Orca;
- любое изменение кода — новый S и полный цикл.

## Интерфейсы и протоколы

### Авторитетный reviewer body

Первая строка body — `Review-Execution: <dispatch-id>`. Ни `MO-REVIEW-REPORT/1`,
ни пояснение к id в body не вставляются: `MO-REVIEW-REPORT/1` остаётся префиксом
**вывода валидатора**. Заголовок сохраняет `Candidate`, requested/effective
`Mode`, `Delegation`, `Verdict`, `Counts`. Затем от `Evidence report` до
последнего `End-Review: <same-dispatch-id>` идут по одному и в прежнем порядке
`Grounding`, `Scope and checks`, `Findings`, `Unknowns`, `Residual risks`.
`Grounding` указывает проверенные HEAD и чистоту worktree, а контекст Dispatch
хранит зафиксированные SHA установленных протокола, reviewer-скила и валидатора.
Ожидаемые Dispatch, SHA и режимы задаёт внешний контекст, а не самосогласованный
body.

Существующий CLI валидатора принимает

```text
validate --file <path|-> --dispatch <id> --candidate <full-sha> --requested <fast|deep|follow_up> [--effective <fast|deep|follow_up>]
```

Именно эти имена флагов сохраняются. Новая read-only команда

```text
template --verdict <PASS|FINDINGS|UNKNOWN> --dispatch <id> --candidate <full-sha> --requested <mode> --effective <mode> [--unknown-reason <reason>]
```

Она печатает полный валидный образец в stdout без файла и побочных эффектов.
`--unknown-reason` обязателен ровно для `UNKNOWN` и принимает только действующий
закрытый набор
`unreadable|candidate_mismatch|dirty_candidate|malformed_report|retrieval_failure|handoff_failure|review_incomplete`.
`PASS` печатает нулевые Counts, `FINDINGS` — один пример `F-001 [P2]` с P2=1,
`UNKNOWN` — нулевые Counts, один `Unknown-Reason` и непустой `Unknown-Account`.
Тест передаёт каждый образец без правок в `validate --file -` с теми же
expected-флагами и требует `status=valid`.

Новая грамматика читает первые шесть **непустых** top-level строк как
`Review-Execution`, `Candidate`, `Mode`, `Delegation`, `Verdict`, `Counts`
строго в этом порядке. Первая строка файла обязана быть `Review-Execution`;
между соседними служебными строками допускается ноль или **одна** пустая
LF-строка, и не допускается проза, list/quote/code-container либо вторая пустая
строка. После `Counts` до первого индекса или `Evidence report` допускается ноль
или одна пустая строка. Индекс состоит только из top-level `F-NNN [P0–P3] ...`
абзацев; между соседними индексами допускается одна пустая строка. После индекса
до `Evidence report` допускается ноль или одна пустая строка. Пустые строки
внутри прозы секций разрешены; каждый маркер секции — единственный top-level
абзац с точным текстом. `End-Review: <id>` — последняя непустая строка, после
неё допускается один завершающий LF. Парсер использует AST-позиции и фактическую
границу `Counts`, а не старый постоянный индекс 6.

Для каждого индекса `F-001` в `Findings` принимаются ровно две формы top-level
тела: top-level строка `F-001` и следующая непустая top-level строка,
начинающаяся `[P2] ...`, **либо** один абзац `F-001 [P2] ...`. Принять:
`Review-Execution: ctx_a\n\nCandidate: <sha>` при остальных пяти корректных
строках; `F-001\n[P2] причина...` и `F-001 [P2] причина...` в `Findings`.
Отклонить: пустую строку перед `Review-Execution`, две подряд пустые строки в
служебном заголовке, `Review-Execution: ctx_a explanation`, тело
`F-001 [P2] ...` внутри списка/цитаты, несовпадение P2 с индексом, отсутствующий
`Unknown-Account` у `UNKNOWN`. У каждого индекса одно тело и одна серьёзность,
`Counts` сходится; остальные нарушения дают `status=malformed`. Эти примеры
входят в fixture-тесты `template → validate` и фиксируются в §A-REVIEW-04 и
`shared/references/review-protocol.md`.

**Целостность body.** Авторитетен только body, полученный координатором из Orca,
и только после его собственной повторной валидации. Структурная валидность
полученного body и побайтовое совпадение с подготовленным файлом — разные
утверждения; отчёт называет оба результата отдельно.

1. **Грамматические инварианты** работают на любом хосте и доказывают валидность
   **полученного** body, но не идентичность подготовленным байтам:
   - первая строка — ровно `Review-Execution: <ожидаемый dispatch-id>`;
   - последняя непустая строка — `End-Review:` с тем же id;
   - каждая top-level секция встречается ровно один раз;
   - `Counts` равен числу разобранных находок по каждой серьёзности.

   Усечение, чужой preamble перед первой строкой и склейка двух отчётов нарушают
   хотя бы один инвариант и дают `malformed`. Другая валидная формулировка той
   же длины может пройти эту проверку, поэтому структурный PASS не маркируется
   как побайтовая идентичность.

2. **Сверка с файлом тела** работает, когда reviewer и координатор на одном
   хосте. Координатор создаёт для прогона каталог вне всех worktree и передаёт в
   brief строку `Body-File: <каталог>/<dispatch-id>.md`. Reviewer:
   - создаёт этот файл исключительно (существующий файл — отказ);
   - записывает в него точные байты body;
   - запускает на нём установленный `validate`;
   - отправляет в `worker_done` содержимое именно этого файла.

   Координатор сравнивает полученный body с файлом побайтно. Допускается только
   нормализация доставки, которую зафиксировал тест совместимости #29 для
   наблюдаемой версии Orca; любое другое расхождение даёт
   `UNKNOWN/body_integrity`. Если файл недоступен (удалённый Orca server) или
   отсутствует, пишется `prepared_body_identity=unverified`; авторитетный
   полученный body может быть принят лишь по своей структуре и внешнему
   Dispatch-контексту, без утверждения, что reviewer отправил ранее проверенные
   байты. Если конкретный review brief требовал именно доказанного совпадения,
   такой Dispatch получает `UNKNOWN/body_integrity_unverified`. Сверка с экраном
   терминала не используется.

Файл тела — временный артефакт с названным потребителем (координатор этого
Dispatch); он удаляется при освобождении слота и не служит дайджестом.
Повреждённый Dispatch нельзя переписать. Если та же provider session доказанно
жива, новый Dispatch получает новый id и проходит полную проверку.

Шаблон и brief запрещают reviewer запускать тесты, lint и QC; собственный
форматный валидатор reviewer разрешён. Находка содержит причинный путь, влияние,
инвариант, направление исправления и конкретный регрессионный случай.

**QC-гейт вместо reviewer (#37).** Исполнитель/координатор проводит локальный
`make mo-qc` (или объявленную проектом QC-команду) в чистом checkout ровно S и
называет команду и код выхода. G1 — создание MR/PR — требует локальный QC и
совпадение удалённого исходного HEAD с S. Для агентного G2 — слияния —
дополнительно нужен CI:

- исход `CI-Coverage/1 covered` на S из существующего контракта `mo-setup`;
- наблюдаемый успешный результат всех покрывающих QC-задач CI, которые
  фактически сделали checkout S — у Meta-O это `mo-qc` и `mo-backlog` из
  `.github/workflows/mo-qc.yml`, прочитанные через API хостинга.

Для Meta-O workflow изменяется так, чтобы на `pull_request` обе задачи явно
делали checkout `github.event.pull_request.head.sha` и печатали
`git rev-parse HEAD` до QC. Контроллер сверяет это значение,
`pull_request.head.sha` и наблюдаемый удалённый HEAD с S; одного
`workflow_run.head_sha` недостаточно, потому что PR-run может принадлежать
синтетическому merge commit. Для `merge_group` его синтетический SHA проверяется
отдельно как интеграционный сигнал и не подменяет QC на S. После создания PR
ожидают успешного run именно для S, затем непосредственно перед G2 повторяют
удалённый HEAD и CI evidence. `config_present`, `no_ci_surface`, `unknown`, иной
checkout SHA либо неуспешный/отсутствующий CI-run запрещают агентное слияние и
дают `needs_attention` с названным пробелом. Review и выдача локально
проверенного кандидата S без CI возможны; статус «готов к агентному слиянию» без
CI не выдаётся. Решение о человеческой интеграции без CI принадлежит человеку.

Если работа ведётся по спецификации, brief обоих reviewer содержит один путь или
Git object спецификации (`Spec: <path|object>`); без спецификации — `Spec: none`
(#30). Вызывающая сторона — оркестратор или исполнитель, запустивший standalone
`mo-review-orca`, — обязана передать этот путь. При `Spec: none` отсутствие
спецификации не считается находкой.

### Версия протокола при бутстрапе

Первый срез изменения review-протокола проверяется установленной версией с
фиксированного исходного SHA. Это сборка `skills/` из того коммита `develop`, от
которого создана ветка; её source SHA записывается в контекст каждого Dispatch.
Новый протокол проходит свои детерминированные и живые проверки на SHA среза, но
никогда не рецензирует сам себя. После интеграции этого среза следующие срезы
проверяются уже новой установленной версией. Отчётная версия определяется source
SHA установленного пакета в контексте Dispatch; новый заголовок body ради этого
не вводится.

У старой установленной версии известны дефекты двух групп. Порядок работы с
ними, пока идут S1 и S2, ниже.

**Дефекты формы отчёта (#27/#29/#31).**

- Brief старой версии дополняется бутстрап-памяткой. В ней дословный образец
  первой и последней строк и порядок секций **из установленных файлов старой
  версии**, а также указание запустить установленный `validate` на файле тела до
  `worker_done`. Это текст brief, а не новая грамматика: авторитетна грамматика
  старой версии.
- Если отчёт `malformed` или `body_integrity` и сессия доказанно жива, в том же
  раунде разрешён один повторный Dispatch с новым id в той же сессии; он не
  начинает новую попытку.
- Второй подряд `malformed` того же слота делает раунд `UNKNOWN` и расходует
  попытку.
- Если усечение или чужой preamble наблюдается воспроизводимо (#29), S1 не может
  получить авторитетный вердикт. Тогда S1 получает `needs_attention` с внешним
  Issue по #29; замена ревью самопроверкой или новым протоколом не допускается.

При такой блокировке S1 остаётся неинтегрированным. Зависимые S2 и остальные
срезы можно разрабатывать в отдельных ветках от прежней `develop` и проверять
детерминированно, но нельзя считать прошедшими парное ревью, переносить их
доказательства в S или агентно сливать. Допустимо отдельно восстановить
поддерживаемую Orca доставку в S3 или дождаться внешнего исправления; затем S1
заново проходит старый установленный протокол на своём точном SHA и только после
успешной интеграции открывает S2. Если Orca не позволяет даже получить два
авторитетных отчёта, финальный исход — `needs_attention/verification_blocked`, а
не `external_blocked`.

**Дефекты жизненного цикла (#32/#33/#34).**

- Координатор рассуждением применяет правило hot/fresh и учёт попыток из раздела
  ниже; methodology уже требует держать remediation-сессии горячими, так что
  новое полномочие не вводится.
- Координатор не закрывает доказанно живую сессию после FINDINGS, даже если так
  предписывает старый текст (#32): сохранение ресурса обратимо и лежит в границе
  §A-ORCHESTRATION-04.
- Отказ старого классификатора экрана на idle-сессии записывается как
  типизированный `session_unavailable` с наблюдением экрана, а не как молчаливый
  повод для новой deep-пары.
- Попытки, потраченные из-за известных дефектов старой версии, учитываются
  честно; исчерпание лимита даёт `needs_attention`, самостоятельное продление
  запрещено.

S2 интегрируется сразу после S1, чтобы S3–S6 уже проверял исправленный жизненный
цикл пары.

### Пара и ранний ремонт

`Dispatch`, PTY, возобновляемая provider session и worktree — разные ресурсы.
`worker_done` расходует Dispatch, но не закрывает сессию. Состояние пары
задаётся фазами
`placed → running → reports_complete → dispositions_pending → same_sha_pass → final_fresh_pair → settled`.
`UNKNOWN` фиксирует неизвестное наблюдение и не придумывает завершение. Это
словарь для скила, а не новая машина состояний или хранилище.

После `FINDINGS` та же пара проверяет исправления через `follow_up` с
собственными предыдущими отчётами и dispositions; байты чужого reviewer ей не
передаются.

**Горячесть слота** определяется одной формулой для каждого слота отдельно:

```text
hot(slot) = alive_and_ready(slot) AND (age < 1h OR context_proven_small(slot))
```

- `age` — время от `worker_done` последнего Dispatch слота по событиям Dispatch.
- `alive_and_ready` — доказанные живая та же provider session, готовность и
  пустой composer.
- `context_proven_small` истинно, только если публичная поверхность доказывает
  не более 100 000 использованных токенов — нормальное рабочее окно по
  §B-SESSION-03.

Доказательством `context_proven_small` служит:

- (а) полностью разобранное абсолютное число использованных токенов, например в
  футере Codex `Context …` (разбор в `mo-harness-screen.mjs` с фикстурами #33)
  или в видимой строке состояния Claude;
- (б) процент использованного или оставшегося окна вместе с размером окна этой
  точной модели, который показан той же публичной поверхностью или подтверждён
  одобренным каталогом моделей.

Обрезанный, частичный или неоднозначный индикатор, процент без доказанного
размера окна и любая эвристика дают `context=unknown`. В этом случае
`context_proven_small` ложно, и решает только `age`. При `age < 1h` слот горячий
независимо от объёма контекста — это правило владельца из #34.

**Замена слота.** Слот, для которого `hot` ложно, заменяется. Новая сессия той
же модели в том же слоте получает `Mode: requested=follow_up`, только
собственные отчёты этого слота и dispositions и проверяет исправления и их
причинных соседей. Это соответствует §B-SESSION-04 («поднимать новую с
переданным состоянием») и не считается ни новой независимой deep-парой, ни
финальной свежей парой. Второй слот при этом продолжает горячим, если для него
`hot` истинно; могут быть заменены оба слота.

Новая независимая deep-пара при паре без PASS запрещена (#34). Исключение — одна
из закрытых причин, записанная в отчёте раунда:

- `state_transfer_impossible` — отчёты или dispositions слота недоступны или
  `UNKNOWN`, поэтому ни продолжить, ни заменить слот с переданным состоянием
  нельзя;
- `hypothesis_stuck` — около десятка безуспешных итераций по одной гипотезе,
  §B-SESSION-01;
- `requirements_conflict` — требования в сессиях противоречат друг другу;
- `owner_request` — прямое указание владельца.

Без записанной причины запуск отклоняется.

После двух PASS текущего кандидата стартует свежая независимая финальная пара на
**том же** SHA. Если она находит FINDINGS, они обрабатываются в ней самой: она
становится горячей парой, и ещё одна свежая пара не заводится, пока эта не даст
PASS.

**Учёт парных попыток.** Парная попытка — один раунд, в котором оба слота выдали
валидный отчёт или типизированный `UNKNOWN` по одному кандидату SHA. Горячий
`follow_up`, замена слота, deep-пара и финальная свежая пара вместе с её
`follow_up` расходуют попытку одинаково. Один повторный Dispatch после
`malformed` внутри раунда попытку не расходует. На существенный срез приходится
не больше пяти попыток; новый SHA счётчик не сбрасывает. Отчёт каждого раунда
называет две величины: `attempt <n>/5` и `deep_reads <m>` — число полных
независимых перечитываний проекта (deep-пары и финальная свежая пара). Так
координатор видит, что свежие пары — самый дорогой путь. Это текст отчёта, а не
хранилище. По пятой попытке заканчивается активная ремедиация, затем следующий
срез либо `needs_attention` по действующей methodology. Срез, исчерпавший лимит
до `settled`, не считается прошедшим.

**Ранний ремонт.** Подтверждённое владельцем раннее исправление после **первого
полного валидного FINDINGS** разрешено, лишь когда выполнены все условия:

- разработка идёт в отдельном worktree исполнителя;
- reviewer A и B имеют каждый своё отдельное дерево;
- checkout reviewer закреплён в detached HEAD на старом полном SHA;
- brief запрещает читать изменяемые refs исполнителя;
- HEAD и чистота перепроверяются непосредственно перед `worker_done`.

Если хоть одно свойство не доказано, координатор ждёт оба отчёта до ремонта.

Первый body публикуется в своём слоте без изменений, по механике существующей
передачи пары: исключительное создание временного файла, проверка realpath,
regular file, размера и конечного маркера, без последующей перезаписи.
Исполнитель читает его и подтверждает
`Review-Preview-Ack: <pair_id> <slot>=<bytes>`; `<bytes>` обязан совпасть с
размером опубликованного файла. Это **не** парный вердикт. Второй reviewer
продолжает работу на старом SHA. После второго body исполнитель читает оба
полных отчёта и подтверждает `Review-Handoff-Ack: <pair_id> A=<bytes> B=<bytes>`
до следующего кандидата. Каждая находка B получает disposition с проверкой
против нового кандидата; «уже исправлено» по памяти раннего ремонта
недостаточно. При ошибке доставки допускается один повтор тех же путей, затем
`UNKNOWN` с сохранённым namespace.

### Владение review-ресурсами

До новой пары инвентаризируются собственные сессии, терминалы и worktree. Ресурс
считается **собственным осиротевшим** только при одновременном выполнении всех
условий:

1. после `orca worktree create/show` получен точный Orca worktree id; одним
   `worktree set --comment` записана первая строка
   `MO-REVIEW-RESOURCE/1 pair=<pair_id> slot=<A|B> candidate=<full-sha> project=<orca-project-id> worktree=<orca-worktree-id>`
   и вторая человекочитаемая строка. Перед действием `worktree show` возвращает
   ту же первую строку и тот же id. Связь terminal id и provider session id с
   этим worktree подтверждается публичными Orca `terminal show/list` и
   `worker show/status`; угадывание по имени или короткому SHA не принимается;
2. общий Git dir worktree совпадает с исходным проектом, а проект
   зарегистрирован в том же Orca;
3. к ресурсу не подключена живая сессия или процесс агента, и это не checkout
   координатора или исполнителя;
4. worktree чист (нет незакоммиченных и неотслеживаемых изменений) и не является
   зависимостью другого живого ресурса.

Такой ресурс освобождается адресно через Orca: сначала доказанно зависимые
терминалы по точным terminal id, затем worktree по точному worktree id. Force не
применяется, `git worktree prune` не применяется. Если связь любого id, метка
или живость сессии неизвестна, ресурс сохраняется и получает
`needs_attention/ownership_unknown`; чужой и немаркированный ресурс не блокирует
следующую пару. Грязное собственное дерево не удаляется и называется в отчёте.
Маркированная живая сессия не освобождается: она проверяется на пригодность как
горячий слот, иначе остаётся на месте. Чистое собственное дерево с правильным
exact-SHA placement переиспользуется. Регрессионная фикстура подставляет похожий
marker с другим `worktree=<id>` и требует отказа от удаления.

**Видимость пары (#38).** Вторая строка того же comment содержит
`<feature> review slot A|B @ <short sha>`, а `--workspace-status in-review`
остаётся человекочитаемым статусом. После старта координатор одной строкой
называет человеку проект Orca кандидата, имена worktree и заголовки вкладок,
отдельно оговаривая случай, когда проект кандидата отличается от проекта
координатора. `--activate` не используется, фокус без нужды не переключается.

### Доставка и зависимости Orca

`mo-harness-screen.mjs` получает фикстуры:

- начального и повторного idle Claude/Codex;
- `Context …` — полного абсолютного, процентного и обрезанного;
- длинной ветки;
- diffstat;
- непустого пользовательского draft.

`inject` разрешён только при независимом подтверждении нужного агента, точного
пути, живой сессии и пустого поля ввода. Текстовое сходство невидимой Claude
suggestion с подсказкой не доказывает, что `draft` безопасно стереть. Пока
публичная поверхность Orca не отличает suggestion от пользовательского draft,
неизвестный непустой `draft` даёт `refuse`. Reattach разрешается, только если
публично доказаны session id, тот же supervised harness и mailbox с
`worker_done`; `--continue` и наличие терминала сами по себе этого не
доказывают.

Для #43 trust recovery сохраняет штатный Codex harness, ownership worktree и
mailbox. Частичный Dispatch после доказанной неудачи освобождается адресно.
Terminal-first запуск допустим, если он реально предоставляет поддерживаемый
интерактивный supervised harness и `worker_done`; сырой
`orca terminal create --command "codex exec …"` не считается reviewer.

Для #29 Orca preamble обязан уступать явно объявленной task-specific полной
grammar body. Координатор проверяет её в живом Dispatch и повторно валидирует
полученный body. Тест совместимости #29 фиксирует для наблюдаемой версии Orca
нормализацию, которую доставка применяет к байтам файла тела, если она есть.

По каждому из #29/#33/#43 спецификация реализации записывает:

- точный недостающий контракт Orca;
- наблюдаемую версию;
- внешнего владельца и его issue;
- тест совместимости;
- событие возврата к live-приёмке.

При отсутствии контрактов — `needs_attention`, исходный issue остаётся открытым,
итоговый исход — `needs_attention/external_blocked` (см. «Исходы финального
цикла»).

### Исполнитель и cleanroom self-review

Перед handoff исполнитель сверяет код со спецификацией, доказательствами и
причинными соседями. На harness с доказанной возможностью субагента он
добивается PASS от cleanroom-субагента, которому передаются только спецификация,
diff и кандидат, без истории исполнителя. Замечания исправляются, и исправление
проверяет тот же горячий субагент. После замечаний координатора или внешних
reviewer для самопроверки нужен новый субагент. Если у harness нет такой
возможности, результат — `self_review_unavailable`, а не выдуманный PASS.

Standalone `mo-review-orca`, запущенный самим исполнителем без оркестратора, в
preflight рекомендует **вызывающему исполнителю**, а не оркестратору, такую же
самопроверку до запуска пары (#39). Рекомендация не блокирует: в отчёте
записывается `self_review=<pass|not_done|unavailable>` по заявлению вызывающего.

### Диагностика, знания и установка

`mo-convergence` срабатывает только по прямому вызову владельца
(§A-ACTIVATION-01). Он спрашивает текущего агента и доступных горячих reviewer
об источнике задержки и собственном вкладе, сверяет последовательность раундов
(включая `attempt`/`deep_reads`) и предлагает
`continue|redesign|narrow|accept-limitation|stop`. Обратимое техническое
исправление делает активная роль; изменение продуктовой границы и остановку
решает человек по действующему §A-ORCHESTRATION-04. Скил не создаёт issue сам.

`mo-debug` срабатывает только по прямому вызову. Он принимает явные пути или
идентификаторы **собственных** Claude/Codex сессий и ограничение по времени или
числу записей. Чтение ищет реальные вызовы `mo-*` и отклонения — прежде всего в
оркестрации, затем в review.

Результат — локальный обезличенный отчёт:

- категории:
  `skill_text_defect|agent_deviation|backend_defect|harness_defect|unknown`;
- evidence locator;
- доказанная историческая версия загруженного скила.

Сборка записывает в `metadata` собранного `SKILL.md` значение `source_tree` —
Git tree id входов сборки этого скила (`src/skills/<name>` и используемые
`shared/`). Это значение без самоссылки: собранный `skills/` коммитится вместе с
исходниками, поэтому SHA собственного коммита в нём быть не может, а tree id
воспроизводится проверкой сборки. Название поля окончательно выбирается при
правке §A-DISTRIBUTION-06; его единственный потребитель — атрибуция `mo-debug`.
`mo-debug` сопоставляет `source_tree` из загруженного в сессии текста с
коммитами истории, у которых те же входы. Если совпадения нет, текста нет или он
неполон, версия `unknown`. Текущий установленный текст не приписывается
исторической сессии. Неизвестные формат, версия или владение дают
`partial|unknown`. Секреты, абсолютные пути и частные тела не копируются в
issue.

Внешнюю запись делает только отдельно активированный и уполномоченный
lifecycle-скил по действующему §A-ISSUE-01, с разрешением на публикацию;
`mo-debug` лишь готовит локальный черновик. Узкое разрешённое диагностическое
чтение требует правки §B-SESSION-02, methodology §1 и новой записи
§A-DIAGNOSTICS-01. Оно не служит доказательством исполнения review или
оркестрации и не читает чужие сессии.

**Состояние слоя знаний (#28).** `mo-knowledge-layer.mjs` проверяет точный
кандидат S. Сигналы слоя — литералы в отслеживаемых файлах S:

- (a) `MO-BACKLOG/1` — объявленная команда закрытия в `Makefile`, `package.json`
  или `AGENTS.md`;
- (b) документ papercut, объявленный в таблице знаний `AGENTS.md`, или
  существующий `docs/papercut.md`;
- (c) блок `history_cutoff_sha:` в `AGENTS.md`;
- (d) строка `Knowledge-Layer: enabled` либо `Knowledge-Layer: disabled` в
  `AGENTS.md`; её пишет `mo-setup` по решению человека, как и предлагает #28.

Состояния определяются в таком порядке:

1. `Knowledge-Layer: disabled` и ни одного из (a)–(c) в S →
   `not_enabled reason=declared_disabled`. Это единственный путь сознательного
   отключения ранее включённого слоя.
2. Присутствуют (a), (b) и (c), а маркер (d) отсутствует или равен `enabled` →
   `enabled`.
3. В S нет ни одного сигнала, полный доступный first-parent ancestry S проверен
   (репозиторий не shallow, команды Git завершаются успешно), а ограниченный
   названными путями поиск

   ```text
   git log --first-parent -1 --format=%H -G '(MO-BACKLOG/1|history_cutoff_sha:|Knowledge-Layer: enabled)' S -- AGENTS.md Makefile package.json docs/papercut.md
   ```

   пуст → `not_enabled reason=never_enabled`. Числовой предел коммитов не
   вводится: для утверждения `never_enabled` нужен весь first-parent путь; при
   недоступном объекте или ошибке чтения результат `needs_attention`, не
   отрицательное доказательство.

4. Всё прочее → `needs_attention` с названной причиной: частичный набор,
   `enabled` без (a)–(c), `disabled` вместе с (a)–(c), исчезновение сигналов,
   найденных в истории, неглубокий клон (`git rev-parse --is-shallow-repository`
   = `true`), нечитаемый файл или ошибка Git.

В `not_enabled` G0/GC/G1/G2 именно для слоя знаний не применяются, но exact SHA,
QC, vendor review и E2E остаются. Проект Meta-O всегда `enabled`: маркер
`Knowledge-Layer: enabled` добавляется в `AGENTS.md` и одновременно в
`CLAUDE.md` (или в единственный источник после миграции #22). Перед каждым
reviewer Dispatch brief содержит буквальную строку
`Knowledge-Layer: state=<enabled|not_enabled|needs_attention> reason=<typed-reason>`,
полученную helper на том же SHA. При `enabled` deferral lens требует действующие
knowledge gates; при `not_enabled` возвращает `not_applicable`; при
`needs_attention` возвращает `unknown` и блокирует readiness. Отсутствие строки
в brief тоже `unknown`, даже если reviewer предполагает обычный проект. Новый
манифест не вводится.

**Переносимое ядро проверки текущего дерева (#19).** `mo-setup` поставляет
самодостаточный `mo-knowledge.mjs` на закреплённой `mdast-util-from-markdown`,
уже используемой проектом; помощник остаётся самодостаточным по
§A-DISTRIBUTION-02. CLI:

```text
node tools/mo-knowledge.mjs check --repo <git-root> --business <path> --architecture <dir> --docs <path> [--docs <path> ...] --first-party-root <dir> [--first-party-root <dir> ...] [--exclude <tracked-path> ...]
```

`--repo` можно опустить: действует Git root от cwd. Все пути относительно него;
`--exclude` принимает только точный отслеживаемый путь, выводит его в typed
результате и не поддерживает wildcard. Объявленные docs могут быть файлом или
каталогом. `git ls-files -z` задаёт исчерпывающий набор отслеживаемых файлов в
каждом `--first-party-root`; каждый Markdown файл там обязан входить в
объявленные docs либо иметь явный `--exclude`. Неизвестный новый отслеживаемый
Markdown файл — `violations/unclassified_tracked_file`, а не тихий пропуск.

Ядро проверяет для каждого объявленного Markdown файла: чтение и разбор AST;
ровно один H1; разрешение относительных `.md` ссылок внутри отслеживаемого
дерева; нормализованную подпись каждой ссылки, содержащую H1 цели; уникальные
определения `§B-*`/`§A-*` в объявленных бизнес/архитектурных документах;
разрешимость цитат по всей объявленной документации; хотя бы одну ссылку на
`§B-*` в каждом архитектурном разделе `§A-*`; и пометки `mo-vocabulary-ok` по
действующему контракту. Необъявленный отслеживаемый файл, ложная подпись,
отсутствующий H1, дубликат id и сломанная ссылка — разные диагностики.
Нечитаемый вход или отказ Git — `unknown`, никогда `ok`.

Вывод содержит одну строку
`MO-KNOWLEDGE/1 status=<ok|violations|unknown> files=<n> definitions=<n> uncovered=<n>`
и ограниченные диагностические строки с путём/причиной; exit 0/1/2
соответственно. Положительная фикстура нового проекта проходит без собственного
checker, отрицательные — пропущенный отслеживаемый `.md`, ссылка с неверной
подписью H1, дубликат id и нечитаемый файл — дают ожидаемые typed причины. Вне
ядра остаются purpose-комментарии кода, правила карты приёмки, согласование
глоссария и предупреждения о чужих обозначениях — это местные правила проекта,
названные в шаблоне setup; «рабочий gate без собственного checker» относится к
перечисленному переносимому ядру, а не к этим местным правилам. До собственного
кода проверяются `markdownlint-cli2` с пользовательскими правилами и зрелые
link-checkers. В сообщении коммита объясняется, почему межфайловый граф id ими
не решается. Грамматику id и заголовка ядро импортирует из существующего
`shared/scripts/knowledge-documents.mjs`; `tools/mo-vocabulary.mjs` Meta-O
переиспользует ядро для графа id и сохраняет дополнительные предупреждения.

**История идентификаторов (#21).** Справочник `mo-setup` дословно цитирует
действующую грамматику из кода, и тест сверяет цитаты с исходником:

- id в заголовке: `^§([AB])-[A-Z][A-Z0-9-]*-\d{2}(?=\s|$)`; упоминание в тексте:
  `§[AB]-[A-Z][A-Z0-9-]*-\d{2}` (`knowledge-documents.mjs`);
- определение — Markdown-заголовок любого уровня, текст которого начинается с
  id; раздел определения длится до следующего заголовка того же или более
  высокого уровня;
- трейлер: `^Knowledge-ID-Change: (remove|reuse|editorial) (\S+) via (\S+)$`
  (`mo-knowledge-history.mjs`), не более одного на коммит на каждый id;
- для `remove` и `reuse` трейлер содержит **один** id:
  `Knowledge-ID-Change: reuse §B-EVAL-01 via §A-EVAL-01`; YAML-запись внутри
  раздела `§A-EVAL-01` содержит `action: reuse`, `id: §B-EVAL-01`, непустой
  `reason`, `references_updated: true`, непустой `new_boundary`. Для `remove`
  меняется только `action`; `via` всегда id архитектурного решения, не SHA
  коммита;
- для `editorial` трейлер содержит отсортированный, разделённый запятыми список
  id без пробелов:
  `Knowledge-ID-Change: editorial §B-SESSION-01,§B-SESSION-02 via §A-SESSION-01`;
  YAML-запись в том же решении содержит `action: editorial`,
  `ids: [§B-SESSION-01, §B-SESSION-02]` в том же порядке, непустой `reason`,
  `references_updated: true` и **не содержит** `id` или `new_boundary`.
  `editorial` не разрешает удаление и не заменяет смысловой `reuse`;
- запись авторизации — YAML-блок кода с ключом `knowledge_id_change` (одна
  запись) или `knowledge_id_changes` (список) внутри раздела решения, названного
  трейлером. Каждая запись действует только для текущего parent edge, а не
  разрешает будущие изменения;
- область стадии: `docs/business.md` и `docs/architecture/`, либо объявленные
  проектом пути;
- точки G0/GC/G1/G2 и их связь с `MO-BACKLOG/1`.

Исполняемые примеры всех трёх действий в справочнике проходят тот же
`mo-knowledge-history.mjs` на одноразовой Git-истории; варианты `B2`, `D24`,
заголовок `## §A-EVAL-01: Название`, `via <sha>`, `editorial` с `new_boundary` и
неверно отсортированный список получают ожидаемый отказ. History helper печатает
`definitions=<n>` и отвергает ноль при объявленной обязательной области. Проект
со старыми `B2`/`D24` сначала делает явную миграцию определений и ссылок;
нулевой набор не считается допустимой адаптацией.

`mo-backlog` и `mo-knowledge-history` без `--repo` определяют Git root из cwd,
даже внутри вложенного каталога; явный `--repo` старше; вне Git — typed failure.
`mo-setup` пишет в AGENTS инструкцию «коммитить каждое связное проверенное
приращение, push по запросу».

**Инструкции Claude (#22).** До изменения `AGENTS.md`/`CLAUDE.md` проводится
живая Claude canary в одноразовом каталоге с уникальным токеном, который есть
только в `AGENTS.md`. Поддерживаемые режимы:

- (1) интерактивный Claude Code во вкладке Orca в корне репозитория;
- (2) то же из вложенного cwd;
- (3) headless `claude -p` — режим eval harness;
- (4) интерактивная сессия после `/compact`, поскольку §B-EXECUTOR-03 требует
  перечитывания после сжатия;
- (5) возобновлённая сессия `--resume`;
- (6) проект, только что настроенный `mo-setup`.

В каждом режиме агент обязан дословно назвать токен. Записываются версия Claude
Code и дата.

- Нативное чтение `AGENTS.md` доказано во всех шести режимах — `CLAUDE.md` в
  Meta-O можно удалить и заменить byte-copy gate `make contract`, а `mo-posture`
  проверяет, что версия Claude не ниже проверенной.
- Иначе допускается **только проверенный** `CLAUDE.md` с `@AGENTS.md`.
  Непроверенный fallback блокирует миграцию.

Проекты, которые генерирует `mo-setup`, всегда получают проверенный `CLAUDE.md`
с `@AGENTS.md`: он работает и на более старых версиях Claude. Одновременно
правятся §B-EXECUTOR-03, `shared/references/project-setup.md`,
`AGENTS.md`/`CLAUDE.md`, цель `contract` в `Makefile` и знания. Ни один
промежуточный коммит не оставляет расходящиеся действующие инструкции. Канарейка
остаётся применимым финальным live E2E, поскольку внешнее поведение может
измениться.

## Оценка и контроль качества

Для каждого воспроизводимого дефекта пишется узкий детерминированный
регрессионный тест, показывающий прежний неправильный исход и новый правильный.
Сценарии поведения агента, невоспроизводимые одной фикстурой, получают live E2E
на реальном поддерживаемом harness.

`make mo-eval-cases` сейчас подтверждает 8 скилов и 24 базовых случая
(`positive`, `forbidden`, `degraded`). `mo-reviewer`, `mo-convergence` и
`mo-debug` добавляют по три базовых случая: 11 скилов и 33 базовых случая. Сверх
них добавляются **четыре** случая класса `regression` с отдельными oracle:

| Владелец / case id                                        | Вход                                                                                  | Единственный решающий oracle                                                                                        |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `mo-review-orca/regression-hot-follow-up`                 | Валидные FINDINGS, два доказанно горячих слота, новый candidate SHA                   | Выбран `follow_up` в той же паре; новый deep Dispatch без закрытой причины отвергнут.                               |
| `mo-review-orca/regression-idle-composer`                 | Idle Claude с отдельным suggestion и пользовательским draft, idle Codex с `Context …` | Доставка происходит только при доказанно пустом composer; draft даёт `refuse`, Codex форма распознана.              |
| `mo-orchestrate-orca/regression-cleanroom-after-findings` | Исполнитель получил внешние FINDINGS после прошлого cleanroom PASS                    | Запущен новый cleanroom subagent, прежнему отправляется follow-up только в рамках предыдущей внутренней ремедиации. |
| `mo-setup/regression-knowledge-layer-absence`             | Обычный repo без сигналов и ранее включённый repo с удалёнными сигналами              | Первый получает `not_enabled`, второй `needs_attention`; оба исхода переданы в reviewer brief.                      |

Итого 37 cases; #19/#21/#22/#24 получают прежде всего детерминированные
регрессии и live canary, а не перегруженный модельный case. #40/#41/#43 получают
отдельные live E2E и точечные тесты безопасности. Схема корпуса, валидатор,
документация и тесты меняются вместе. Для четырёх новых cases на одноразовой
старой ревизии выполняется ограниченная дискриминационная проверка, но её исход
не заменяет финальное доказательство. Существующие cases `mo-review-orca` и
`mo-orchestrate-orca`, которые сейчас ожидают `needs_attention` при отсутствии
всех трёх артефактов слоя знаний, переписываются под `not_enabled`,
`declared_disabled` и частичный набор.

**Обязательная модельная матрица меняется по решению владельца.** Каждый
применимый case исполняется на трёх реальных harness профилях:

| Профиль                | Requested route/model/effort | Правило фактической идентичности                                                                                                          |
| ---------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `required-claude-opus` | `claude/opus[1m]/low`        | Нативный Claude `init` и каталог должны доказать конкретный effective id и `low`; неразрешённый алиас блокирует.                          |
| `required-codex-sol`   | `codex/gpt-6-sol/low`        | Точный effective id и `low`; разрешённое действующей §A-EVAL-01 чтение только собственных Codex `turn_context`, пока нет публичного поля. |
| `required-codex-luna`  | `codex/gpt-6-luna/high`      | Точный effective id и `high` по той же границе доказательства.                                                                            |

Две Codex пары модель/effort подтверждены локальным каталогом на 2026-09-28.
Claude catalog на этом запуске вернул `supportedModels() cleanup failed`,
поэтому alias/effective id и доступность `low` должны быть подтверждены живым
запуском; автоматическая замена не допускается.

До реализации меняются:

- §B-EVAL-01 в `docs/business.md` и §A-EVAL-01 в архитектуре;
- `shared/references/methodology.md`;
- `shared/scripts/model-testing-policy.mjs` и `tools/skill-evals.mjs`;
- `docs/e2e.md`;
- все связанные конфигурационные и evidence-тесты.

Существующие desired Codex/OpenCode координаты сохраняются отдельными, с
`NOT_AVAILABLE` при доказанной недоступности; запущенные `FAIL|UNKNOWN`
блокируют. Критический Qwen/OpenCode цикл оркестрации остаётся отдельно.
`repetition=1` сохраняется: повтор ради удачного PASS на том же SHA запрещён;
`FAIL|UNKNOWN` требует исправления причины и нового SHA. При 37 cases новая
обязательная тройка требует до 111 реальных исполнений; доказанная
неприменимость уменьшает это число только по правилу самого case.

**Миграция §A-EVAL-01.**

1. **Точный Claude id.** Он записывается в §A-EVAL-01 по первому нативному
   `init` для `opus[1m]`, с датой и версией Claude CLI, по образцу прежней пары
   `sonnet → claude-sonnet-5`. Дальнейшее несовпадение — типизированная ошибка
   разрешения алиаса. Уровень `low` доказывается той же публичной поверхностью
   Claude, которую сейчас использует `tools/skill-evals.mjs`. Если для этой
   модели уровень публично не наблюдаем, координата `blocked`: исключение на
   приватное чтение распространяется только на Codex.
2. **Codex-исключение.** Узкое исключение от 2026-09-20 на чтение собственного
   `turn_context` применяется к обеим Codex координатам без расширения области:
   только модель и уровень, только собственный процесс, только пока нет
   публичного поля. Запись фиксирует версию Codex CLI, на которой разрыв
   наблюдается повторно, вместо `codex-cli 0.155.0`.
3. **Клапан повышения.** Прежний клапан до `codex/gpt-5.6-terra/low`
   сформулирован для старой Codex координаты. Для новых профилей он недоступен,
   пока владелец не запишет новую цель. Записанных повышений нет, поэтому
   действующие доказательства от этого не меняются.
4. **Старое evidence.** Доказательства v3 со старыми профилями `sonnet/low` и
   `gpt-5.6-luna/low` читаются как `legacy` с `accepted: false` и не закрывают
   проверку.

На **одном полном финальном SHA S** выполняются:

- чистый checkout;
- `make mo-qc`, включая offline `mo-eval-cases`;
- успешные CI-задачи `mo-qc` и `mo-backlog` с доказанным checkout S и
  `CI-Coverage/1 covered` до агентного слияния (см. «QC-гейт вместо reviewer»);
- актуальные G0/GC/G1/G2 там, где применимы;
- две независимые проверки моделями разных поставщиков;
- все применимые B/W E2E;
- новая live-матрица каждого case;
- отдельный критический сценарий Qwen/OpenCode.

`--validate-evidence --candidate S --require-all` сверяет case, профиль,
requested/effective identity, native execution, oracle и SHA. Предварительные
пробы на SHA среза разрешены для диагноза, но не переносятся на S.
`FAIL|UNKNOWN|NOT_RUN` и недоступная обязательная координата блокируют
завершение; единственное типизированное исключение для внешних положительных
путей описано в «Исходах финального цикла». `not_applicable` требует точного
правила из case и доказанного наблюдения. Изменение после S требует нового SHA и
полного повторного доказательства. Если применимы, на каждом итоговом S
повторяются: совместимость Orca preamble/body и нормализации файла тела (#29),
текущие idle-экраны (#33), trust-supervision (#43), Claude AGENTS canary (#22),
восстановление ресурсов и `mo-debug` на реальных собственных сессиях.

Новые B/W сценарии получают уникальные идентификаторы после действующих B52/W4;
номера распределяются при правке `docs/e2e.md` без переиспользования.
Минимальные новые end-to-end oracle:

- `template → validate → worker_done received body`, со сверкой с файлом тела и
  без неё;
- второй reviewer на старом SHA во время раннего ремонта;
- `FINDINGS → hot follow_up → PASS → fresh same-SHA pair`, со счётчиками
  `attempt`/`deep_reads`;
- замена остывшего слота с переданным состоянием при `age ≥ 1h` и
  `context=unknown`;
- idle Claude/Codex с реальным непустым draft и `Context …`;
- Codex trust failure с восстановлением штатного harness;
- видимость пары в проекте кандидата;
- перезапуск координатора с маркированной сиротой, а также с грязным собственным
  деревом и чужим деревом;
- обычный repo `not_enabled`, repo `declared_disabled` и ранее enabled repo с
  исчезнувшими сигналами;
- установленный бандл из вложенного cwd;
- Claude AGENTS canary во всех шести режимах;
- `mo-debug` на собственной исторической сессии с доказанной и неизвестной
  версией.

Если capability harness отсутствует, сценарий выдаёт typed
`UNKNOWN/needs_attention` либо, для внешней возможности Orca,
`blocked:external_capability`. Соответствующий issue не закрывается, фиктивного
PASS нет.

## Порядок срезов, проверки и выходы

1. **S1: протокол ревью** (#20, #25, #27, #29, #30, #31, #37). Грамматика,
   template, файл тела, reviewer brief с `Spec:`, полный Orca body, QC/CI-гейт;
   предварительная живая совместимость. Срез проверяется старой установленной
   версией по правилам бутстрапа, новую версию проверяют тесты и live E2E.
2. **S2: пара и ресурсы** (#26, #32, #34, #35, #38, #40, #41). Exact-SHA
   изоляция, hot/fresh, учёт попыток, ранний ремонт, маркеры владения,
   видимость, cleanup. Интегрируется сразу после S1.
3. **S3: доставка и trust** (#33, #43). Screen fixtures, публичные
   доказательства composer и индикатора контекста, supported harness recovery;
   внешняя зависимость Orca оформляется и повторно проверяется.
4. **S4: исполнитель и диагностика** (#18, #36, #39). Cleanroom self-review,
   рекомендация в standalone review, `source_tree` в сборке, user-invoked
   diagnostics, privacy.
5. **S5: знания и установка** (#19, #21, #22, #23, #24, #28). Состояние слоя
   знаний, portable current-tree checker, history contract, root discovery,
   AGENTS/CLAUDE migration.
6. **S6: корпус и матрица** (сквозная приёмка, без собственного issue). Новые
   eval cases и E2E, новая обязательная тройка профилей, обновлённые
   бизнес/архитектурные документы. Этот срез ставит финальный контракт S.

Срезы допускают зависимый порядок внутри группы. Каждый завершённый срез имеет
свой SHA, подходящий QC, review, применимые E2E и G1/G2 перед агентной
интеграцией. Если положительный путь issue среза заблокирован внешне, срез
интегрирует доказанное fail-closed поведение, а issue остаётся открытым.
Конкретная внешняя работа Orca может идти параллельно, но её отсутствие не
маскируется локальной реализацией. После всех доступных срезов создаётся
финальный S и проводится полный цикл выше с одним из трёх именованных исходов.
На G0 блокнот переносит подтверждённую внешнюю работу в Issue владельца, на
GC/G1/G2 пустота `docs/backlog.md` и удалённый HEAD проверяются в действующих
границах. Нечитаемый исход, неизвестный эффект записи или отсутствующее
доказательство дают `UNKNOWN/needs_attention`, а не автоматическое продолжение.

## Открытые вопросы и условия разрешения

1. **Orca #29/#33/#43:** предоставляет ли текущий поддерживаемый выпуск
   task-specific full body, различение Claude suggestion/user draft и supervised
   Codex trust recovery? Ответ дают живые пробы в Orca и, при отказе, issue
   внешнего владельца с точным контрактом. До PASS эти исходные issues не
   закрываются, а итоговый исход — `needs_attention/external_blocked`.
2. **Claude alias:** во что фактически разрешается `opus[1m]` и наблюдаем ли
   `low` публично на установленном harness? Ответ даёт нативный `init`/каталог и
   один live case; результат записывается в §A-EVAL-01. При недоступности
   обязательная координата `blocked|not_run`, без подмены; изменение профиля
   требует нового решения владельца и правки §B-EVAL-01.
3. **Индикатор контекста для #34:** порог и правило доказательства заданы (≤100
   000 токенов, абсолютное число либо процент с доказанным окном). Открыто
   только, какие именно формы показывают текущие Codex footer и строка состояния
   Claude. Их фиксируют фикстуры S3; всё, что не доказывает число токенов,
   остаётся `context=unknown`, и действует правило времени.
4. **Историческая версия для mo-debug:** сессии до S4 не несут `source_tree`.
   Для них версия устанавливается только по сохранённому артефакту с доказуемым
   происхождением, иначе `unknown`; текущий SHA не приписывается.

Эти вопросы не делают интерфейс неопределённым: у каждого уже задан безопасный
исход и критерий, после которого соответствующий путь можно принять.

## Отвергнутые и отложенные варианты

Отклонены:

- новый движок, прокси или state store;
- сырой `codex exec` как reviewer fallback;
- стирание непроверенного Claude draft;
- самопубликация issues из `mo-debug`/`mo-convergence`;
- объявление #29/#33/#43 исправленными по fail-closed отказу;
- автоматическое закрытие всех issues одним merge или `Fixes`;
- повторы live eval до PASS;
- общий лимит пяти попыток на все 25 issues;
- новая независимая deep-пара на каждой итерации remediation;
- `git worktree prune` и force-удаление собственных грязных деревьев;
- удаление `CLAUDE.md` только по номеру версии;
- сверка body по числу байтов, прочитанному с экрана терминала;
- SHA собственного коммита в метаданных сборки, невозможный без самоссылки;
- рецензирование S1 новым протоколом из самого кандидата S1.

Отложена одна строго каноническая форма тела находки: вернуться к ней можно лишь
при доказанной неоднозначности двух допускаемых форм и согласованной миграции
§A-REVIEW-04.
