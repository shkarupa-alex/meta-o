# Возможности бэкенда

Meta-O поддерживает бэкенд только тогда, когда его публичная нативная
поверхность проходит общий контракт и реальные сценарии документа
[Сквозная проверка](e2e.md). Обязательное поведение имеет одного автора в
[Backend contract](../shared/references/backend-contract.md), а механика бэкенда
задаёт точные команды.

Поддержка конкретного запуска здесь не фиксируется. Версии диагностичны и не
прибиты. Бэкенд, потерявший извлечение полного финального ответа, обработку
вопросов или надёжное различение состояний, становится неподдерживаемым до
устранения наблюдаемого сбоя.

## Запуск вне Orca

Бэкенд нужен исполнителям, а не самому рассуждению. Поэтому каждый скил Meta-O
запускается и из обычной оболочки; отличается только то, чем именно он в этот
момент распоряжается.

| Скил                                         | Вне Orca | Условие                                                      |
| -------------------------------------------- | -------- | ------------------------------------------------------------ |
| `find-reuse`, `senior-jsts`, `senior-python` | да       | Orca не нужен                                                |
| `mo-setup`                                   | да       | часть отчёта про Orca считается отдельно                     |
| `mo-review-orca`                             | да       | исполнители остаются ресурсами Orca                          |
| `mo-e2e`                                     | да       | контроллер портируем, E2E-исполнитель остаётся ресурсом Orca |
| `mo-watchdog`                                | да       | наблюдает только цели Orca                                   |
| `mo-orchestrate-orca`                        | да       | наблюдатель не является условием запуска                     |

Своё положение оркестратор узнаёт по одному условию — по собственному
дескриптору терминала: `ORCA_TERMINAL_HANDLE` в окружении и читаемый
`orca terminal read --terminal "$ORCA_TERMINAL_HANDLE" --screen --json` — это
«внутри»; отсутствие переменной или отказ этого чтения — «снаружи». Где стоит
процесс, не решает ничего и вторым условием не становится: обычная оболочка в
зарегистрированном worktree не владеет терминалом, а созданный Orca терминал
сохраняет свой дескриптор из любого каталога. Форма без `--terminal` разрешает
терминал, на котором стоит фокус приложения, а не терминал вызывающего, и
признаком размещения не является. Тогда селекторы `current` и `active` не
называют ничего, Run создаётся без `--from`, ожидание идёт через
`check --run <id> --wait`, а заголовок координатора не ставится. Отсутствие
наблюдателя не останавливает работу: оркестратор один раз называет принятое
ограничение и продолжает.

## Идентичность модельного исполнителя

Доказательство эвала называет фактические модель и уровень рассуждений, а не
запрошенные, поэтому границей поддержки становится и то, публикует ли
исполнитель этот факт.

| Исполнитель | Публичная поверхность идентичности                                 | Наблюдение                                                                                                                 |
| ----------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| Claude      | событие `init` в `claude -p --output-format stream-json --verbose` | сессия и фактическая модель приходят публично                                                                              |
| Codex       | нет                                                                | `codex-cli 0.155.0`: `codex exec --json` даёт только `thread.started`, `turn.started`, `item.completed` и `turn.completed` |

Разрыв у Codex закрыт узким исключением §A-EVAL-01, которое читает только этот
факт и только из журнала собственного запуска. Появится публичная поверхность —
исключение прекращается, и запись выше называет версию CLI, на которой разрыв
наблюдался, чтобы это можно было перепроверить.

## Обязательные companion-скилы

| Бэкенд | Управление            | Обязательные companion-руководства |
| ------ | --------------------- | ---------------------------------- |
| Orca   | `orca` или `orca-cli` | `orchestration`, `orca-cli`        |

Управляющий исполняемый файл и каждое руководство проверяются отдельно. Наличие
исполняемого файла не доказывает, что агент знает семантику бэкенда.
Документированный пакет бэкенда подходящей версии считается источником
companion-скила, если полное руководство читается и управляющий агент прочитал
его до действий; установка в личный каталог среды агента для этого не нужна.

Работоспособность управления и готовность каждой среды агента — тоже разные
свойства. Готовность Orca должна быть доказана для каждой выбранной среды; общий
статус плоскости управления не отменяет сбой запуска поставщика.

## Внешние контракты Orca

Три сценария зависят от возможностей Orca, которых в наблюдаемом выпуске нет.
Meta-O здесь закрывается безопасным отказом, но отказ не восстанавливает штатный
путь: соответствующие issue остаются открытыми до живого `PASS`, а сценарии в
[Сквозная проверка](e2e.md) дают `blocked:external_capability`. Внешний владелец
у всех трёх — Orca (`stablyai/orca`). Внешний Issue заводится только с
разрешения владельца проекта на публикацию; пока его нет, запись здесь и есть
контракт, а исход — `needs_attention/external_blocked`.
