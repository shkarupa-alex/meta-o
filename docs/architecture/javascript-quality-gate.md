# §A-QUALITY-01 — JavaScript-границы проверяет ESLint

```yaml
knowledge_id_changes:
  - action: reuse
    id: §A-QUALITY-01
    reason:
      Все first-party test entrypoints должны сохранять отдельный process
      lifecycle host-sensitive posture tests.
    new_boundary:
      Обычные test files выполняются последовательно, затем provider-posture
      запускается в отдельном Node process; npm test делегирует этому же gate.
    references_updated: true
```

## Решение

Весь собственный JavaScript проходит ESLint внутри `make mo-lint`. Проверка
контролирует рекомендуемые правила корректности, цикломатическую сложность,
глубину вложенности, размер функции и модуля, а также JSDoc у публичного API и
классов. Сгенерированное дерево `skills/` повторно не проверяется: его байты уже
доказаны `skills-check`, а проверка принадлежит исходным модулям.

Базовые пределы — 500 строк на модуль, 80 строк на функцию, сложность 15 и
глубина вложенности 4. Исключения живут в `eslint.config.mjs`, а не в памяти
сопровождающего:

- самодостаточный `mo-models.mjs` имеет отдельный измеренный предел, а
  `mo-models.mjs` и `build-skills.mjs` — пределы уже измеренной сложности,
  потому что первый собирается в устанавливаемый скил без пакета среды
  выполнения, а второй целиком владеет атомарной транзакцией сборки;
- тестовые фикстуры и имитации оркестрации допускают больше строк и ветвей, но
  их отдельные пределы всё равно блокируют новый неограниченный рост. Одна
  кампания мутаций в `provider-posture.test.mjs` имеет отдельный предел функции:
  её фикстуры должны оставаться в одном жизненном цикле теста с общей очисткой.

Проверка ничего не изменяет: `eslint .` только оценивает отслеживаемые
исходники. Автоматическое исправление в `make mo-qc` не входит.

`mo-test` последовательно запускает обычные тестовые файлы через
`--test-concurrency=1`, а затем проверяет чувствительный к хосту
`provider-posture` в отдельном процессе Node. Это сохраняет полный набор
утверждений, но не переносит состояние группы процессов и нагрузку тяжёлого
обхода истории Git в средство запуска проверок режима.

`npm test` делегирует тому же `make mo-test`: параллельной собственной точки
входа с прежним шаблоном запуска в одном процессе нет.

## Бизнес-причина

Решение служит §B-LONGEVITY-02: границы кода должны ломаться в проверке, а не
зависеть от внимания ревьюера. Оно также поддерживает §B-LONGEVITY-01: дешёвое
добавление новой ветви не должно незаметно превращать помощник в
неподдерживаемую границу.

Если §A-QUALITY-01 отменяется, зависимости ESLint, конфигурация и его шаг в
`make mo-lint` становятся лишними; вместо них нужна другая зрелая неизменяющая
проверка JavaScript с теми же границами.
