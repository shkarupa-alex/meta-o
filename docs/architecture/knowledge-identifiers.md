## Решение

Каждый самостоятельный тезис в [Зачем существует Meta-O](../business.md) несёт
идентификатор `§B-<AREA>-<NN>`. Каждое архитектурное решение несёт
`§A-<AREA>-<NN>` и обычным текстом называет тезисы, которым служит. Назначение
модуля и символа называет `§A-*` и не ссылается на бизнес-уровень напрямую:
цепочка уже проходит через решение.

Идентификатор уникален, стабилен и не переиспользуется. Грамматика —
`§[AB]-[A-Z][A-Z0-9-]*-\d{2}`; латиница здесь технический идентификатор, а не
человекочитаемый текст. Служебных блоков вида `Derived from` или `Implemented by`
нет: связь читается как обычное предложение.

Тезис — это раздел третьего уровня бизнес-постановки, решение — заголовок с
якорем в `docs/architecture/`. Проверка опирается на эту структуру, поэтому раздел
третьего уровня без якоря считается забытым тезисом, а не свободной прозой.

Граница поставки проходит по тому, что установит чужой проект:

- исходный Markdown может содержать отдельный HTML-маркер
  `<!-- mo:source-anchor <architecture-id> -->`. Сборка разбирает позиционный AST
  Markdown и удаляет точный диапазон байтов маркера справа налево, не сериализуя
  документ. Обычные упоминания идентификатора не удаляются; маркер в коде, прозе или ссылке,
  а также повреждённый маркер останавливает сборку. Сгенерированные скилы не
  содержат id проекта;
- скрипты-помощники, которые сборка копирует побайтово, — `mo-posture.sh` и
  `mo-watchdog.sh`, — несут `§A-*` в чужой проект сознательно. Id здесь
  провенанс кода, поэтому в шапке он всегда назван вместе с проектом-владельцем
  (`meta-o §A-POSTURE-01`): потребитель читает чужую координату, а не висячую
  собственную ссылку, и разрешать её ему не нужно. Это же требует поставляемое
  правило назначения;
- `mo-models.mjs` собирается бандлером, и его шапка в поставку не попадает
  вообще. Назначение этого помощника читают по источнику, а не по установленной
  копии;
- недистрибутируемые файлы (`tools/`, `tests/`) называют `§A-*` всегда;
- поставляемая методология требует того же от любого проекта общими словами.
  Конкретные идентификаторы принадлежат проекту, а не поставке.

В `.mjs` экспортируемые объявления функций и классов несут JSDoc, который
объясняет назначение и называет `§A-*`; это проверяет `eslint-plugin-jsdoc`. Для
`.sh` нет выбранного зрелого парсера или линтера, надёжно проверяющего смысловое
назначение каждой функции. Поэтому оболочка имеет машинно проверяемый заголовок
модуля и обязательное поимённое ревью содержательных функций. Собственный
регулярный парсер не создаётся.

Историческая нижняя граница — воспроизводимый входной коммит программы
`75a95f87efe6cea53167fa3f8d8c3b09a7c7ad96`:

```yaml
program_input_sha: 75a95f87efe6cea53167fa3f8d8c3b09a7c7ad96
```

`tools/knowledge-history.mjs`
перечисляет полный граф истории через `git rev-list --topo-order --reverse --parents`,
читает блобы через интерфейс объектов Git и проверяет каждое ребро от родителя.
Тихое удаление или смысловое повторное использование после нижней границы требует
трейлера:

```text
Knowledge-ID-Change: remove <id> via <architecture-id>
Knowledge-ID-Change: reuse <id> via <architecture-id>
Knowledge-ID-Change: editorial <sorted-id>,<sorted-id> via <architecture-id>
```

Трейлер разрешает изменение, только когда указанное решение существует в том же
коммите и добавляет относительно проверяемого родителя отдельную машиночитаемую
YAML-запись с действием, идентификатором, непустыми причиной и новой смысловой границей, а
также `references_updated: true`:

```yaml
knowledge_id_change:
  action: reuse
  id: <business-id>
  reason: Требование разделено на две независимо проверяемые части.
  new_boundary: Старый id теперь обозначает только первую часть.
  references_updated: true
```

Чистая редактура нескольких заголовков, подписей ссылок или пробелов может
использовать одну запись `editorial`: её отсортированный список `ids` должен в
точности совпасть со всеми существующими определениями, семантический отпечаток которых
изменился на этом переходе от родителя, кроме идентификаторов с отдельным
валидным трейлером `reuse`. Такая запись содержит непустую причину и
`references_updated: true`, но не выдумывает новую границу. Она не разрешает
удаление идентификатора, изменение обычной прозы или идентификатор, не включённый в её
собственный список. Для каждой секции проверка сохраняет весь AST, кроме текста
заголовков и подписей ссылок, и нормализует пробелы только в обычном тексте.
Встроенный код и блоки кода сравниваются побайтово. Поэтому замена нормативного слова,
предложения или байта технического литерала требует обычного `reuse`. YAML-блоки авторизации в
семантический и редакторский отпечатки не входят, но их нормализованные записи
образуют добавляемый журнал: запись родителя обязана без изменений присутствовать
у потомка.

```yaml
knowledge_id_change:
  action: editorial
  ids:
    - <architecture-id>
    - <business-id>
  reason: Человекочитаемые формулировки приведены к языку проекта.
  references_updated: true
```

Ссылки проверяются на каждом коммите диапазона, а не только на текущем `HEAD`:
ссылка — свойство одного дерева, поэтому коммит с висячим id, исправленный более
поздним коммитом, иначе полностью исчезает из результата. Благодаря этому
`references_updated: true` в записи авторизации перестаёт быть
самоутверждением на уровне двух документов знаний.

Удаление при слиянии считается унаследованным, только когда id отсутствует у
другого родителя и присутствовал в их базе слияния. Родитель, ответвившийся до
создания id, ничего не удалял, и слияние в его пользу не имеет права терять id
молча.

Смысловое повторное использование проверяется начиная с явно закреплённого
коммита, добавившего саму проверку:

```yaml
semantic_enforcement_sha: 4127f414a43fee467415db955a2ed19e57ebc159
```

Два перехода между нижней границей и этой границей изменили тело секции по правилу,
которого тогда ещё не существовало; история не переписывается, чтобы это скрыть, и
граница не выводится из состояния файлов. Удаления и ссылки проверяются от
нижней границы без исключений.

Привязка разрешающей записи к конкретному переходу от родителя применяется
начиная с проверенного кандидата, после которого правило стало исполняемым:

```yaml
current_record_enforcement_sha: 661eaf0f25a3d50c1f5aef686b106eddfe9a9489
```

Граница оставляет в прежней проверке формы ровно одно старое ребро
`3a292e716e9614c9ff71b138d2dc8b10ee2d551f..a8113132c2f7a23d0a7cd18c156de527108dd953`
со смысловым повторным использованием §A-DELIVERY-01: оно появилось до правила,
учитывающего ребро, и история не переписывается ради вымышленной записи
авторизации. Само ребро с исправлением
`661eaf0f..2e8dd1a` уже проверяется новым правилом.

Строгое ограничение `editorial` применяется к переходам после завершённой
языковой миграции:

```yaml
strict_editorial_enforcement_sha: 6e30dc1d3a386c41df06cf8ed7562b099501f11b
```

До этой границы `editorial` дополнительно сохраняет литералы и ссылки на §-id,
но не доказывает эквивалентность обычной прозы. История сохраняет это ограничение
явно; все последующие переходы проверяются по узкому машинно доказуемому классу.
С этой же границы записи авторизации становятся добавляемым журналом: более
ранние переходы не проверяются по правилу, которого тогда не существовало.

Нижняя граница и все границы применения обязаны разрешаться в коммит из истории
`HEAD`; существующий соседний коммит считается недостижимым и даёт
`history_unavailable`. Одного `rev-parse` недостаточно: сосед заставил бы все
последующие проверки происхождения по рёбрам вернуть ложь и молча отключил бы
правило. `merge-base` также остаётся дешёвой защитой ветки для жизненного цикла
фичи.

## §A-MEMORY-02 — Дословный реестр живёт с задачей, постановка хранит тезисы

Полный дословный реестр пользовательских намерений — исходный запрос и каждое
последующее уточнение, мнение, исправление, предпочтение и ограничение — ведётся
вместе с задачей или спецификацией и нормативен для исполнителя и ревьюеров.
Бизнес-постановка хранит те же интенты сведёнными в устойчивые тезисы: смысл
сохраняется, формулировка — нет, и остаётся только то, что переживает конкретную
реализацию.

Разделение реализует §B-MEMORY-04 и следует §B-FRAMING-01 и §B-MEMORY-03:
дословный ledger нормативен вместе с задачей, намерение хранится отдельно от
выведенных из него требований, а реализованная спецификация вместе со своим
реестром уходит из проекта. Иначе постановка вырастает в нечитаемую переписку, а
отменённый разговор читается будущим агентом как действующее требование. Там,
где дословная запись ещё нормативна, пересказ её не заменяет — этого требует сам
§B-MEMORY-04.

Если §A-MEMORY-02 отменяется, сведение становится лишним: постановка снова растёт
дословной перепиской, и проект теряет единственный документ, который человек
действительно читает целиком.

## §A-MEMORY-03 — Удалённый бэклог сохраняет проверяемое происхождение в Git

Временная карта закрытия существует только в контрольном коммите и связывает каждый
узел AST замороженного реестра с явно назначенными обязательством, владельцем, решением и
реальным доказательством. После удаления программных артефактов
`docs/acceptance.md` сохраняет id исходных блобов, коммит закрытия, блоб карты и
постоянную команду проверки.
`tests/backlog-provenance.test.mjs` проверяет достижимость объектов, точную
разрешённую дельту удаления и существование каждого долговечного пути
доказательства. Он не
считает структурную биекцию доказательством семантического закрытия.

Это решение служит §B-MEMORY-03, §B-MEMORY-04, §B-PROOF-01 и
§B-LONGEVITY-04. Если §A-MEMORY-03 отменяется, временная карта, ссылки на объекты Git
и постоянная проверка происхождения удаляются вместе: оставлять непроверяемую
квитанцию без потребителя запрещено.

## §A-MEMORY-04 — Поведенческий дефект оставляет регрессионную проверку и инвариант

Подтверждённый воспроизводимый поведенческий дефект получает минимальную целевую
регрессионную проверку, падающую до исправления. Существенная правка владения,
конкурентности, доверия, безопасности, совместимости, транзакции или времени жизни
ресурса сохраняет в продуктовом коде комментарий о неочевидном инварианте и причине
границы. Комментарий не пересказывает синтаксис и не содержит локальный идентификатор
замечания из отчёта.

Решение служит §B-REVIEW-02 и §B-SELFHOST-02: повторный класс сбоя должен ловиться
раньше и быть понятен следующей сессии. Без §A-MEMORY-04 контракт настройки,
регрессионная норма и комментарии об инвариантах становятся лишними, а найденный
дефект снова остаётся только в транскрипте.

## Бизнес-причина

Решение служит §B-MEMORY-01 и §B-MEMORY-02: уровни знаний существуют, чтобы агент
шёл маршрутом, а связи между ними работали в обе стороны. Без имени у тезиса
маршрут проходится только сплошным чтением, а совпадение формулировок ломается
при первой же редактуре — тогда снизу вверх дойти до бизнес-смысла нельзя.

§B-LONGEVITY-02 требует, чтобы такая граница проверялась машинно и блокирующе:
надежда на внимательность ревьюера не переживает нескольких лет разработки.
§B-PORTABILITY-04 определяет язык идентификатора, а §B-PORTABILITY-03 — почему
поставка остаётся без наших якорей: знание, читаемое только вместе со скилом,
делает проект непередаваемым.

## Что проверяет проверка

`tests/knowledge-chain.test.mjs` в `make mo-qc` разбирает Markdown настоящим AST
и требует: у каждого тезиса есть якорь, все идентификаторы уникальны, каждое `§A-*` называет
существующий `§B-*`, каждый первичный модуль кода называет существующий `§A-*` и
не ссылается на `§B-*` напрямую, висячих ссылок нет, сгенерированные скилы не
содержат якорей, а исходник использует только позиционные маркеры.
`tests/knowledge-history.test.mjs` проверяет полный граф истории от
нижней границы.
Отдельная проверка требует, чтобы в шапке побайтово
копируемого скрипта рядом с каждым `§A-*` стояло имя проекта-владельца.

## Чего решение не требует

Обязательного покрытия «у каждого тезиса есть своё решение» нет. Тезис, который
продукт реализует самим текстом методологии, не получает архитектурного документа
ради формальной полноты: документ без названного потребителя запрещает
§B-CONTROL-04. Проверка ловит разорванную цепочку, а не отсутствие решения.

## Что станет лишним при отмене

Если §A-MEMORY-01 отменяется, удаляются якоря в бизнес-постановке и архитектуре,
ссылки наверх в заголовках назначения и сам тест цепочки. Связь уровней
возвращается к совпадению слов, и цену этого платит тот, кто через год спросит,
зачем код вообще существует.
