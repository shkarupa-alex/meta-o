# §A-WAIT-01 — Одна общая точка ожидания следит за активностью всех исполнителей запуска

```yaml
knowledge_id_changes:
  - action: reuse
    id: §A-WAIT-01
    reason: >-
      Исполнитель завершил задачу на границе тихого тайм-аута, а координатор
      судил о ходе работы по устаревшему предпросмотру терминала и не заметил
      завершения, пока пользователь не спросил статус (#54); подтверждение
      передачи отчёта приходит сообщением `status`, которого не было в наборе
      пробуждения.
    new_boundary: >-
      Набор пробуждения выводится из наблюдаемой фазы: `status` входит в него,
      только пока отправленная передача отчёта не подтверждена. Тихий тайм-аут,
      ответ пользователю о статусе и повторное сообщение исполнителю проходят
      контрольную точку сверки с публичным Orca; ожидание перевооружается только
      после неё, а неустановленное состояние — честный `unknown`.
    references_updated: true
```

## Решение

Вызывающая сторона держит одну блокирующую точку ожидания для всех активных
исполнителей и распределяет `worker_done`, `escalation` и `question` по точному
дескриптору. Интервал ожидания равен наименьшему интервалу среди ожидаемых
классов: для исполнителя реализации — до 600000 мс, для ревьюера и
E2E-исполнителя — до 300000 мс. Значимое событие завершает ожидание раньше;
тайм-аут без событий разрешает публичную сверку по контрольной точке ниже и
возобновление ожидания без сообщения исполнителю или человеку.

После первого сбоя транспорта тот же интервал повторяют один раз, после второго
возвращают `UNKNOWN/needs_attention`, не перезапуская, не освобождая и не
заменяя исполнителей. Пакет событий обрабатывают целиком в порядке, заданном
бэкендом, до подтверждения; события чужих или уже освобождённых исполнителей
отбрасывают. Запрещены `sleep`, ежеминутный опрос и несколько ожидающих
процессов для одного исполнителя.

Набор пробуждения — `worker_done`, `escalation` и `question`. К нему добавляется
`status`, пока в запуске есть отправленная исполнителю передача отчёта ревью —
предпросмотр или пара — без соответствующего `Review-Preview-Ack` или
`Review-Handoff-Ack`: подтверждение приходит именно сообщением `status`. Фазу
выводят из наблюдаемых сообщений Orca, а не из памяти вызывающей стороны,
поэтому она восстановима и после компакции. Постоянный `status` в наборе
отклонён: это лишние пробуждения на каждом сообщении о ходе работы.

Контрольная точка проходится после каждого тихого тайм-аута, перед любым ответом
пользователю о статусе и перед любым повторным сообщением исполнителю:

1. Прочитать текущий непрочитанный пакет запуска без ожидания, включая `status`,
   сопоставить сообщения с точными Dispatch и обработать пакет целиком до
   подтверждения. Уже доставленное подтверждение передачи проверяется помощником
   отчёта ревью; повторное «продолжай» не отправляется.
2. Для каждого активного Dispatch прочитать его публичное состояние. Завершение
   Dispatch и живость исполнителя — независимые факты: завершённый Dispatch
   обрабатывается через свой `worker_done` до ответа, а `unverifiable` или
   `stale_status` живости завершения не отменяют. Завершённый Dispatch без тела
   — неполное доказательство, а не продолжающаяся работа.
3. Ход агента и его дочерний процесс — разные состояния. Простаивающее поле
   ввода при ещё идущей дочерней команде значит, что агент сообщений пока не
   читает: оба факта сообщаются раздельно, а указание ставится в очередь того же
   терминала по правилам доставки §A-DELIVERY-01, один раз.
4. Обрезанный предпросмотр терминала исхода не доказывает. Без установленного
   состояния ответ — `unknown/unverifiable`.

Ожидание перевооружается только после этой сверки, и утверждать «жду», когда
ожидание не взведено, нельзя.

Решение служит §B-UPTIME-03, §B-UPTIME-05 и §B-CONTROL-04. Без §A-WAIT-01 ранние
завершения и вопросы теряются, тайм-аут без событий ошибочно выглядит как сбой,
а повторные опросы и ожидания создают лишнюю нагрузку и гонки владения.
